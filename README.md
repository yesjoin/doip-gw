# doip-gw

DoIP 诊断网关：以太网侧收 DoIP，CAN 侧走 ISO-TP，中间做翻译。

**项目三**。前两个项目：`uds-ecu`（CAN 上的 ECU）、`dbc-toolkit`（DBC 词典与代码生成）。

---

## 现在到哪了

**M0 完成**：DoIP 报文的字节层。只做"字节 → 结构 → 字节"，不碰 socket、不碰总线。

理由：诊断链路出问题时，九成情况是"看不懂那串十六进制"。先有尺子，再谈连接。

| 做了什么 | 说明 |
|---|---|
| 8 字节头 | 版本 / 版本反码 / 载荷类型（2B）/ 载荷长度（4B），**全部大端** |
| 16 种载荷类型 | 只实现本项目会用到的 7 种，其余认得名字、不解析 |
| 解析器 | 区分"半包（接着等）"和"格式错误（回 NACK 并丢弃）" |
| 通用负应答 0x0000 | 5 个码：格式不对 / 类型不认识 / 太长 / 内存 / 长度不符 |
| 工具 `doip-dump` | 粘一串十六进制 → 翻译成版本、类型、源/目标地址、UDS 服务名 |

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j4
cd build && ctest --output-on-failure        # 90 项断言

./build/doip-dump "02 FD 80 01 00 00 00 07 0E 00 00 01 22 F1 90"
```

输出：

```
头部
  版本       0x02（ISO 13400-2:2012）
  版本反码   0xFD（对得上）
  载荷类型   0x8001 Diagnostic message
  载荷长度   7 字节

载荷
  源地址       0x0E00
  目标地址     0x0001
  UDS 数据     22 F1 90（3 字节）
  服务         0x22 ReadDataByIdentifier（读 DID）
  读的 DID     0xF190
字节数正好对齐（15 = 8 头 + 7 载荷），没有多余字节。
```

## 报文长什么样

```
 0        1        2        3        4        5        6        7
┌────────┬────────┬────────┬────────┬────────┬────────┬────────┬────────┐
│ 版本   │ 版本   │  载荷类型（大端 2B）│      载荷长度（大端 4B）      │
│ 0x02   │ 反码   │  0x8001            │      0x00000007               │
│        │ 0xFD   │                    │                               │
└────────┴────────┴────────┴────────┴────────┴────────┴────────┴────────┘
                                                                  ↓
                                    载荷（7 字节）：0E 00 | 00 01 | 22 F1 90
                                                    源地址  目标地址  UDS
```

**反码那一字节是 DoIP 的魔数。** 它不是冗余 —— 在一串乱码里，`byte1 == ~byte0` 是最便宜的"这到底是不是 DoIP"判断。

**大端是什么意思**：0x0E00 这个逻辑地址，线上是 `0E 00`，不是 `00 0E`。高字节先走。
同一个网关里三套字节序观念并存：DoIP 大端、DBC Intel 小端、DBC Motorola 锯齿 `+15`。混一次查半天。

## 三个设计决定

**① 半包不是错误。**

```
NeedMoreData  → 数据不够，等。TCP 上这是常态
BadPattern    → 头读到了但不对，回 NACK 0x00 然后丢掉这 8 字节
```

混成一种的话，M3 做流式解析时一定出现"每隔一帧丢一帧"。

**② 头没凑齐时，不能回 NACK。**

你连版本字节都没读到，凭什么说人家格式不对？正确动作是等。

**③ 长度先检查，再分配。**

客户端只要写个 `0xFFFFFFFF`，不检查的话你先申请 4GB 再想"要不要处理"。所以 `parseMessage` 在拷贝载荷**之前**就拦住。

## 已知边界（M0）

- 载荷类型 0x4001-0x4004（实体状态 / 电源模式）只认得名字，不解析（本项目不做）。
- 不做 TLS。
- 不做 CAN FD。
- `parseMessage` 是单条解析；粘包靠调用方循环 `pos += consumed`（M0 的测试里已经验证过这个循环）。
