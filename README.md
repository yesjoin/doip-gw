# doip-gw

[![CI](https://github.com/yesjoin/doip-gw/actions/workflows/ci.yml/badge.svg)](https://github.com/yesjoin/doip-gw/actions/workflows/ci.yml)

DoIP 诊断网关：以太网侧收 DoIP，CAN 侧走 ISO-TP，中间做翻译。

**项目三**。前两个项目：`uds-ecu`（CAN 上的 ECU）、`dbc-toolkit`（DBC 词典与代码生成）。

```bash
git clone git@github.com:yesjoin/doip-gw.git && cd doip-gw
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j4
(cd build && ctest)          # 17 个套件、960 条断言
```

只依赖 cmake ≥ 3.16、C++17 编译器、Linux SocketCAN（`vcan0` 可用 `tools/vcanup.sh` 拉起来）。
GitHub Actions 跑 gcc / clang 两条腿（含 `-Werror` 与 `-O2`），真 CAN 与第三方客户端的步骤只在本地跑。

M16 把"谁能刷"变成一个可以被拒的问题：默认会话里 `0x34` 回 `0x7F`，编程会话但没解锁回 `0x33`，
两条路分开写死 —— 因为这两个码在排查现场指向完全不同的错。

M0 只做"字节 → 结构 → 字节"，不碰 socket。理由：诊断链路出问题时，
九成情况是"看不懂那串十六进制"。先有尺子，再谈连接。

M1 开始碰 socket，但**应答规则和收发包是分开的**：`respondTo()` 是纯函数，
`UdpDiscoveryServer` 只负责搬运。所以 30 条"谁该回、谁该沉默"的规则在内存里测完，
真 socket 只测"包发出去了、从对端口回来了"。

| M0 做了什么 | 说明 |
|---|---|
| 8 字节头 | 版本 / 版本反码 / 载荷类型（2B）/ 载荷长度（4B），**全部大端** |
| 16 种载荷类型 | 只实现本项目会用到的 7 种，其余认得名字、不解析 |
| 解析器 | 区分"半包（接着等）"和"格式错误（回 NACK 并丢弃）" |
| 通用负应答 0x0000 | 5 个码：格式不对 / 类型不认识 / 太长 / 内存 / 长度不符 |
| 工具 `doip-dump` | 粘一串十六进制 → 翻译成版本、类型、源/目标地址、UDS 服务名 |

## 报文长什么样

```
 0        1        2        3        4        5        6        7
┌────────┬────────┬────────┬────────┬────────┬────────┬────────┬────────┐
│ 版本   │ 版本   │  载荷类型（大端 2B）│      载荷长度（大端 4B）      │
│ 0x02   │ 反码   │  0x8001            │      0x00000007               │
│        │ 0xFD   │                    │                               │
└────────┴────────┴────────┴────────┴────────┴────────┴────────┴────────┘
                                                                  ↓
                                    载荷（7 字节）：0E 00 | 00 01 | 22 F1 90
                                                    源地址  目标地址  UDS
```

**反码那一字节是 DoIP 的魔数。** 它不是冗余 —— 在一串乱码里，`byte1 == ~byte0` 是最便宜的"这到底是不是 DoIP"判断。

**大端是什么意思**：0x0E00 这个逻辑地址，线上是 `0E 00`，不是 `00 0E`。高字节先走。
同一个网关里三套字节序观念并存：DoIP 大端、DBC Intel 小端、DBC Motorola 锯齿 `+15`。混一次查半天。

## 三个设计决定

**① 半包不是错误。**

```
NeedMoreData  → 数据不够，等。TCP 上这是常态
BadPattern    → 头读到了但不对，回 NACK 0x00 然后丢掉这 8 字节
```

混成一种的话，M3 做流式解析时一定出现"每隔一帧丢一帧"。

**② 头没凑齐时，不能回 NACK。**

你连版本字节都没读到，凭什么说人家格式不对？正确动作是等。

**③ 长度先检查，再分配。**

客户端只要写个 `0xFFFFFFFF`，不检查的话你先申请 4GB 再想"要不要处理"。所以 `parseMessage` 在拷贝载荷**之前**就拦住。

## M1：UDP 车辆发现

一句话：客户端广播"有人吗"，实体各自回"我是谁，VIN 是 XX"。

```
客户端                                实体（本工程）
   │  ── 0x0001 车辆识别请求（空载荷） ──►   │
   │  ◄── 0x0004 车辆识别应答（33 字节） ──  │
```

`0x0004` 的 33 字节长这样：

```
VIN(17) | 逻辑地址(2) | EID(6) | GID(6) | furtherAction(1) | 同步状态(1)
```

三种请求，三种应答规则：

| 请求 | 载荷 | 什么时候回 |
|---|---|---|
| `0x0001` | 空 | 无条件回 |
| `0x0002` | EID（6 字节） | 只有 EID 和我一致才回 |
| `0x0003` | VIN（17 字节） | 只有 VIN 和我完全一致才回（大小写敏感） |

不是发现请求的一切报文（`0x8001` 诊断、`0x0005` 路由激活、`0x0007` 心跳）**一律沉默**。
发现阶段还没建立任何上下文，贸然回应只会制造噪声。

```bash
# 一端当实体（10 秒），一端当客户端
./build/doip-discover --serve --port 13400 --seconds 10 &
./build/doip-discover --host 127.0.0.1 --port 13400 --wait-ms 800
```

### 两个 UDP 特有的坑

**① 收到坏报文不能回 NACK。**

M0 里那套 `0x0000` 负应答是给 TCP 用的。UDP 可能收到广播 ——
一个坏广播 + N 个实体各自回 NACK = 广播风暴。正确动作是**安静丢弃**。

**② 应答必须从同一个 socket 发出。**

客户端的 socket 绑在 13400 上等回复，你从别的端口回，它可能根本收不到。
所以收发共用一个 fd，`sendto` 的目标就是 `recvfrom` 给的 peer。

还有个更隐蔽的：**绑定必须用 `0.0.0.0`**。绑 `127.0.0.1` 只能收到回环包，
广播包（`255.255.255.255`）根本进不来 —— 这是"发现功能就是收不到"最经典的故障。

## M2：TCP 13400、路由激活、心跳

M1 是"还没连上，先找车"。M2 是**连上之后第一件事：证明你是谁**。

```
客户端（诊断仪）                          实体（本工程）
   │  ── TCP 连 13400 ─────────────────►  │
   │  ── 0x0005 路由激活（11 字节） ─────►  │  我是 0x0E00，想发诊断
   │  ◄── 0x0006 路由激活应答（13 字节）──  │  好，0x10 成功
   │  ── 0x8001 诊断报文 ───────────────►  │  这时才允许
   │  ── 0x0007 心跳 ───────────────────►  │
   │  ◄── 0x0008 心跳应答 ───────────────  │
```

`0x0005` 载荷 11 字节：`源地址(2) | 激活类型(1) | 保留(4) | OEM(4)`。
`0x0006` 载荷 13 字节：`tester 地址(2) | 实体地址(2) | 响应码(1) | 保留(4) | OEM(4)`。
连上 8 字节头，应答正好 21 字节 —— 这个数建议自己先手算一遍再看代码。

### 判据顺序（顺序本身就是规则）

1. 源地址合法吗？`0x0000` 是保留值、等于实体自己 —— 都是 `0x00`（方向搞反了）
2. 激活类型支持吗？只放行 `0x00` 默认 / `0x01` WWH-OBD，其余 `0x06`
3. 这个 socket 上已经激活过别人吗？是 → `0x02`（**不能中途换人**）
4. 同一个源地址重发 → 幂等，仍回 `0x10`

### 三条关键规则

**① 激活状态跟着连接走，清空只有一个入口。**

改 `activated_` 的地方只有 `RoutingActivation::reset()`，
而 `reset()` 只有一处调用：`dropConn()`。漏了这一句，TCP 断了但激活还在，
客户端重连后**直接就能发诊断** —— 看起来"很贴心"，实际是权限被继承，安全漏洞级别。

这条被测试钉死：断开 → 用**另一个**源地址重连 → 仍能激活成功，说明旧状态没留下。

**② TCP 上收到坏报文要回 NACK，然后断开；UDP 上安静丢弃。**

同一个"坏报文"，两层处理相反。因为 TCP 是有连接的，对面在等你说话；
而 UDP 可能收到广播，N 个实体各回一个 NACK 就是广播风暴。**传输层决定错误模型。**

**③ 心跳是两个时钟。**

```
静默超过 idleBeforeAliveCheck  → 发 0x0007，记下 aliveDeadline
aliveDeadline 到了还没收到 0x0008 → 断开
```
只做前半段 = 发了没人管；只做后半段 = 永远不触发。两个都要。

### 真踩到的坑：listen fd 必须非阻塞

`acceptPending()` 里是 `while (true) accept(...)` —— 阻塞模式下"没新连接了"
这一步会**永久卡在 `accept()`**。现象极具迷惑性：客户端能连上、服务器一声不响，
`/proc/<pid>/wchan` 写着 `inet_csk_accept`。修法是 listen fd 加 `O_NONBLOCK`，
让 `accept()` 没连接时返回 `EAGAIN` 跳出循环。

这类 bug 不出错、不报警，只是"不动了"。**排查手段：先看进程卡在哪（wchan），别猜。**

```bash
# 开一个实体，另开一个终端跑客户端
./build/doip-serve --port 13400 --seconds 10 --idle-ms 2000
./build/doip-client --host 127.0.0.1 --port 13400 --sa 0E00 --alive
```

```bash
cd build && ctest --output-on-failure        # 90 + 57 + 70 项
```

### M2 的阶段性取舍（写明，不糊过去）

- `0x8001` 在**已激活**连接上只记日志、不转发 —— 诊断业务是 M3 的事，M2 只守顺序。（M3 已补上）
- `0x8001` 在**未激活**连接上：M2 直接断开，**不去猜** 0x8003 的码值。
  规范没逐条核对过的地方宁可保守 + 写明理由，也不猜一个"看起来对"的数字。
  （M3 查清码表后改成"回 `0x8003 0x02` 再断开"，见下文 M3 章节）

## M3：诊断报文通道

M2 只守"先激活再诊断"的次序，收到 `0x8001` 就扔了。M3 把它变成一条完整的通路：

```
客户端 ── 0x8001（SA | TA | UDS）──► 本实体
                                     │ ① 这条连接激活了吗？SA 是它吗？
                                     │ ② 目标是我吗？
                                     │ ③ UDS 超长了吗？
                                     ▼
         ◄── 0x8002 正应答（收下了）──
         ◄── 0x8001 响应（UDS 应答）──   ← 下游给什么就送什么
```

`0x0001` 的载荷：`SA(2) | TA(2) | UDS(n)`（载荷可变长，所以 `0x0001` 的"长度"字段才有意义）。

### 三个设计决定

**① 先回应答，再算业务。**

`0x8002` 的含义是"报文收到且已受理"，不是"诊断做完了"。做完的结果另用一条 `0x8001` 送回去。
混成一条，客户端就分不清"没收到"和"收到了但超时"——这两种故障的处理方式完全不同。

**② 通道不碰 UDS 语义。**

`0x62` 正响应、`0x7F` 负响应是 ECU 的事，这一层只搬字节。
DoIP 层去解释 UDS，会让"到底哪一层出错"永远说不清。**分层的第一价值是可定位。**

**③ 下游是可替换的函数。**

```cpp
srv.diagnosticSink = stubEcuAnswer;   // M3：假 ECU
srv.diagnosticSink = iso-tp 通道;      // M4：换成真的，通道代码一个字不改
```

### 0x8003 码表（这次是查清了的，不是猜的）

| 码 | 含义 | 本工程什么时候用 |
|---|---|---|
| `0x02` | 源地址非法 | 没激活就发诊断；SA ≠ 本连接激活的地址 |
| `0x03` | 目标地址未知 | TA 不是我，也没有路由可达 |
| `0x04` | 诊断报文太大 | UDS 超过 `maxUds`（默认 512） |
| `0x05` | 内存不足 | 留位 |
| `0x06` | 目标不可达 | M4 桥接时用 |
| `0x07` | 网络未知 | 多网段网关才用 |
| `0x08` | 传输层错误 | 下游（ISO-TP）报错 |

`0x8002` 的 ack code 只有一个值：`0x00`。

**M2 → M3 的一处升级（不是推翻）：**

M2 里"未激活就发 `0x8001`"是直接断开，因为当时没有 0x8003 码表，干脆不猜。
M3 查清了码值，改成"先回 `0x8003 0x02`，再断开"。**同一件事两种做法，区别只在"有没有查清"。**

### 假 ECU 是故意的

`stubEcuAnswer()` 只答三件事，其余一律 `7F xx 31`：

```
3E 00        → 7E 00
22 F1 86     → 62 F1 86 01      （和项目一那个 ECU 同一个答案）
其它          → 7F <sid> 31
```

一棵"什么都答得上"的假 ECU 会掩盖真问题。**桩要故意留有不会的事。**

```bash
./build/doip-serve --port 13400 --seconds 10 --idle-ms 2000
./build/doip-client --host 127.0.0.1 --port 13400 --sa 0E00 --diag "22 F1 86"
```

```
← 0x0006 应答：tester=0x0E00 entity=0x0001 code=0x10 (0x10 路由激活成功)
→ 0x8001 诊断：SA=0x0E00 TA=0x0001 UDS=22 F1 86（ReadDataByIdentifier，3 字节）
← 0x8002 ACK：SA=0x0001 TA=0x0E00 code=0x00
← 0x8001 响应：SA=0x0001 TA=0x0E00 UDS=62 F1 86 01（正响应（对应 0x22））
```

三种故障自己造出来看：

```bash
./build/doip-client --sa 0E00 --dsa 0E01 --diag "22 F1 86"    # 0x8003 0x02 冒用地址
./build/doip-client --sa 0E00 --ta 0002  --diag "3E 00"       # 0x8003 0x03 目标不认识
./build/doip-client --sa 0E00 --diag "22 F1 90 00 11 22 ... (600 字节)"   # 0x8003 0x04 太大
```

### 一个容易漏的坑：一次 recv 可能收到两条报文

服务器会把 `0x8002` 和 `0x8001` 响应连着发。客户端如果"读一次就解析第一条、把剩下的丢掉"，
就会出现**偶发收不到响应**——本机测十次也许只错一次。

自测里的 `Client` 结构专门维护了跨 recv 的缓冲区（`buf`），工具 `doip-client` 也用了同样的写法。
**TCP 上"一次 recv = 一条报文"是错的假设，这在 M0 就写下了，M3 第一次真正撞上它。**

## M4：以太网 ↔ CAN 的桥

M3 的下游是个假 ECU。M4 把它换成 **项目一的真 ECU**（一个独立进程，在 vcan0 上）：

```
doip-client ── TCP 13400 ──► doip-gateway ── vcan0 / ISO-TP ──► uds-demo --ecu
   (0x8001)                    (7E0 请求)                          (7E8 响应)
```

**为什么不用项目一的库里那句"抽个 uds-core"？**

原来的计划里有个 M3.5：把项目一的 UDS 核心抽出来给网关复用。真做的时候发现方向不对：
**网关不需要内嵌 UDS，它只需要 ISO-TP 的"另一方"。** ECU 本来就是总线上一个独立进程
（项目一），网关只要当 tester 把字节转发过去就行。抽 `uds-core` 反而把"网关"变成了"第二个 ECU"，
而真实车上的网关从来不解释 UDS —— 它只转发。

所以 M3.5 取消，M4 直接对接真 ECU 进程。**这是设计上的修正，不是偷懒。**

### 两侧的方向不一样，代码不能照抄

项目一的 `IsoTp` 是 **ECU 侧**：被动收帧，等上层问"要不要回流控"。
网关这侧是 **tester 侧**：主动拆帧、发首帧、**停下来等对方的流控**、按 BS/STmin 发连续帧。
方向反过来，状态机就不同。这一份 `IsoTpStack` 只管拆/装，`IsoTpClient` 管"等"。

### 40 字节到底怎么走

```
UDS 40 字节
  → 首帧（FF）：长度 0x028 + 前 6 字节
  → 5 张连续帧（CF）：SN=1..5，每张 7 字节
  → 中间收到 FC（0x30 08 0A）：BS=8 表示发满 8 张再等，STmin=10ms 表示帧间至少 10ms
```

47 字节就变成 6 张连续帧。手算方式：`(总长 - 6 + 6) / 7` 向上取整。

响应方向反过来：ECU 发 FF → **网关必须回流控帧** → 否则 ECU 会一直停在那里不敢继续发。
20 字节的 VIN 就是这么回来的。

### 真踩到的坑：DLC 不一定是 8

第一次跑通了 `22 F1 90`，但 `3E 00` 永远超时。抓 `candump` 才看见：

```
vcan0 7E0#023E000000000000     ← 我们的请求，8 字节
vcan0 7E8#027E00               ← ECU 的响应，只有 3 字节（不补零）
```

接收代码里写着 `if (can_dlc < 8) continue;`，把所有短响应当噪声扔了。
**为什么 22 F1 90 没暴露问题？** 因为它的响应是 20 字节、走多帧，帧恰好都是 8 字节。

教训有两条：

- ISO 15765-2 允许单帧只发实际长度，**补零是可选的**；
- "某个功能能用"不等于"这条路径对"，要多试一个形态不同的用例（短请求 vs 多帧响应）。

修法是：接收时按 `dlc` 拷贝、其余补零，并把 `dlc` 一路传给重组器，让它按真实字节数截断。

### 并发：一把锁换"不串包"

CAN 是**共享介质**。两个 tester 同时发诊断，如果各开一条通道各等各的响应，
双方都会看到对方 ECU 的帧 —— 然后各自把"别人的答案"当自己的。

所以 `DiagnosticGateway` 里就一句 `std::lock_guard`，把请求串行化。
排队只有几毫秒（实测 `最长排队 0 ms`），换来"永不串包"。这就是验收第 4 条。

```bash
# 终端 1：项目一的 ECU
~/uds-ecu/build/uds-demo --ecu --iface vcan0 --wait-s 60
# 终端 2：网关
./build/doip-gateway --iface vcan0 --port 13400 --seconds 30
# 终端 3：诊断仪
./build/doip-client --port 13400 --sa 0E00 --diag "22 F1 90"
```

输出：

```
← 0x8002 ACK：SA=0x0001 TA=0x0E00 code=0x00
← 0x8001 响应：SA=0x0001 TA=0x0E00 UDS=62 F1 90 4C 53 56 41 41 30 30 30 30 41 31 32 33 34 35 36 37
```

那 17 个字节译成字符就是 `LSVAA0000A1234567` —— 和项目一里 ECU 的 VIN 一致。
**验收第 2 条"同一 DID 经 DoIP 与 CAN 直读值一致"，证据就是这两处字符串一模一样。**

### 验收硬指标对照（M4 之后）

| 验收项 | 现在的状态 |
|---|---|
| ① 能连上/激活/读到 `22 F1 90` | ✅ `doip-client` + 真 ECU |
| ② DoIP 与 CAN 直读值一致 | ✅ 都是 `62 F1 90 4C 53 56 ...` |
| ③ 40 字节请求穿过网关、CAN 侧自动多帧 | ✅ 47 字节实测走 FF + 6 CF |
| ④ 两客户端并发不串包 | ✅ 交替 4 轮，TA 归属全对 |
| ⑤ 断开后激活清空、重连须重新激活 | ✅ M2 的自测钉死 |

## M5：让"别人家的客户端"来验收

前面所有测试都是**自己写的东西测自己写的东西**。客户端和服务器出自同一套理解，
哪怕双方都理解错了，也照样能"通"。M5 换人：用 Python 的 `doipclient`（别人按同一份
标准独立实现的库）来连我们，能通才说明**我们符合标准**，而不是自说自话。

```bash
pip3 install --user doipclient        # 第三方客户端
bash tools/m5_e2e.sh 13458            # 6 步跑完 5 条硬指标
```

`m5_e2e.sh` 会自动起项目一的 ECU 和网关，然后依次做：

```
1/6 第三方客户端做 UDP 车辆发现
2/6 第三方客户端 22 F1 90 → 读 VIN
3/6 CAN 直读同一个 DID → 和 DoIP 侧逐字节对比
4/6 47 字节请求穿过网关（CAN 侧自动 FF + 6 CF）
5/6 新连接不激活直接发诊断 → 必须被 0x8003 0x02 拒掉
6/6 两个第三方客户端并发 → 不许串包
```

结果：**通过 6 项，失败 0 项**。网关自己的账：

```
发现：收到 1 条 UDP，回了 1 条
接入 6，激活 4，诊断请求 7（ACK 6 / NACK 1）
转发 6 条，失败 0 条，最长排队 0 ms
ISO-TP：发帧 15，收帧 16，流控 收 1 / 发 3，超时 0，序号错 0，迟到帧丢弃 3
```

### 第三方客户端暴露的三个问题（这才是 M5 的全部价值）

**① 它发的路由激活请求只有 7 字节，我们只认 11 字节。**

一上来就被拒：`0x0000 NACK 0x04（载荷长度不对）`。原因是 ISO 13400-2 改过版：
早期 7 字节（SA + 类型 + 保留 4），2019 版加了 OEM 4 字节变 11 字节。`doipclient` 发的是 7 字节那种。

修法有讲究：**接收侧两种都收，发送侧只发 11 字节**。
"严于律己、宽以待人"（Postel 定律）——但只对**格式变体**宽容，
SA 合法性、激活类型这些**语义判断照旧严格**。现在 `codec-selftest` 里有 4 条断言钉这件事。

**② 总线上的"迟到帧"把多帧请求弄挂了，而 M4 完全看不到这个问题。**

现象：单跑 47 字节请求是好的，但在 `m5_e2e.sh` 的序列里（前面刚用项目一的 tester
跑过一次 `22 F1 90`）就 100% 失败。

根因：tester 读 VIN 时 ECU 回了 `FF + 2 个 CF`，这些帧**我们的 socket 也收到了**
（CAN 是广播的），只是没人读，就堆在缓冲区里。下一次我们发完首帧去等流控，
读出来的第一帧是那堆旧 CF，于是报"首帧之后收到的不是流控帧"，整条请求作废。

修法是三件事：
- `request()` 发之前先**清仓**（`drainStale()`，0 超时读空缓冲区）；
- 等流控时撞到非 FC 帧**跳过**，用 p2 的总预算兜住，不会无限等；
- 收响应时，没有 FF 在途却收到 CF → 当迟到帧丢掉。

账上看得见：`迟到帧丢弃 3`。M4 的时候这个数永远是 0，因为总线上只有我们自己。

**③ `doipclient` 的 `send_diagnostic` 不返回响应。**

它只处理 `0x8002`（ACK）/`0x8003`（NACK），真正的诊断响应要用 `receive_diagnostic()` 拿。
这不是库的缺陷——标准里 ACK 和响应本来就是**两条报文**，只是我们自己的 `doip-client`
把两步揉成一步了。这也解释了当年 M3 为什么要给 `recvMsgBuf` 加跨 recv 缓冲：
服务器会把 ACK 和响应连着发。

### 顺手补的一件事：网关也要能"被扫到"

M4 的网关只有 TCP。真实 DoIP 实体是 UDP 发现 + TCP 激活**同一个端口号**，
所以 M5 给 `doip-gateway` 加了 UDP 车辆发现（同端口，协议不同不冲突）。
不加这一步，第三方客户端根本看不见网关，只能手工填 IP——验收第一句"能连上"就无从谈起。
另外网关声明的 VIN 设成和 ECU 的 VIN 一致（`LSVAA0000A1234567`）：同一辆车报两个 VIN 是硬伤。

### 五条硬指标，证据在这

| 验收项 | 证据 |
|---|---|
| ① 第三方客户端能连上/激活/读到 VIN | `doipclient` 1.3.0 读到 `LSVAA0000A1234567` |
| ② 同一 DID 经 DoIP 与 CAN 直读一致 | 两侧都是 `62 F1 90 4C 53 56 41 41 30 30 30 30 41 31 32 33 34 35 36 37` |
| ③ 40+ 字节请求跨层不截断 | 47 字节 → FF + 6 CF → ECU 回 `7F 2E 7F` |
| ④ 两客户端并发不串包 | 各 2/2 条响应，A 全是 `62 F1 90...`，B 全是 `7E 00` |
| ⑤ 断开后必须重新激活 | 新连接不激活直接发诊断 → `0x8003 0x02` + 断开 |

## M6：从"一台 ECU"到"一张路由表"

M4 的网关其实只认识**一台** ECU：`7E0` / `7E8` 是 `#define` 级别的常量，谁连上来都往这两个 ID 上打。
真实网关后面挂着一串 ECU（发动机、网关自己、车身、电池……），诊断仪只给一个东西：**目标地址 TA**。
网关要做的事，一句话概括——

> 收到 `(SA, TA, UDS)`，按 TA 查表得到 `(请求 ID, 响应 ID)`，然后照 M4 的老路把字节搬过去。

这句话里藏着 M6 的全部设计压力：**路由错了不会报错**。你把 TA=0x0003 的请求打到 `7E0` 上，
项目一的 ECU 照样会认真答一个 `62 F1 90` 回来——只是那是**另一台车/另一个零件**的值。
不崩、不超时、只悄悄答错，这是最难查的一类故障。所以 M6 的思路是**在加表的时候就拒绝**，而不是运行期补救。

### 路由表长什么样（`include/RouteTable.h`）

```cpp
struct RouteEntry {
    std::uint16_t logicalAddress;   // 诊断仪给的目标地址 TA
    std::uint32_t txId;             // 网关往总线上发请求用的 ID
    std::uint32_t rxId;             // 网关从总线上收响应用的 ID
    std::string   name;             // 记账、日志用（ECU_A / ECU_B）
};
```

`RouteTable` 只有 `add / lookup / known / size / entries / clear`。`add()` 做四道校验，
**任何一道不过就整条拒绝**，并用 `err` 说明原因：

| 校验 | 拒绝理由 |
|---|---|
| `logicalAddress != 0` | 0x0000 是保留地址，真表里出现说明配置写错了 |
| `txId != 0 && rxId != 0` | ID 为 0 在 CAN 上是无效的（11 位最小合法是 0x001，29 位同理） |
| `txId != rxId` | 收发同 ID 意味着自己发的帧自己收，ISO-TP 会立刻把请求当响应 |
| 地址不重复 + ID 对不重复 | 两个 TA 落到同一对 ID，等于两条路由抢一个通道，串包必现 |

最后一条是重点：**允许"多 TA 共用一个通道"是错的**（真实网关里也不这么做，因为无法区分响应属于谁）。
宁可启动失败并指出"TA=0x0003 与 TA=0x0002 撞在 7E0/7E8 上了"，也不要在现场调三天。

### 判据改了一个字，语义全变（`DiagnosticPolicy`）

M3 的 0x8001 校验第 ④ 条是"目标地址是不是我"：`TA == entityAddress`，否则 `0x8003 0x03`。
M6 把它换成一个可注入的谓词：

```cpp
std::function<bool(std::uint16_t)> targetKnown;   // 为空 → 退回 M3 老语义
```

```cpp
const bool reachable = policy.targetKnown ? policy.targetKnown(o.targetAddress)
                                          : (o.targetAddress == entityAddress);
```

为什么用谓词而不是把 `RouteTable` 塞进策略里：策略是纯逻辑（不碰 socket、不碰 CAN），
`RouteTable` 是配置数据。用一个 `bool(uint16_t)` 隔开，测试里可以塞个 lambda 假装"我知道 2 和 3"，
不用为了测判据去建真通道。同时**留了退路**：`targetKnown` 为空时行为与 M3 逐字一致，M2/M3 的 73 项断言一条没动。

注意语义上的一个变化：M6 之后网关**不再区分"这个地址是我自己"和"这个地址是我背后的 ECU"**。
因为对诊断仪来说两者没区别——都是我该答。所以实体自己的地址也必须**显式出现在表里**才受理。

判据顺序一点没动：未激活 `0x02` → 载荷不足 4 字节（回 `0x0000 0x04` 并断开）→ 源地址不符 `0x02` →
目标不可达 `0x03` → UDS 超长 `0x04`。路由判断插在原第 ④ 位，所以"没激活"永远先于"地址不认识"。

### 网关从"一条通道"变成"一张通道表"（`DiagnosticGateway`）

```cpp
DiagnosticGateway(std::string iface, const RouteTable& table, Timing tim);
```

- `start()` 按表**逐条**建 `IsoTpClient`，存进 `std::map<uint16_t, std::unique_ptr<Channel>>`；
  任一条开不起来（接口不存在、ID 被占用）**整体启动失败**，并指名"哪条、TA 多少、什么原因"。
  半个网关比没有网关更危险：它会让一部分 ECU 通、另一部分"随机不通"。
- `operator()` 先 `lookup(TA)`；查不到就 `++unknownTargets_` 然后 `return false`——
  **绝不猜一台 ECU 顶上**。这一条在验收里被钉死（TA=0x0004 → `0x8003 0x03`）。
- 仍然用**一把 `std::mutex`** 串行化全部通道：总线是共享的，两条通道同时发 FF 会把彼此的流控搅乱。
  实测 9 条转发、最长排队 **0 ms**，说明在单机规模下串行不是瓶颈。
- 记账分两层：网关级 `handled/failed/unknownTargets/maxWaitMs`，通道级 `ChannelStats{ta,txId,rxId,open,handled,failed,stats}`。
  `stats` 直接复用 M5 的 `IsoTpClient::Stats`（超时、序号错、迟到帧丢弃），所以这些老指标**按 ECU 分别可见**了。

### 命令行：`--route` 可重复

```bash
./build/doip-gateway --iface vcan0 --port 13461 --seconds 36 \
    --route 0002:7E0:7E8:ECU_A \
    --route 0003:7A0:7A8:ECU_B
```

格式 `TA:TX:RX[:名字]`，全十六进制，`parseRoute()` 逐段 `strtoul(..., 16)` 校验。
**默认值 `0001:7E0:7E8:ECU_A`**，所以 M5 那条命令一字不改照样能跑——加功能不破坏老用法，
是能拿来当"回归测试"的前提。启动时打印整张表，收工时逐条路由一行账。

### M6 为什么必须自己写一台 ECU（`tools/stub_ecu.cpp`）

项目一的 `uds-demo` 的 CAN ID 是**源码常量**（`tools/uds_demo.cpp` 第 37–38 行写死 `0x7E0` / `0x7E8`），
VIN 也硬编码在 `src/Uds.cpp` 的 DID 表里。要验"两个 TA 读到**不同**的 VIN"，就必须有第二台能换 ID、
能换 VIN 的 ECU。于是有了 `stub-ecu`：

```bash
./build/stub-ecu --iface vcan0 --rx 7A0 --tx 7A8 \
    --vin LSVZZ0000B7654321 --hw HW02 --seconds 40
```

它是**真的 SocketCAN 节点**（不是 mock）：用 `IsoTpAssembler` 收请求（按 DLC 处理，因为对端可能不补零）、
FF 一到就回 `buildFlowControl(0, 10, 0)`、用 `segmentMessage` 发响应（多帧先 FF、等 tester 流控、再按 STmin 发 CF）。
答 `3E 00 → 7E 00`、`22 F1 86 → 62 F1 86 02`、`22 F1 90 → 62 F1 90 + 17 字节 VIN`、
`22 F1 91 → 62 F1 91 + HW`，其余 `7F <sid> 31`。

一句话说清它和网关的关系：**拆帧/组帧用的是同一份 `IsoTpStack`，两侧的差别只在"谁等谁"**。
网关等 ECU 的流控，ECU 等 tester 的流控；同一套状态机，方向一翻就是另一个角色。
这也是"共用代码"的价值——真要错了，两边错得一样，反而说明我理解的是同一套协议。

### 真踩到的坑：`0x8002` / `0x8003` 的源地址不能写死

第一次用第三方 `doipclient` 打两台 ECU，两个 TA 全都 `TimeoutError: ECU failed to respond in time`。
可网关日志明明写着"回了 `0x8002` ACK / 下游答了 20 字节 / 用 `0x8001` 送回"。
换成我们自己的 `doip-client --ta 0002` 又能读到 VIN，日志里 ACK 的 `SA=0x0001`。

根因：**`0x8002`（诊断 ACK）和 `0x8003`（NACK）的源地址原先写死 `cfg.entityAddress`（0x0001）**。
M5 时实体地址和 ECU 地址碰巧都是 `0x0001`，所以看不出问题；M6 一分开，`doipclient` 按
"我发出去的目标地址就是应答该来的地方"去校验源地址，把 ACK 当成噪声丢掉 → 客户端只会超时。

修法：**应答源 = 请求里的 TA（`o.targetAddress`），应答目标 = 请求的 SA**。共四处：
策略类 `0x8003`、`0x8002` ACK、下游失败时的 `0x8003 0x08`、`0x8001` 响应。
改完两台 ECU 都通、并发也通。这条恰好是"M6 存在的意义"的实证：
**地址一多，"谁是源、谁是目标"就不能靠巧合成立了。**

顺手清掉两个卫生问题：`doip_gateway.cpp` 注释行尾的 `\`（`-Wcomment`，CI 开 `-Werror` 会红）、
`RouteTable.cpp` 里 `std::to_string(0x0002)` 打成十进制（改成 `snprintf("0x%04X")`）。

### 一条命令跑完（`tools/m6_e2e.sh`）

```bash
bash tools/m6_e2e.sh 13461       # 七步，双 ECU，端到端
```

脚本自己起三个进程：项目一的 ECU（`7E0/7E8`，VIN `LSVAA0000A1234567`）、
`stub-ecu`（`7A0/7A8`，VIN `LSVZZ0000B7654321`，HW `HW02`）、网关（两条 `--route`）。

| 步骤 | 验什么 | 结果 |
|---|---|---|
| 1 | 启动就打印路由表（两行都在） | ✅ |
| 2 | `TA=0x0002` 读 `22 F1 90` | ✅ `LSVAA0000A1234567` |
| 3 | `TA=0x0003` 读同一个 DID | ✅ `LSVZZ0000B7654321`（**值不同**才证明路由真的生效） |
| 4 | `TA=0x0003` 读 `22 F1 91` | ✅ `62 F1 91 48 57 30 32`（HW02） |
| 5 | `TA=0x0004`（表里没有） | ✅ `0x8003 0x03`，`SA=0x0004 TA=0x0E00` 反向填 |
| 6 | 两客户端并发，A 打 TA=2 读 VIN、B 打 TA=3 读 HW | ✅ 各 3/3 条，前缀全对，没串包 |
| 7 | 网关汇总账 | ✅ 转发 **9** 条、失败 0、未知地址 0、最长排队 0 ms |

第 7 步的账本身也是证据：`TA=0x0002（7E0/7E8）：转发 4 条`、`TA=0x0003（7A0/7A8）：转发 5 条`
—— 4 + 5 = 9，**每条诊断都落在了自己该落的那条通道上**，没有一条走错。

第 5 步为什么用**裸 socket**：`doipclient` 一构造就自动做路由激活，没法"故意发到一个不存在的地址
然后只读那条 NACK"。所以 `m5_check.py` 里的 `noact` / `unknown` 两个子命令是自己拼包、自己收包。
顺便：NACK 的 `SA=0x0004`、`TA=0x0E00` 是**照请求反向填**的——这一点在第 3 章（M3）就定过规矩：
应答的源地址永远是"请求的目标"，M6 只是让它第一次在真实多地址场景里生效。

## M7：CAN ID 有宽度（11 位 / 29 位）

M6 的路由表里存的是"一个数"，但这个数其实有两种宽度。11 位最大只到 `0x7FF`，
再往上（`0x800`–`0x1FFFFFFF`）只能用 29 位扩展帧发。**M7 做的事就是让同一张表里两种宽度并存。**

### 为什么这条不能"顺手加一下"

SocketCAN 有一条**反直觉**的规矩：同一块内存里的 `can_id` 字段，发和收的语义相反。

- **发**：29 位 ID 必须手动把 `CAN_EFF_FLAG`（`0x80000000`）置上，否则内核按 11 位截断，帧发出去是错的 ID。
- **收**：内核把这个标志位置好了给你，你必须自己**剥掉**才能比对；直接拿 `can_id` 和路由表里的 `0x18DA00F1` 比，永远不相等。

两条规矩方向相反。只做对一半的现象特别气人：**网关启动正常、路由表打印正常，然后每一条请求都超时，
`candump` 一条帧都没有**——因为发的时候没置位，内核根本没把这帧当 29 位发出去。
所以 M7 的第一步不是写代码，是承认"ID 有宽度"这件事必须**收敛到一个地方**。

### 一个新文件 `include/CanId.h`

```cpp
namespace doip {
inline constexpr std::uint32_t kCanIdMax   = 0x1FFFFFFFu;  // 29 位全 1
inline constexpr std::uint32_t kCanEffFlag = 0x80000000u;  // SocketCAN 的"这是扩展帧"标志
inline constexpr std::uint32_t kStdIdMax   = 0x7FFu;       // 11 位全 1

bool        isExtendedId(std::uint32_t id);   // > 0x7FF
bool        isValidCanId(std::uint32_t id);   // 0 < id <= kCanIdMax
std::uint32_t idForSend(std::uint32_t id);    // 29 位 → 置 kCanEffFlag
std::uint32_t idFromRecv(std::uint32_t id);   // 剥掉 kCanEffFlag（连 RTR/ERR 高位一起剥）
std::string  formatCanId(std::uint32_t id);   // 11 位打 0x%03X，29 位打 0x%08X
}
```

为什么单独开文件，而不是塞进 `RouteTable.h`：**"宽度"不是路由表的知识，是 CAN 的知识。**
`IsoTpClient`、`stub-ecu`、`doip-gateway` 三处都要用同一套判断，抄三遍迟早有一处忘了剥位。
放进 `doip-route` 库（`CMakeLists.txt` 里给它加 `src/CanId.cpp`），是因为 `formatCanId` 要打日志、
需要 `<string>`，但整个文件**不碰 socket**，所以单测不用起 vcan0 也能跑。
路由表本身仍然只存"32 位原值"，**什么时候置位是发帧那一刻的事**——表是配置，帧才是动作。

### 路由表多一道校验，错误信息点名上限

`RouteTable::add()` 现在四道校验变成五道，第 ③ 道是 `isValidCanId(txId) && isValidCanId(rxId)`：

```
路由地址与 CAN ID 对重复：TA=0x0006 → 0x18DA00F1 / 0x18DAF100（29 位）
CAN ID 0x20000000 超出 29 位上限（29 位最大是 0x1FFFFFFF）
```

错误信息从"这数不对"变成"这数为什么不对、上限在哪"，出问题时不用回头翻代码。
顺便，原来 `0x7A0` 是打十进制的（`RouteTable.cpp` 里 `std::to_string` 的老问题），现在统一走 `formatCanId`。

### 发帧置位、收帧剥位（`src/IsoTpClient.cpp`）

```cpp
// open() 里先拦一次：ID 非法就别等内核回 EINVAL
if (!isValidCanId(cfg_.txId) || !isValidCanId(cfg_.rxId)) return false;

// sendFrame
f.can_id = idForSend(cfg_.txId);          // 29 位自动带上 CAN_EFF_FLAG
// 失败信息里注明"扩展帧/标准帧"，省得以后又猜

// recvFrame
if (idFromRecv(f.can_id) != cfg_.rxId) continue;   // 原来是 f.can_id & CAN_EFF_MASK
```

`CAN_EFF_MASK` 是 `0x1FFFFFFF`，用它也能剥，但**只剥了 ID 那 29 位，RTR / ERR 两个标志位还留着**。
换成 `& kCanIdMax` 是把 32 位里所有高位一起清掉——收帧比对要的是"纯 ID"，不是"ID 加一堆标志"。

### `stub-ecu` 同步改造

假 ECU 是 M6 为了"第二台 ECU"自己写的，它也必须能挂 29 位 ID，否则 M7 没有对照物：
`sendFrame` 用 `idForSend`、两处收帧比较改 `idFromRecv`、启动横幅改成 `formatCanId`。
现在 `--rx 18DA00F1 --tx 18DAF100` 直接就能用，和项目一的 `uds-demo`（`7E0/7E8`）挂在**同一条 vcan0 上**。

### 日志的宽度要能一眼看出来

`DoIpGateway` 和 `doip-gateway` 里原来用 `%03X`，29 位 ID 会被打成 17 位十六进制（`18DA00F1` → 一长串），
既不像 ID 也没法抄进脚本。现在统一 `%s` + `formatCanId`：11 位是 `0x7E0`（3 位）、29 位是 `0x18DA00F1`（8 位），
**看位数就知道是哪种帧**。`DoIpGateway.cpp` 里为此加了个小函数 `hexTa()`，启动失败信息改成字符串拼接。

### 自测从 32 项涨到 57 项（`tests/route_selftest.cpp`）

新增 C 段 25 项，都冲着边界去：

| 组 | 项 | 验什么 |
|---|---|---|
| 宽度判定 | `0x7FF` / `0x800` | 边界两侧各判一次，差一位就换帧类型 |
| 合法性 | `0` / `0x1FFFFFFF` / `0x20000000` | 0 非法；29 位全 1 合法；再多一位必须拒 |
| 置位/剥位 | `idForSend` / `idFromRecv` 正反跑 | 置完再剥必须回到原值，11 位要原样不动 |
| 格式化 | 两种宽度 | 3 位 / 8 位，且都带 `0x` |
| 入表 | 超 29 位 | `add()` 拒绝，且错误信息里含"29" |
| 混表 | 11 位 + 29 位并存 | 同一张表两条路由互不干扰 |

`ctest` 六套件全绿，累计 **421 项**（94 / 57 / 70 / 73 / 70 / **57**）。

### 一条命令跑完（`tools/m7_e2e.sh`）

```bash

```

三个进程同时在跑：项目一 `uds-demo`（标准帧 `7E0/7E8`，`TA=0x0002`，VIN `LSVAA0000A1234567`）、
`stub-ecu --rx 18DA00F1 --tx 18DAF100`（扩展帧，`TA=0x0006`，VIN `LSVZZ0000B7654321`，HW `HW02`）、
网关（两条 `--route`）+ `candump -L` 录总线。

| 步骤 | 验什么 | 结果 |
|---|---|---|
| 1 | 路由表打印的宽度对不对 | ✅ `TA=0x0002 → 0x7E0 / 0x7E8`（3 位）、`TA=0x0006 → 0x18DA00F1 / 0x18DAF100`（8 位） |
| 2 | 标准帧通道读 VIN | ✅ `LSVAA0000A1234567` |
| 3 | 扩展帧通道读同一个 DID | ✅ `LSVZZ0000B7654321`（值不同，证明真打到了另一台） |
| 4 | 扩展帧上 `22 F1 91` | ✅ `62 F1 91 48 57 30 32` |
| 5 | 总线侧取证（`candump`） | ✅ `18DA00F1#...` 与 `7E8#...` 同时出现（8 位 = 扩展帧，`CAN_EFF_FLAG` 置对了） |
| 6 | 两条通道分开记账 | ✅ 见下 |

第 5 步是这次唯一"能推翻结论"的证据：以太网侧读到正确的 VIN，**也可能只是网关自己编的**。
只有在总线上同时抓到 8 位的 `18DAF100` 和 3 位的 `7E8`，才能说"两种宽度真的都发出去了"。

第 6 步的账可以手算对得上：

```
TA=0x0002（0x7E0/0x7E8）：转发 1 条，发帧 2，收帧 3
TA=0x0006（0x18DA00F1/0x18DAF100）：转发 2 条，发帧 3，收帧 4
转发 3 条，失败 0 条
```

读 VIN 是**多帧**：1 个首帧（FF）+ 2 个连续帧（CF）= 3 发，ECU 回 FF + CF + CF = 3 收，再加 1 个流控帧就是 3 发 4 收；
读硬件版本是**单帧**：1 发 1 收。所以扩展帧那条是 3 发 4 收，标准帧那条是 1 次 VIN = 2 发 3 收。**加起来正好是打印的数。**

### M7 里踩的两个小坑

1. `src/IsoTpClient.cpp` 加完 `idForSend` 忘了 `#include "CanId.h"` → 六个 `was not declared in this scope`。
   头文件分开的代价就是这个，编译器在提醒你"你用了别人的知识，得先声明"。
2. `m7_e2e.sh` 第一版写了半截死代码（有个 `m7_vin_a.log` 从来没被生成、`echo` 字符串跨行引号错位），
   整份重写。**验收脚本自己也要验收**——它绿了不代表它对，得看它到底断言了什么。

还有一个"改完才发现"的连带影响：`m6_e2e.sh` 里断言的是老格式 `TA=0x0002 → 7E0 / 7E8`，
日志改成 `0x7E0` 之后那两项就红了。这不是 bug，是**格式统一后必须同步的断言**——CI 第 10 步替我们抓住了它。

## M8：功能寻址（一条请求，几台 ECU 一起答）

M7 结束时，网关能问"那一台"（物理地址，一对 CAN ID）。M8 补的是另一种语气：**"你们这一类，全都听着"**。

两种寻址不是"少一个参数"，而是两条完全不同的路径：

| | 物理寻址 | 功能寻址 |
|---|---|---|
| TA | 0x0001–0x0DFF 里的某台 ECU | 0xE400（厂商自定义功能组） |
| CAN 侧发什么 | 那台的请求 ID（如 `0x7E0`） | **一个广播 ID**（`0x7DF`），所有 ECU 都在听 |
| 应答条数 | 恒为 1 | **由"谁在听"决定**，可能 0、可能 3 |
| 应答怎么归属 | 只有一条通道，不用归属 | 每条应答要带自己的 SA（谁答的） |

### 地址段为什么不能随手挑

ISO 13400 把 0xE000–0xE3FF 留给 **ISO/SAE 保留的功能组**（0xE000 已经被 WWH-OBD 占掉），
0xE400–0xEFFF 才是**厂商自定义**的功能组——所以 `0xE400` 是业界最常用的那个。本项目按这条划：

```cpp
inline bool isFunctionalAddressRange (std::uint16_t a) { return a >= 0xE000 && a <= 0xEFFF; }
inline bool isVendorFunctionalAddress (std::uint16_t a) { return a >= 0xE400 && a <= 0xEFFF; }
```

`RouteTable::addFunctional()` 因此多两条规矩：地址必须落在 0xE400–0xEFFF（落进保留区就报"厂商自定义应从 0xE400 起"），
广播 ID 必须合法且**不能和任何物理通道的收发 ID 撞**。反过来，`add()` 也拒绝两件事：
拿功能地址当物理目标、拿广播 ID 当某台 ECU 的收发 ID。这四条互相咬住，配错一条就启动失败。

### 功能路由长什么样（`FunctionalRoute`）

```cpp
struct FunctionalRoute
{
    std::uint16_t logicalAddress;   // 0xE400
    std::uint32_t txId;             // 0x7DF
    std::string   name;
};
```

**故意没有 `rxId`**：广播的应答不算"某一条通道的响应 ID"，而是"所有已知通道各自用自己的响应 ID 回话"。
把 `rxId` 写进来反而会误导人以为"广播也有个固定的回话地址"。

命令行：`--func 0xE400:0x7DF:ALL`，可重复；和 `--route` 各管一张表。

### 网关的一次广播，是四步

`DiagnosticGateway::broadcast()`：

1. **查功能表**：TA 不在功能段 → `0x8003 0x03`（地址问题，不是传输问题）。
2. **先给每条通道清仓**：上一条请求留下的多帧尾巴如果还在 socket 缓冲区里，会被当成本次应答——
   现象是"只问了 `3E 00`，却收到一条 20 字节的 VIN"。
3. **广播只发一次**：借第一条通道的 socket 发（发帧不看 bind 的 rx 过滤），并记 `funcRequests`。
   每台 ECU 各发一遍是错的：ECU 会答 N 遍，账也乱了。
4. **挨条通道收**：每通道 `funcWindowMs`（默认 150ms）。谁答了就记一条 `DiagnosticReply{SA=该通道 TA, UDS}`；
   一条都没有 → `0x8003 0x06`（**目标存在但不可达**，和 0x03"地址不认识"是不同的错因）。

### 单帧这件事，是协议限制不是偷懒

经典 CAN 的 ISO-TP 单帧只能装 7 字节（`8 - 1` 的 PCI）。功能寻址下：

- **请求**也必须是单帧：网关没法给"所有 ECU"发流控帧——流控总得有个唯一收件人。
  超过 7 字节，网关在发之前就拒：`0x8003 0x04`（报文太大）。
- **响应**也必须是单帧，同理：ECU 发首帧之后等不到一个唯一的流控方向。
  所以 `stub-ecu` 收到广播请求时，如果答案塞不进 7 字节，就**真的不答**——
  读 VIN（20 字节）在功能寻址上就是"没有答案"这件事，不是 bug。

这条规矩在验收里被刻意做成一步：`22 F1 90` 广播出去，两台 ECU 都不吭声，网关回 `0x8003 0x06`。

### 一条广播 → 几条 0x8001（`DiagnosticMultiSink`）

原来的下游是 `bool (req, resp, err)`：一问一答。功能寻址下这是错的——
两台 ECU 都答了，只回一条等于替另一台说了话。所以新增：

```cpp
struct DiagnosticReply { std::uint16_t sourceAddress; std::vector<std::uint8_t> uds; };
struct DiagnosticMultiResult { bool ok; std::uint8_t nackCode; std::string reason; std::vector<DiagnosticReply> replies; };
using DiagnosticMultiSink = std::function<DiagnosticMultiResult (const DiagnosticRequest &)>;
```

服务器因此只有一套逻辑：`ok` 就逐条发 `0x8001`（`SA` 用每条应答自己的地址），
`!ok` 就按 `nackCode` 回 `0x8003`。物理寻址在同一个 sink 里包一层"一条应答"，行为与 M6 完全一致。

### 真踩到的坑：多响应下游被一行老代码吃掉了

第一次跑 `m8_e2e.sh` 时 15 项里红了 12 项，网关日志里每一句都是
**"没有装下游，只回 ACK（M3 允许这样，M4 必须接上 ISO-TP）"**——可明明装了 `diagnosticSinkMulti`。

根因：M3 时代那行 `if (!diagnosticSink) { log(...); continue; }` 还在，而且排在新的多响应分支**前面**。
只要没装单响应 sink（M8 只装了多响应那个），请求就在这儿被 `continue` 掉了，压根走不到广播。
删掉那处旧判断、把"没有下游"的兜底放到最后，一次就通。

这条教训值得记：**新增一条分支时，要先看它前面有没有"提前返回"的旧守卫。**
守卫本身没错，错在它还按旧世界的假设工作（"下游只有一种"）。

## M9：CAN FD（同一套协议，换个信封）

### 结论先摆出来

FD 不是"再写一套 ISO-TP"，是**同一个状态机换了个帧长**：

| 项目 | 经典帧 | CAN FD |
|---|---|---|
| 一帧多少个字节 | 8 | 8..64（本项目固定 64） |
| 单帧（SF）最多装 | 7（`0x0N`） | 62（`0x00` + 长度 + 数据，即**转义单帧**） |
| 首帧（FF）能带 | 6（`frameBytes-2`） | 62（`frameBytes-2`） |
| 连续帧（CF）能带 | 7（`frameBytes-1`） | 63（`frameBytes-1`） |
| 长度字段上限 | 4095（12 位） | 一样 4095（**没变**） |
| SN 循环 | 1..15 | 一样 1..15（**没变**） |
| 流控帧结构 | `30 BS STmin` | 一样（**没变**） |
| 内核结构体 | `can_frame`（16 字节） | `canfd_frame`（72 字节） |
| socket 开关 | 无 | `CAN_RAW_FD_FRAMES` 必须显式打开 |

变的只有**每帧能装多少**：`frameBytes-2`、`frameBytes-1`、以及单帧从"长度塞进 PCI"
变成"长度另开一个字节"。这也是整个 M9 唯一需要动脑的地方，其余全是照抄。

### 8 到 62 这段是个空档，只能用转义单帧

`0x0N` 里的 N 是 4 位，但协议规定 N 只能是 1..7（0 表示"长度在下一字节"）。
所以 8..62 字节的消息在 FD 上既不能写成 `0x08`（非法），也没必要上首帧 + 连续帧：

```
00 3E  62 F1 A0 00 01 02 ...     ← 转义单帧：0x00 打头，第 2 字节是长度（0x3E=62）
```

一条消息刚好 62 字节时，`00 3E` + 62 字节数据 = 64 字节，**一张 FD 帧塞得刚刚好**。
这条边界是 M9 特意挑出来验的：多 1 字节就得改成首帧，少 1 字节就浪费。

### 三个设计决定

**① FD 是通道的属性，不是全局开关。** `RouteEntry` 加了一个 `bool fd`，所以一张路由表里
可以同时挂经典 ECU 和 FD ECU——真实网关后面本来就可能是两种总线（老车 500 kbps 经典段 + 新车 FD 段）。
如果做成"全局 `--fd`"，这个项目就退化成"再跑一遍 M8"。

**② 写侧分两条路，不做"兼容写"。** `can_frame` 和 `canfd_frame` 是两个结构体（16 vs 72 字节），
拿错结构体去 `write()` 内核只回 `EINVAL`。所以 `sendFrameAs()` 里是干净的两支：

```cpp
if (cfg_.frameBytes > kClassicFrameBytes) { canfd_frame f; ... f.len = 64; write(fd_, &f, sizeof(f)); return; }
can_frame f; ... f.can_dlc = 8; write(fd_, &f, sizeof(f));
```

**③ 收侧统一用 `canfd_frame` 读。** FD socket 上经典帧只读回 16 字节、FD 帧读回 72 字节，
两种结构体**前 8 字节布局完全一致**，长度都在第 5 字节（`can_dlc` / `len` 同一位置）。
所以 `recvFrame()` 只准备一个 72 字节的缓冲，按读回字节数判断是哪种帧，长度取 `f.len` 就行——
不用两套读代码，也不会因为"读错结构体"把长度读成垃圾。

### 真踩到的坑：`#if defined` 对枚举常量无效

第一版写完，编译干净、单测全绿，跑 e2e 直接 20 项里红一片。网关日志只有一句话：

```
下游拒绝 → 0x8003 0x08 传输层错误：写 CAN FD 帧失败（0x18DA00F1，FD 帧长 64）
```

`strace` 一看就明白了：

```
write(3, "...", 72) = -1 EINVAL (无效的参数)
```

**整段日志里根本没有 `setsockopt(3, SOL_CAN_RAW, CAN_RAW_FD_FRAMES, ...)`。** 根因是这一行：

```cpp
#if defined (CAN_RAW_FD_FRAMES)      // ← 一直为假
```

`CAN_RAW_FD_FRAMES` 在 `linux/can/raw.h` 里是 **enum 的枚举成员**，不是 `#define`；
`defined()` 只认预处理宏。于是 `setsockopt` 那段被静默编译掉了——编译器不报、单测不报
（单测不碰 socket），只有真总线上的 `write` 会回 `EINVAL`，而它的表现又是"全都超时"。
去掉 `#if` 直接调用，一次就通。

教训有两层：**① 用 `defined()` 之前先确认对象是宏还是枚举；② 这类"静默编译掉"的错误只能靠端到端抓包 / `strace` 抓出来**，
纯逻辑单测永远抓不到——这也是为什么每个里程碑都要有一条真总线上的脚本。

### 另一个环境前提：vcan 的 MTU 要 ≥ 72

FD 帧是 72 字节的结构体，`vcan0` 的 MTU 不够就直接丢：

```bash
cat /sys/class/net/vcan0/mtu        # 72 才够
sudo ip link set vcan0 mtu 72
```

`m9_e2e.sh` 第 0 步就先查这个，不够就 `[SKIP]` 而不是红——因为这是环境问题，不是代码问题。

### 演示用的长 DID：让帧数自己说话

`stub-ecu` 加了三个长 DID，payload 一律取 `i & 0xFF`，远程一眼能校验：

| DID | 响应总长 | FD 帧数 | 经典帧数 |
|---|---|---|---|
| `0xF1A0` | 62（`62 F1 A0` + 59） | **1**（转义单帧刚好装满） | **9**（FF + 8 CF） |
| `0xF1A1` | 103 | 2 | 15 |
| `0xF1A2` | 200 | **4**（FF + 3 CF） | **29**（FF + 28 CF） |

同一个 `22 F1 A2`，两条通道内容**逐字节相同**，帧数 4 vs 29——这就是"换信封"最直观的证据。

### 一条命令跑完（`tools/m9_e2e.sh`）

```bash
bash tools/m9_e2e.sh 13465      # 七步二十项，一条总线两种信封
```

拓扑（同一条 `vcan0`，一张路由表）：

```bash
stub-ecu --iface vcan0 --rx 7A0 --tx 7A8 --vin LSVZZ0000B7654321 --hw HW02
stub-ecu --iface vcan0 --fd --rx 18DA00F1 --tx 18DAF100 --vin LSVCC0000C7654321 --hw HW03
doip-gateway --iface vcan0 --port 13465 \
    --route 0003:7A0:7A8:ECU_C \

```

| 步骤 | 验什么 | 结果 |
|---|---|---|
| 0 | vcan0 的 MTU ≥ 72 | ✅ 72 |
| 1 | 表里两种信封都标对（`（FD，帧长 64）` / `经典 CAN（帧长 8）`） | ✅ |
| 2 | FD 读 `0xF1A2`：200 字节逐字节正确 + 总线恰好 **4** 帧 + 每帧 64 字节 | ✅ |
| 3 | 经典读同一个 DID：内容相同 + **29** 帧 | ✅ |
| 4 | 边界 `0xF1A0`（62 字节）：FD **1** 帧（`00 3E …`），经典 **9** 帧 | ✅ |
| 5 | VIN（20 字节）：FD **1** 帧，经典 **3** 帧（FF 装 6，余 14 分两张 CF） | ✅ |
| 6 | 网关账：每条请求都记了应答条数，零失败 | ✅ |

总线样本（`candump -L`）——同一个 200 字节响应，两种信封：

```
(1795518503.279596) vcan0 18DAF100##410C862F1A2000102030405...   ← FD：## 双井号，第一位是 FD flags，之后是 64 字节数据
(1795518528.729054) vcan0 7A8#10C862F1A2000102                    ← 经典：# 单井号，首帧只带 6 字节
```

`##` 后面第一位是 FD flags（本项目一直是 `4`，BRS 位），后面才是数据；
数帧就数 `18DAF100##` 出现几次，不用写解码器。

### 单元断言：70 → 96 项

新增 E 段 26 项，把"信封变了以后哪些数要跟着变"钉死：

| 组 | 覆盖 |
|---|---|
| 单帧边界 | 7 字节仍是 `0x07`；8 字节变 `00 08`；62 字节是 `00 3E`（上限）；63 字节溢出一张帧 → 首帧 `10 3F` |
| 分片 | 200 字节 = 4 帧；首帧带 62（`frameBytes-2`）；CF 带 63（`frameBytes-1`）；`consecutiveFrameCount(200,8)=28` |
| 往返 | 62 / 63 / 200 / 1000 字节在 FD 下拆了再装，字节全等 |
| 严格校验 | 转义单帧声明 ≤7 → 报错；经典信封里出现"转义单帧声称 20 字节" → 报错；首帧声称总长 ≤7 → 报错 |
| 流控 | FD 流控头部 `0x30`、尾部补齐到第 64 字节 |

`ctest` 七套件全绿，累计 **521 项**（94 + 57 + 72 + 73 + 96 + 100 + **29**）。

## M10：多 tester 独立通道（一条通道一条队列 + 一条线程）

### 结论先摆出来

三条通道、两台 tester 同时打，端到端 20 项全绿：

| 现场 | 数字 |
|---|---|
| 慢 ECU（每条应答前睡 700ms）在跑的时候，快通道照样拿 VIN | 快 143ms / 慢 785ms |
| 同一通道两个 tester 抢同一台 ECU | 总线帧序 `1014 215A 2237 1014 215A 2237`，两条答完再开始下一条 |
| 同一条连接连发两条 | 第一条 `0x8002` ACK，第二条 `0x8003 0x08` |
| 发完慢请求立刻断连 | 那条结果回来找不到人，网关记"作废 1 条"，下一位 tester 拿到的是自己的 VIN |
| 3 个 tester × 5 条交替打两个通道 | 15 条全对，网关账 `转发 24 条，失败 0 条` |

### M4 到 M9 的网关，其实只有一把锁

`DiagnosticGateway::operator()` 里那句 `std::lock_guard<std::mutex> g (mu_)` 是 M4 留下的：
它保证"同一条总线上不会有两条请求的帧缠在一起"，代价是**连不相干的通道也被拉进同一队列**。
`0x0003` 走 `7A0/7A8`，`0x0006` 走 `18DA00F1`，物理上井水不犯河水，却要在同一把锁上排队。

更要命的是调用方：`DoIpTcpServer::runFor()` 是单线程 `poll`，一句 `0x8001` 进来就**同步**等 CAN 答完。
慢 ECU 一条 700ms，这 700ms 里服务器不 accept、不读别的连接的心跳。这就不是"串行化"的问题了，
是"一条通道的重活能卡死整个实体"。

### 拆成三件东西，各管一件事

| 部件 | 管什么 | 不管什么 |
|---|---|---|
| `JobQueue`（每条通道一个，容量 8） | 通道内 FIFO、满载当场拒、`stop()` 唤醒阻塞的 pop | 不知道 socket、不知道 UDS |
| `ResultBoard`（全局一张） | 交卷：`complete` / `wait`（带超时）/ `takeAny`（非阻塞）/ `abandon` | 不知道谁在等 |
| `DoIpTcpServer` | 受理时回 ACK、每轮 `poll` 之后 drain 结果、按 `jobId` 找连接 | 不等 CAN，一微秒都不等 |

前两件抽在 `include/JobQueue.h`，是纯逻辑、无 socket，所以能单线程测完 FIFO、容量、超时、作废这些语义；
`tests/pool_selftest.cpp` 29 项全在内存里跑，没有一条需要 `vcan0`。

### 为什么"满了当场拒"，而不是让 I/O 线程等

队列的意义是**削峰**，不是**扩大内存**。容量 8 已经比"一秒钟几条诊断请求"宽松得多；
真满了说明这台 ECU 已经被打爆，此时阻塞 I/O 线程等于把"这台 ECU 慢"升级成"整个网关不干活"。
所以 `push()` 满了一律返回失败，`doip-gw` 当场回 `0x8003 0x08`，tester 自己决定重试。
`ChannelStats` 里因此多了 `rejected`，退场时能看见"到底拒过多少"。

### 为什么结果回来要"找不到槽就落地无声"

`abandon(id)` 把槽删掉，之后 worker 答完拿 `complete` 找不到人，只把 `abandoned_` 加一。
这一步不是洁癖，是 M5"迟到帧"那件事的以太网版本：诊断仪发完请求就断线（人走了、网断了），
它那条结果如果留给"下一个连上来的 tester"，下一个就会读到一份不属于自己请求的答案——
这在真车上意味着**把 A 车的 VIN 报给 B 车**。宁可丢掉，不可错配。

### 数据面的顺序：先放锁，再交卷

`workerLoop(ta)` 里唯一允许的次序是：

```
takeJob → 记排队时长 → 独占 busMu → request() → 放 busMu → finishJob（交卷）
```

交卷必须在放锁之后。反过来的话，客户端可能在"总线还锁着"的瞬间就收到答复，
立刻发下一条，结果那条新请求还得等同一把锁——日志上就会出现"回得比问得早"这种读不懂的时序。

### 广播也得挪出 I/O 线程

M8 的 `broadcast()` 要挨个通道收应答，最坏 150ms × N 条通道。它现在跑在一条专用线程上，
`lockAllBuses()` 按 TA **升序**拿所有 `busMu`（顺序固定才不会两个线程交叉等成死锁），
`funcMu_` 保证同一时刻只有一次广播。广播期间物理请求照常在自己队列里排队，但 I/O 线程始终是空的。

### 一条命令跑完（`tools/m10_e2e.sh`）

```bash
bash tools/m10_e2e.sh 13466
```

八步二十项，拓扑是同一条 `vcan0` 上三台 ECU：`0x0003 → 7A0/7A8`（经典）、
`0x0006 → 18DA00F1/18DAF100`（FD）、`0x0007 → 7B0/7B8 --delay-ms 700`（每条应答前先睡 700ms）。

第 4 步是这一步的核心取证：两个 tester 同时打 `0x0003`，然后**不看日志看总线**——
`candump` 里 `7A8` 的数据必须是 `1014 215A 2237` 再来一遍 `1014 215A 2237`，
即"首帧 + 两个连续帧"成组出现；中间插进一个别人的首帧，就是同通道串行被破坏。

第 6 步用一段裸 socket 造断线：激活 → 发一条打到慢通道的 `0x8001` → 立刻 `close()`，
睡一秒后另开一条连接读 `0x0003` 的 VIN。拿到自己的 VIN 才算过，网关那边同时要有"作废 1 条"。

网关用 `--seconds 22` 自己退场，脚本 `sleep` 等它打印账目再断言，所以整条脚本大约 27 秒。
账要对得上：`2 + 2 + 2 + 1 + 2 + 15 = 24`，忙拒那条根本没进网关。

### 单元断言：492 → 521 项（新套件 `doip-pool` 29 项）

| 组 | 覆盖 |
|---|---|
| 顺序 | 三条 job 进、三条按 FIFO 出，`depth` 与 `peak` 跟着涨落 |
| 满载 | 容量 3 的队列塞第 4 条 → `push` 返回 false，`rejected` 加一 |
| 停机 | `stop()` 之后不再收新活，但已入队的照跑完；`stop()` 能唤醒阻塞在 `pop` 上的线程 |
| 交卷台 | `complete` → `takeAny` 拿回**同一个** `id` 与原请求；`wait` 超时返回 false 且槽被清 |
| 作废 | `abandon` 之后迟到结果无人接，`pending` 归零 |
| 跨线程 | 一个线程 `pop` 阻塞中，另一个线程 40ms 后 `push`，被唤醒耗时实测 46ms |

`tests/pool_selftest.cpp` 不碰 socket、不碰 CAN，`ctest -R doip-pool` 一秒内跑完。

### 这一步踩到的坑

- **`-Werror` 抓到一个死函数**：`src/DoIpGateway.cpp` 匿名命名空间里还留着 M8 的 `nackFor()`，
  重写后没人调，直接 `unused-function` 报红。删掉即可——`-Werror` 在这种"重写大文件"的活上真值钱。
- **自测的断言写早了**：`stop()` 之后我第一版直接断言"马上 `pop` 返回 false"，可队列里还剩 job 2/3。
  `stop` 的语义是"不再收新活"，不是"清空"。改成连取三条再断空，29 项才全绿。
- **M9 的断言被异步路径打红**：`m9_e2e.sh` 第 6 步原本 `grep "下游答了"`，可 M10 之后这条日志变成了
  `job=N 回来 N 条 → 逐条用 0x8001 送回`。判据改成 `grep -qE "回来 .* 条|下游答了"`，
  M9 恢复 20/20——异步化会改日志形状，这是回归脚本必须一起改的地方。
- **`pendingTarget` 漏赋值**：`deliver()` 失败要回 `0x8003`，里面的 SA 必须是"请求里的 TA"，
  初版只存了 tester 的 SA。给 `Conn` 加了 `pendingTarget`，submit / deliver / dropConn 三处成对清空。
- **取证脚本的 PCI 位置看错**：`candump -L` 的 data 是十六进制串，`1014` 里前两个字符 `10` 就是首帧 PCI、
  `14` 是长度；我第一版按"第三个字符才是 PCI"写断言，明明帧序完全正确却报"交叉"。
  断言错和代码错长得一样，这也是为什么这一步要先把 `SEQ=` 打出来再判。

## M11：诊断仪侧多响应配对（一条广播，三台 ECU 各答一句）

### 结论先摆出来

`doip-client` 现在能收齐一轮广播的所有答案，并且**按 SA 归档**：

| 现场 | 数字 |
|---|---|
| 三台 ECU 都听 `7DF`，一条 `22 F1 91` 广播 | `RESPONSE_COUNT=3`，`RESPONSE_SAS=0x0003,0x0006,0x0007` |
| 每条答案归谁 | `0003:HW02  0006:HW03  0007:HW04`，没有一条对错门 |
| 客户端窗口 80ms（最慢那台 120ms） | 整批 0 条；窗口 300ms 就三条全收 |
| 没人听的功能地址 | `0x8003 0x06` + `RESPONSE_COUNT=0` |
| 表里没有的物理地址 | `0x8003 0x03` + `RESPONSE_COUNT=0` |

### 这一步补的是一个"看起来早就做完了"的洞

M8 已经让网关把几条答案逐条送回，`m8_e2e.sh` 也验过"两台各答一句、SA 不相同"。
但那 15 项是**用 python 裸 socket 收的**——项目自己的 `doip-client` 一直只收第一条：

```cpp
Message resp;
if (!recvMsgBuf (fd, resp, inbuf, 3000, why)) ...   // 收一条就 return 0
```

于是"功能寻址"在仓库里只是**服务端能力**，客户端侧依旧只能读第一台。
真拿去做诊断，症状是"扫不到另外两台车"——而且不报错，最容易被当成"那两台不在线"。

M11 给 `doip-client` 加了 `--all`：收齐、归档、出一张表，最后打机器可读的几行给脚本。

### 三件纯逻辑，抽成 `DiagResponseCollector`

`socket` 里做归档最难测，所以和 M10 的 `JobQueue` 一样，先把它剥成纯逻辑放 `include/DiagResponseCollector.h`：

| 问题 | 答案 | 为什么不能偷懒 |
|---|---|---|
| 这条答案是谁说的？ | 按 `SA` 查表；重复的直接并进那一台 | 按"第几条"猜，只要有一台答晚了就全错位 |
| 同一台又答一遍算什么？ | `duplicates++`，**正文保留第一次** | 不能覆盖：第二次可能是重发，也可能是它改了状态，覆盖就丢证据 |
| 同一台两次答得不一样？ | `changes++` | 这不是重复，是它在两问之间换了状态——必须报出来 |
| 收齐了吗？ | 静默满窗口 | DoIP 的 `0x8001` **没有"最后一条"字段**，协议层没有批次概念 |

最后一行是这一步的硬骨头：真实诊断仪判断"功能寻址收齐了"用的是 UDS 的 `P2*` 计时（等它不响了），
本质上和我们这个"静默窗口"是同一件事。所以窗口不是一个可以随手拍的参数，它直接决定漏不错。

### 一次广播的时序，决定了窗口该给多大

网关这一轮广播的动作是：发一帧 `7DF` → 按 TA 升序，每条通道固定 150ms 收 →
**攒齐所有答案后一次性交回**。中间有一台慢 120ms 的 ECU，整批答案到达诊断仪的时刻就由它决定。

```
t=0     客户端发 0x8001（TA=0xE400）
        ← 0x8002 ACK（立刻）
t≈120   ECU_C 才答（它每条前面睡 120ms）
t≈130   网关把 3 条答案一次交回
```

所以"窗口小于最慢那台"的后果不是"少收一条"，而是**整批 0 条**；网关账上那 3 条是实打实收到了的。
M11 当时的验法是 `80 → 0 条`、`300 → 3 条`，第 9 步的 `广播 5 次，收回应答 15 条` 证明"网关收齐了、客户端没等到"。

**M12 之后这条变了**：网关不再攒批，同一场景变成 `60 → 2 条`（快的两台先到，慢的还没到）。
`m11_e2e.sh` 第 5 步的断言跟着改成 2 条，并在注释里写明这是 M12 之后的语义。

### "没有答案"的两种情形必须分得清

| 码 | 含义 | 客户端该做什么 |
|---|---|---|
| `0x8003 0x06` | 广播出去了，没有一台答（没人听/都不支持这个 DID） | 换 DID 或换地址，**不是**"这台车没有 ECU" |
| `0x8003 0x03` | 这个 TA 不在路由表里 | 路由表配错了，或问错了人 |

两者的客户端表现都是"零条答案"，只有 NACK 码不同。所以 `doip-client --all` 必须把 `0x8003`
也当答案处理（**它常常比 ACK 晚到**），打印码并停止等——第一版漏了这点，第 7 步直接红。

### 一条命令跑完（`tools/m11_e2e.sh`）

```bash
bash tools/m11_e2e.sh 13467 13468
```

九步二十项。拓扑是一条 `vcan0` 上三台 ECU 都听 `7DF`（`0x0003` 经典 / `0x0006` FD / `0x0007` 经典且每条答前睡 120ms），
再起第二个网关，功能表挂一个**没人听**的 `0x5DF` 用来验 `0x06`。

第 3 步验条数与顺序，第 4 步拿 python 把 `RESP<n>_HEX` 解成 ASCII，逐条和 SA 对（`HW02/HW03/HW04`）；
第 5 步是窗口对照；第 6 步连跑两轮，证明上一轮的答案不会混进来；第 9 步对账并对总线：
`7DF` 帧数必须等于广播次数（一次广播 = 一帧请求，不是一帧一台）。

### 单元断言：521 → 566 项（新套件 `doip-collector` 45 项）

| 组 | 覆盖 |
|---|---|
| 空 | 0 台、0 条、`quietMs=-1`、等多久都不算收工 |
| 顺序 | 按到达排序（先到的 `0x0006` 排第 1，不是按 SA 大小） |
| 重复 | 同 SA 再答 → `Duplicate`，台数不涨、`duplicates++`、正文不覆盖 |
| 改口 | 同 SA 换了正文 → `changes++`，仍不覆盖第一条 |
| 窗口 | 静默 99ms 不收工、100ms 收工（边界含等号）、新响应把收工时间往后推 |
| 负响应 | `0x7F xx yy` 也算一条答案，`negative()` 为真 |
| 长报文 | 200 字节逐字节相同 |
| 规模 | 20 台一起答，两头都能查到 |
| 复位 | `reset()` 之后回到"从来没响过" |

`ctest -R doip-collector` 一秒内跑完，不需要 `vcan0`。

### 这一步踩到的坑

- **功能寻址只收单帧**：我第一版拓扑用 `22 F1 90`（VIN，20 字节），三台 ECU 里两台当场拒绝回答——
  `stub-ecu` 的日志写着"响应 20 字节塞不进单帧（上限 7），按协议不答"。只有 FD 那台答了，
  于是 `RESPONSE_COUNT=1`。换成 `22 F1 91`（硬件号，6 字节）才对。这不是 bug，是 M8 的边界在教训我。
- **`0x8003` 会晚到**：`--all` 的循环第一版只认 `0x8001`，`0x8003` 被当"不是响应，跳过"，
  结果第 7 步永远等不到码。ACK 先回、NACK 后回，是网关"先受理再判断"的直接后果。
- **`nameOf(DiagNack)` 返回 `const char*`**，不是 `std::string`，`.c_str()` 直接编译报错——
  这个文件里别处的 `nameOf` 是另一个重载，照抄就错。
- **`const` 的 `find()` 不能在 `add()` 里用来改**：编译报 `invalid conversion from const*`。
  加了一个私有的 `findMutable()`，语义上也清楚：查询是只读的，归档要改。

## M12：流式交付（收一条转一条，且一条都不发两遍）

### 结论先摆出来

- **首条答案时延从"最慢那台决定"变成"谁答完谁先到"**：同一台车、同一条总线、同样三台 ECU，
  流式网关 `FIRST_AT ≈ 0ms`，`--no-stream` 对照 `FIRST_AT ≈ 107~213ms`。
- **同一条答案一条也没多发**：`RESPONSE_ARRIVALS = RESPONSE_COUNT = 3`、`COLLECTOR_DUPLICATES = 0`，
  网关账上写的是 `回来 3 条（流式已发 3 条）→ 补齐 0 条`。
- 新套件 `doip-stream` 27 项；`ctest` 九套件 **593 项**；`m12_e2e.sh` 八步 **25 项**；`ci_local.sh` **16 步 29 项**。

M11 攒批的账是这样的：一轮广播 → 按 TA 升序逐通道收 → **全部收齐才一次性交回**。
一条 `22 F1 91` 出去，快的两台 1ms 内就答了，但那 3 条答案要等慢的那台 120ms 之后才一起到诊断仪手里。
功能寻址问的本意是"这一类 ECU 谁在"，结果被最慢的那台按在地上。

### 两半，缺一不可

**上半：边收边发。** 网关加一个 `ReplySink`：`broadcastLocked(jobId, req)` 每 `push_back` 一条答案就调一次
`replySink_(jobId, rep)`；`functionalLoop` 传 `job.id` 进来，同步路径（M8 的 `broadcast(req)`）传 `0`，
所以老的同步用法一行都不用改。

这个回调**是在"所有通道的 busMu 都被持有"的状态下被调用的**——它只许往队列里塞一下，
真正的 `send` 仍然只由 I/O 线程做。这不是新发明，就是 M10"一条总线一个主人、一个 socket 一个主人"的延续。

**下半：交卷只补差额。** 边到边发完之后，`JobResult` 里**仍然带着全部 replies**（这是失败语义、
统计和日志的基础），如果交卷时再发一遍，客户端就会看到重复。所以记一本账（`include/StreamLedger.h`）：

```
已流式发 k 条 → 交卷时结果共 total 条 → 该补发 total - k 条
```

`deliver()` 里 `already = ledger.streamed(jobId)`、`ledger.forget(jobId)`，然后从 `replies[already..]` 开始发。
顺序能对上的理由很朴素：广播按通道顺序收、按通道顺序外发，流式发出去的一定是 `replies` 最前面那几条。

### 一个绕不开的细节：睡在 poll 上的线程醒不过来

答案进了队列，可是 I/O 线程正睡在 `poll` 里等 fd 事件——**队列变化不是 fd 事件**。
第一版没管这件事，实测首条答案要等 poll 超时（最长 100ms）才出去，等于白干。

解法是自唤醒管道（self-pipe）：`open()` 里建一对 `pipe`，读端塞进 poll 集合，写端非阻塞；
`onStreamReply()` 入队后写一个字节，poll 立刻返回，`drainStream()` 在锁外把队列整体换出来再逐条 `send`。

### 40ms 不是我们的代码：Nagle 与延迟 ACK

接上自唤醒管道后，首条答案稳定在 **43ms**，怎么改都快不起来。取证：`candump -L` 显示 7DF 与 7A8 之间
只差 **0.06ms**——总线上是毫秒级，慢的是以太网这一侧。

原因：`0x8002 ACK` 和紧随其后的第一条 `0x8001` 是两条小报文，服务端没开 `TCP_NODELAY`，
Nagle 把第二条压住等前一条的 ACK，正好撞上对端的"延迟确认"（≈40ms）。
两端都 `setsockopt(TCP_NODELAY)` 之后，同一场景的首条答案变成 **0ms**。

量时延的时候，这 40ms 千万别记在网关的排队上——它不是我们的。

### 真踩到的坑（这一节一共五个，按发现顺序）

1. **`drainStale()` 一直是个空操作。** 它原来写的是 `while (recvFrame(d, dlc, 0, e))`，
   而 `recvFrame` 第一步是 `if (now >= deadline) return "接收超时"`——`timeout=0` 时 deadline 就是"现在"，
   一条都不会读。平时只是让"偶发超时"多一点点，M12 把它放大成**答案错位**：
   另一台网关（或上一轮）让 ECU 答的那一帧躺在缓冲区里没人读，
   下一次广播的 `recvFunctional` 就把它当成本次的答案——**上一轮慢 120ms 的那台，这一轮 0ms 就"答"了**，
   它真正的答案留给下一轮，一轮轮传下去。M11 攒批时这个错被整批延迟掩盖着，谁都看不见。
   现在改成真正的非阻塞清仓（`poll(0)` 说没数据就停）。
2. **测试桩自己的睡意混进了测量。** `stub-ecu` 的主循环 `poll` 超时是 50ms，
   于是"应答只要几毫秒"被量成"应答要 50ms"。收到 10ms 之后，测量才站得住（顺带省了总线空转）。
3. **`-O2` 下 `(void)::write(...)` 照样报错。** glibc 给 `write()` 标了 `warn_unused_result`，
   强转 `(void)` 在 `-O0` 放过、`-O2` 必红。ci_local 故意用 `-O2`，就是为了抓这种只在优化后才露头的警告。
4. **`routing_selftest` 的收包没有缓冲。** 开了 `TCP_NODELAY` 之后，两条 21 字节应答经常同段到达，
   而测试桩的 `recvMessage` 把两条一起塞进 `whole` 就返回了——看起来像"服务器吞了粘包的第二条"，
   其实是测试桩自己吞的。按 fd 记"还没交出去的余字节"之后稳定。
5. **窗口 40ms 的断言连红两次**，我一直以为是阈值定错，实际是坑 1 造成的"慢的也秒回"。
   **验收脚本自己也要被验收**：断言红了先证明现象，再调数字。

### 工具与开关

- `doip-gateway --no-stream`：不接 `ReplySink`，退回 M11 的攒批行为，专门用来做 A/B 对照。
- `doip-client --trace`：每条答案打 `RESPn_AT`（相对发出诊断请求的毫秒），末尾打 `FIRST_AT / LAST_AT / SPAN_AT`。
- 退场账多两行：`流式交付 N 条（收到就转，不等一轮收齐；同一 job 交卷时只补差额）`、
  `流式时连接已断 M 条（丢弃不转交）`。

### 一条命令跑完（`tools/m12_e2e.sh`）

```bash
# 两台网关（流式 13469 / --no-stream 13470）+ 三台 ECU（0x0003 经典、0x0006 FD、0x0007 慢 120ms）
bash tools/m12_e2e.sh 13469 13470
```

八步：启动 → 流式三条先到 → 攒批对照（首条被拖住）→ 不重发 → 窗口 40ms 收到 2 条 →
提前断线（迟到的流式答案丢弃、不转交）→ 下一位 tester 拿自己的三条 → 网关账与总线取证。

核心断言（实测值）：

```
FIRST_AT=0ms  LAST_AT=135ms  SPAN_AT=135ms        ← 流式
FIRST_AT=213ms SPAN_AT=0ms                        ← 攒批对照
RESPONSE_COUNT=3  RESPONSE_ARRIVALS=3  COLLECTOR_DUPLICATES=0
job=… 回来 3 条（流式已发 3 条）→ 补齐 0 条
流式交付 16 条 / 流式时连接已断 2 条
广播 6 次，收回应答 18 条；总线 7DF 帧 7 条 = 两个网关之和
```

时间断言不写死绝对值：stub 自己有几十毫秒抖动，所以用**同一次会话里的两端对比**
（`nFirst - sFirst ≥ 80ms`）和 **SPAN 的形状**（流式 ≥90、攒批 ≤20），比死数字稳得多。

### 单元断言：566 → 593 项（新套件 `doip-stream` 27 项）

`StreamLedger` 只做整数加减，所以自测全是"同一批答案被两条路径各处理一次"的情形：

- 一条都没流式 → 交卷时补发全部；
- 全部流式过 → 补发 0（**这就是不重复发的全部保证**）；
- 部分流式（2/3）→ 补 1；账比结果还多 → 补 0（不许下溢）；
- 多个 job 互不串味；`forget` 之后账销、`jobs()` 归零、累计计数是观测量不回退；
- `clear()` 全部归零；64 位 jobId 也能归档。

`ctest` 九套件全绿，累计 **593 项**（94 + 57 + 72 + 73 + 96 + 100 + 29 + 45 + **27**）。

## M13：实体级的 tester 地址仲裁（0x01 / 0x03 第一次真的用起来）

### 先把一个说法纠正掉

我在上一节末尾提 M13 时说"真实网关会给每台 tester 分配逻辑地址"。查了 2019 版的地址分段和 0x0006 的码表之后，
这句话是不准确的：**tester 的逻辑地址是 tester 自己选的**，0x0E00–0x0E7F 留给法规诊断仪、
0x0E80–0x0EFF 留给厂商/售后增强诊断仪，它自己带过来，实体不发号。

实体真正要做的两件事是**查重**和**限流**，对应的就是 0x0006 里那两个一直写在枚举里、却从没被用过的码：

| 码 | 含义 | 什么时候回 |
|---|---|---|
| `0x03` | 该源地址已在**另一条** TCP_DATA socket 上注册并激活 | 两台 tester 想用同一个地址 |
| `0x01` | 本实体能同时承载的 socket 都已被注册并激活 | 激活名额满了（但 TCP 还连得上） |

### M2 留下的洞：激活状态只跟着"连接"走

`RoutingActivation` 是每条连接一份的，它管三件事：SA 合法、激活类型支持、**这条 socket 内不许换人**。
这三条都没错，但它管不了第四条——**两台 tester 各开一条连接、用同一个 SA 各激活一次**。

网关这边一切正常，总线那头却是两个同址的诊断仪在说话：ECU 分不清谁是谁，
只有网关靠 `jobId` 才没把答案送错人。真网关不允许这件事，所以 M13 必须有一张**实体级**的账。

### 两张表 + 一台机器：`TesterRegistry`

```cpp
byConn_ : 连接号 → 逻辑地址     // 这条连接占了哪个地址
bySa_   : 逻辑地址 → 连接号     // 这个地址被谁占着
```

`tryRegister(sa, connId)` 的四种结论，顺序是有讲究的：

| 情形 | 结论 | 为什么不这样排就错 |
|---|---|---|
| 本连接已登记同一个地址 | `0x10`（幂等） | 断线重连后重发请求是常态，不能当错误 |
| 本连接已登记别的地址 | `0x02` | 一个 socket 代表一段已认证的上下文，不许中途换人 |
| 地址被**别的**连接占着 | `0x03` | 这就是同址冲突，先报"你"的问题 |
| 名额已满 | `0x01` | 再报"我"的问题；两者同时成立时先报 0x03，因为它更具体 |

用连接号而不是 fd 当身份：**fd 会被内核复用**，断开一条、再开一条，fd 可能还是同一个数字，
拿它做身份就会出现"新连接继承了老连接地址"的幽灵 bug。

### "连接 ≠ 激活"：0x01 以前为什么出不来

M13 之前，`maxConnections` 和"能激活几台"是同一个数（4）。于是第 5 个客户端**连 TCP 都连不上**，
根本走不到路由激活那一步——0x01 这个码在代码里存在，但永远不可能被发出去。

现在拆成两个数：`maxConnections = 8`（挂得住几条 socket）、`maxActivated = 4`（同时能给几台 tester 激活）。
第 5 台连得上、也能发 0x0005，然后拿到 `0x01`——这才是这个码存在的意义：**告诉它"我来得了，但排不上"**。

### 断开必须还地址

`dropConn()` 里在 `routing.reset()` 旁边加一句 `registry_.release(c.id)`。
漏了它的表现不是报错，而是"这个地址永远在别人名下"：下一位 tester 拿同一个地址会一直吃 0x03，
而你已经找不到那个"别人"了——**地址泄漏比内存泄漏更难查**，因为它没有任何症状，只有一个错误码。

### 一条命令跑完（`tools/m13_e2e.sh`）

```bash
# 网关（8 连接 / 4 激活名额）+ 一台经典 ECU，多连接场景由裸 socket 脚本精确控制
bash tools/m13_e2e.sh 13471
```

十五项，核心是这一段场景（`tools/m13_check.py`）：

```
A  0x0E00 → 0x10        A  0x0E00 再来 → 0x10（幂等）     A 改 0x0E09 → 0x02
B  0x0E00 → 0x03（A 还占着）      C/D/E 各用自己的 → 0x10（凑满 4 台）
F  0x0E04 → 0x01（第 5 台，TCP 连得上）
A 断开 → B 重试 0x0E00 → 0x10（地址还回来了）      G → 0x01（又满了）
B 发 22 F1 90 → ACK + 62 F1 90 + LSVZZ0000B7654321（仲裁没把数据通路弄坏）
```

网关的账要对得上：`地址冲突 1 次（0x03）`、`激活名额已满 2 次（0x01）`、`成功激活 6 次`（A、A 重复、C、D、E、B 重试）。

### 单元断言：593 → 636 项（新套件 `doip-registry` 43 项）

| 组 | 覆盖 |
|---|---|
| 空/正常 | 0 个激活；登记后 `addressOf` / `ownerOf` 双向查得回 |
| 幂等 | 同连接同地址重发 → 0x10，计数不涨 |
| 换址 | 同连接换地址 → 0x02，原绑定不变，新地址没被偷偷登记 |
| 冲突 | 另一连接抢同一地址 → 0x03，原主人不变，冲突计数 +1 |
| 容量 | 上限 2 时第三个 → 0x01，且**不记到 0x03 的账上**（两种错因要分开） |
| 释放 | 断开后地址可被新连接拿走；重复释放返回 false；两张表都清 |
| 观测 | 计数只涨不回退，`clear()` 才归零 |
| 边界 | 0x0EFF、64 位连接号、运行期改上限 |

`ctest -R doip-registry` 一秒内跑完，不需要 `vcan0`——它证明的是"账不会算错"，
"码真的发出去了"只能靠 `m13_e2e.sh` 在真 socket 上称。

## M14：实体状态与电源模式（把 M13 的账对外公布）

M13 建了一张实体级的账：谁激活了、还剩几个名额。但这张账只活在网关自己的退场日志里 ——
诊断仪想知道"你还接得下几台"，只能靠撞（撞出 0x01 才知道满了）。标准里回答这个问题的是
**0x4001 → 0x4002**，同一族的还有 **0x4003 → 0x4004**（"现在能做诊断吗"）。

这两对报文和 M1 的车辆发现是邻居：都走 **UDP 13400**，都不需要建 TCP 连接。区别只在问什么：

| 请求 | 应答 | 问的是 |
|---|---|---|
| `0x0001` | `0x0004` | 你是谁、VIN 多少（发现） |
| `0x4001` | `0x4002` | 你还能接几台、能收多大（实体状态） |
| `0x4003` | `0x4004` | 现在能做诊断吗（电源模式） |

### 0x4002 的四个字段，每个都要和实现对得上

| 字段 | 字节 | 我们填什么 | 对不上会怎样 |
|---|---|---|---|
| node type | 1 | `0x00` 网关 | 填 0x01（节点）等于告诉诊断仪"我后面没有子网"，它就只来问网关自己 |
| max open sockets | 1 | 8 | 报大了，第 9 台连上来会被 `accept` 之后立刻关，诊断仪看不到任何码 |
| cur open sockets | 1 | 现在开着几条 | 报错了，诊断仪据此判断"实体很忙"，实际空着 |
| max data size | 4（大端） | 4096 | 报 32KB 却在内部分 4KB 拒收，诊断仪每次都吃 NACK 0x02 |

第三条最容易写错：**这个数数的是"开着的 TCP_DATA socket"，不是"激活了几台 tester"**。
这两件事 M13 才刚拆开（`maxConnections = 8` / `maxActivated = 4`）。所以场景里专门开了
3 条连接只激活 1 条，`cur` 必须是 **3** 而不是 1 —— 一个没激活的连接也占着 socket。

第四条也一样：公告的 4096 就是 `parseMessage` 里真正卡的那个 `maxPayload`。
**对外报一个数、内部卡另一个数**，是"公告 ≠ 实现"的典型，排查时会一直怀疑网络。

### 0x4001 / 0x4003 只许走 UDP

它们不是"连接内协商"，是"连上来之前先问清楚"。所以：

- 走 TCP 发过来：**不回答，只记账**（`TCP 上收到 UDP 专属请求 N 次`）。惯着它，客户端就不会改。
- 带载荷发过来：**沉默**。UDP 上没有 NACK（M1 定的规矩：一个坏广播 + N 个实体 = 广播风暴），
  沉默就是唯一正确的回答。
- 只做发现的实体（`doip-discover --serve` 之外，或没接 `entityStatus` 回调的）：沉默也是对的 ——
  这是可选特性。

### 同一个端口上的两套业务，靠类型分派

`UdpDiscoveryServer` 的 `runFor()` 里先看类型：`0x4001`/`0x4003` 走 `respondToEntityQuery()`，
其余交给 M1 的 `respondTo()`。两套判据都是**纯函数**，都能在内存里测完。

### 跨线程读状态：为什么加了一个 atomic

`cur open sockets` 是活的，必须现数。但数的过程有个坑：

- `conns_` 只有 **I/O 线程**在动（accept / drop / 遍历）；
- 回答 0x4001 的是 **UDP 线程**。

让 UDP 线程去遍历 `conns_` 就是数据竞争 —— 而且它不会每次都崩，是"跑十遍崩一次"的那种。
所以服务器维护一个 `std::atomic<std::size_t> openSockets_`：accept 加一、close 减一，
UDP 线程只读它。快照可能差一条（那一刻正好有人连上），但**不可能是坏内存**。

同一条道理在 M13 也能看到：`TesterRegistry` 也是 I/O 线程独占的，UDP 线程只能通过原子量或
`entityStatus()` 这种明确的取数口去读。

### 一条命令跑完（`tools/m14_e2e.sh`）

```bash
# 网关（8 连接 / 4 激活 / UDP 上同时答发现 + 实体状态）+ 一台 ECU
bash tools/m14_e2e.sh 13472
```

二十项，核心是这一段场景（`tools/m14_check.py`，裸 socket）：

```
0x4001 空闲      → 0x4002：node=00(网关)  max=08  cur=00  maxdata=4096
0x4003           → 0x4004：01 ready
开 3 条 TCP      → cur=03        （数 socket，不是数激活）
激活其中 1 条    → cur=03（仍是 3）  + 0x0006 码 0x10
0x4001 带 1 字节 → 沉默           0x4003 带 1 字节 → 沉默
0x4001 走 TCP    → 不回           0x0001 同端口 → 0x0004（VIN 照旧）
全部断开         → cur=00        （账要还，和 M13 释放地址同源）
```

网关的账也要对得上：`实体状态/电源模式 7 条`（5 次 0x4001 + 2 次 0x4003）、
`TCP 上误发 1 次`（只记账不回答）。

### M14 第一遍踩的两个坑（都记在代码注释里）

1. **0x0006 的码取错了位**：`payload[2]` 是实体地址的高字节 `0x00`，看着像"未知源地址被拒"，
   实际成功码 `0x10` 在 `payload[4]`。教训：**验收脚本自己也要被验收** —— 拿一个"本来就该失败"
   的码去断言成功，会把一个通过的实现判成红的。
2. **账目条数算少了**：以为场景发 6 条，实际 7 条（带载荷的那两条也算实体查询）。
   断言前先数清楚，比事后改期望值省事。

### 单元断言：636 → 694 项（新套件 `doip-entity` 58 项）

| 组 | 覆盖 |
|---|---|
| 编码布局 | 7 字节、字段顺序、4 字节大端（4096 = `00 00 10 00`，写成小端就是 1048576） |
| 往返 | 四个字段编了再解，一个不差 |
| 短式 | 只发 3 字节的老实现也认，`maxDataSize = 0`（未告知，不猜 4096） |
| 长度 | 2 / 5 / 8 字节都解不开，且带原因 |
| 电源模式 | 0x00 / 0x01 / 0x02 三值 + 保留值 0x03 拒绝（不猜成 ready） |

| 折快照 | 300 → 255（不能回绕成 44）；0 个连接报 0 |

## M15：UDS 刷写链路（0x31 擦除 → 0x34 → 0x36 → 0x37 → 0x31 校验）

前面十四节里，每条诊断都是**一问一答**：问 VIN 就得 VIN，问快照就得快照，ECU 不需要记住
上一个请求是什么。所以到 M14 为止，整条链路上唯一"记着东西"的是连接状态和地址账。

刷写不是这样。它是**一条有状态的会话**：

```
0x31 01 FF00  擦除          → 71 01 FF 00
0x34          我要传 100 字节，放 0x00400000，一块最大多少？ → 74 20 00 22
0x36 01 <32B> 第 1 块        → 76 01
0x36 02 <32B> 第 2 块        → 76 02
...
0x37          传完了         → 77 <4 字节 CRC-32>
0x31 01 FF01  你自己校验一下  → 71 01 FF 01 00（00 通过 / 01 失败）
```

这五步里，**每一步都依赖上一步留下的东西**：没擦就不能下载、没协商就不能传、没传够就不能收尾。
M9 的 FD 决定了"一块最多能塞多少"，M10 的队列决定了"一百块会不会把别的通道堵死"，
M12 的流式决定了"每块的 76 会不会等最后一起回来"。M15 就是把它们串成一条真实的刷写链。

### 五个服务的分工，别混

| 服务 | 名字 | 干什么 | 谁记状态 |
|---|---|---|---|
| `0x31 01 FF00` | RoutineControl（擦除） | 清镜像、把状态回到"可下载" | ECU |
| `0x34` | RequestDownload | 声明地址、长度、数据格式，**协商块长** | ECU |
| `0x36` | TransferData | 一块一块传，每块带 **BSC 序号** | ECU |
| `0x37` | RequestTransferExit | 收尾，回报整条镜像的 CRC-32 | ECU |
| `0x31 01 FF01` | RoutineControl（校验） | tester 把 CRC 送上来，ECU 比对 | ECU |

注意最后一个方向：**CRC 是 tester 算好发上来的**，ECU 只负责"和我手里的一致吗"。
所以这条例程的"失败"不是否定响应，而是正响应 `71 01 FF 01 01`——传输本身没出错，
是内容不对。这两件事必须分开，否则日志里"刷写失败"永远分不清是链路问题还是镜像问题。

### 三个最容易写错的地方（都在 `include/FlashTarget.h` 里钉住了）

**① `0x76` 回的是"收到的那块 BSC"，不是"下一块"。**
真实实现和 scapy / udssimulator 都是 echo。写成"回下一块"的客户端会跟着错位：
第 1 块收到 `76 02`，于是它以为该发 3 —— 现场表现是"每 256 块错一次"（回绕的地方更乱）。
本项目第 1 块发 `36 01`，回 `76 01`。

**② `maxNumberOfBlockLength` 含 `0x36` 的 SID 和 BSC 两个字节。**
标准里这个数限的是**整条 0x36 请求**，不是数据段。通告 34，客户端就只能塞 32 字节数据。
我们把它当"数据上限"，每块多带 2 字节 —— 边界那一块必挂，而且报的是 0x13（长度错），
看着像"客户端写错了"，其实是被刷端自己理解错了。启动行里专门写清楚：
`通告块长 34 字节（含 0x36+BSC，数据 32）`。

**③ BSC 从 `0x01` 起，`0xFF` 之后是 `0x00`（回绕），不是 `0x01`、也不是报错。**
100 字节的镜像永远测不到这一条：4 块就到头了。所以自测里专门造了 260 块（2080 字节）
跑一遍回绕。有的 OEM 变体是 `0xFF → 0x01`（`0x00` 非法），那是另一套规矩，
我们按"回绕到 0x00"实现，并把它写进边界。

### 每个错误用哪个码，别一律 0x10

| 情况 | 码 | 为什么是这个 |
|---|---|---|
| 没擦除就 0x34 / 已 active 又 0x34 | `0x22` conditionsNotCorrect | 参数没错，是"现在不许" |
| `0x34` 的 `dfi≠0` / `alfid=0` / 长度 0 / 超镜像上限 | `0x31` requestOutOfRange | 参数本身越界 |
| `0x34` 地址/长度段字节数不对 | `0x13` incorrectMessageLength | 长度错 |
| 没协商就 `0x36` / 没协商就 `0x37` / 收尾后再 `0x36` | `0x24` requestSequenceError | 顺序错 |
| `0x36` 数据比通告的块长多 | `0x13` | 还是长度错 |
| `0x36` 的 BSC 跳号 | `0x73` wrongBlockSequence | 序号错 |
| `0x36` 超出 `0x34` 声明的总长 | `0x71` transferDataSuspended | 暂停，不是"重来" |
| `0x37` 时数据没传够 | `0x24` | 顺序/完整性错 |

一张表的意义：现场看日志时，`7F 36 73` 和 `7F 36 13` 差一个字节，指向的却是
"客户端序号管理"和"块长口径"两个完全不同的方向。都给 0x10 就等于什么都没说。

### 重发为什么必须幂等

ISO-TP 会重传，应用层也可能因为应答丢了而重发。如果 ECU 把"同一个 BSC 又来一遍"当成跳号，
那么**链路丢一次应答就永久卡死**：客户端一直重发那一块，ECU 一直回 0x73。

所以 `transferData()` 的第一条判断不是"序号对不对"，而是"这是不是我刚收过的那块"：
`lastBsc_ != 0 && bsc == lastBsc_` → **不重复写、只重回 `76 <bsc>`**。
自测里专门发两次 `36 01`，两次都 `76 01`，并且最后的 CRC 证明镜像里没有写两遍
（写两遍就是 132 字节，CRC 立刻不一样）。

### 0x37 带 CRC，"长度对"不等于"内容对"

`0x37` 的判据是 `image_.size() == expectedSize_`，但那只证明**字节数够了**。
所以正响应里必须带一个 4 字节 CRC-32（`crc32Of()`，poly `0xEDB88320`，初值与结果都异或
`0xFFFFFFFF`，和 zlib / python 的 `zlib.crc32` 一致）。

自测第一条就是这个函数的标准校验值：`crc32("123456789") = 0xCBF43926`。
CRC 自己算错的代码，后面所有"校验通过"都是假绿 —— 所以先钉这把尺子。

### 状态机只有三个格

```
        ┌────────── 0x31 FF00 ──────────┐
        ↓                               │
   [已擦除] ──0x34 成功──> [下载中] ──0x37 成功──> [已收尾]
        ↑                               │
        └─────── 再次 0x31 FF00 ────────┘   （现场重来：擦除把在途状态一起清掉）
```

- 擦除**允许在下载中途发生**（现场就是这么重来的），它把镜像、`expectedSize_`、
  `active_`、`lastBsc_` 一起清掉；
- `0x34` 成功时也清镜像（重新声明长度就是重新开始），所以"最后一次会话"才是退场账里那一条。

### 纯逻辑，header-only，54 项自测

`include/FlashTarget.h` 不碰 socket、不碰 CAN，只做"收到一条 UDS 字节，我该回什么"。
因为刷写最难的部分是**状态与判据**，不是发帧。`stub-ecu --flash` 只是把它接到主循环里，
`m15_check.py` 再通过网关从以太网侧打进来。

| 组 | 覆盖 |
|---|---|
| CRC | `"123456789"` = `0xCBF43926`；空数据 = 0 |
| 未擦除 | `0x34` → `0x22`；`0x31 FF01` 空镜像 → `0x22` |
| 擦除 | `71 01 FF 00`；擦除后回到可下载 |
| 0x34 参数 | `dfi≠0` / `alfid=0` / 少字节 / 长度 0 / 超上限，五个码各就各位 |
| 0x34 成功 | `74 20 00 22`、`payloadPerBlock = 34-2 = 32`、进入下载态 |
| 顺序 | 没 0x34 就 0x36 / 0x37 → `0x24` |
| BSC | 01→02 接受；重发幂等；跳到 05 → `0x73` 且不改记账；被拒后下一块仍能接 |
| 块长/总长 | 11 字节 > 通告 10 → `0x13`；超出声明总长 → `0x71`；最后短包补齐 |
| 0x37 | 只传 8/20 → `0x24`；传够 → `0x77` + CRC 与镜像实算一致；收尾后 `0x36` → `0x24` |
| 回绕 | 260 块，第 256 块必须是 `0x00`，全部接受，能正常收尾 |
| 校验 | 对 CRC → `71 01 FF 01 00`；错 CRC → `...01`（正响应）；2 字节 CRC → `0x13` |
| 重置 | 下载中途再擦除 → 允许，状态与镜像全清 |

`ctest -R doip-flash` 一秒内跑完，不需要 `vcan0`——它证明"判据不写错"，
"真的从以太网打进去、经网关、过 ISO-TP、再逐块回来"只能靠 `m15_e2e.sh` 在真 socket 上称。

### 一条命令跑完（`tools/m15_e2e.sh`）

```bash
# 网关 + 一台带 --flash 的 ECU（块长 34）
bash tools/m15_e2e.sh 13474
```

三十九项，两条腿。第一条腿走完整条链路（`tools/m15_check.py`，裸 socket）：

```
22 F1 90         → 62 F1 90 <VIN>        刷写模式没砸掉老服务
36 01 AA         → 7F 36 24              没 0x34 就传：顺序错
34 …（未擦除）    → 7F 34 22              条件不满足
31 01 FF00       → 71 01 FF 00           擦除
34 dfi=1         → 7F 34 31              参数越界
34 alfid=00      → 7F 34 31
34 少 3 字节     → 7F 34 13              长度错
34 正常          → 74 20 00 22           协商 34 字节
36 05            → 7F 36 73              跳号
36 01 <32B>      → 76 01
36 01 <32B>      → 76 01                 原样重发：幂等
36 02 <33B>      → 7F 36 13              块超长
36 02…36 04      → 76 02 … 76 04
37（只传 2/4）    → 7F 37 24              没传完
37               → 77 7D11B4C9           CRC = zlib.crc32(镜像)
31 01 FF01 错CRC  → 71 01 FF 01 01        校验失败：正响应带状态
31 01 FF01 对CRC  → 71 01 FF 01 00
31 FF00 + 重刷 8 字节 → 77 73A423E6       现场重来：擦除把状态清干净
```

第二条腿把 `--flash-block 10` 打开：同一份脚本、同一条镜像（100 字节被切成 13 块），
`0x74` 必须回 `74 20 00 0A`——**通告的块长真的在卡客户端**，不是启动行里写个好听的数字。

ECU 的退场账也要对得上：`刷写：收下 1 块，镜像 8 字节，CRC-32=0x73A423E6`
（账是"最后一次 `0x34` 起算的会话"，前一条 100 字节的已经由 `0x77` 的 CRC 证过了）。

### M15 第一遍踩的三个坑

1. **读 VIN 的 DID 写成了 `F186`**：`22 F1 86` 落到"未知 DID"分支，回了一个 4 字节的
   `62 F1 86 02`，脚本却断言 20 字节 —— 整条场景在第一步就红了。正确是 `F190`。
   教训同上一条：**先确认"我发的这条请求本来就该成功"**。
2. **把 `0x8003` 当成了诊断响应**：DoIP 里 `0x8001` 是诊断报文本身（请求和响应都用它），
   `0x8003` 是"诊断报文否定应答"。按 `0x8003` 取响应，永远取不到 —— 每个请求都白等 3 秒，
   还顺带触发了网关的心跳检查（`0x0007` / `0x0008`）。客户端必须会回心跳，否则 3 秒就被断链。
3. **退场账写成了"整场 4 块"**：账是跟着**最后一次 `0x34`** 算的（`0x34` 会清镜像），
   最后重刷的是 8 字节，所以是 1 块。断言前先想清楚"这个数是从哪一刻起算的"。

## M16：会话层（0x10 会话 + 0x27 安全访问 + S3 超时）

M15 把刷写链路跑通了，但那时这台 ECU 有个大问题：**谁连上来都能刷**。
真实的 ECU 有两道门 —— 先 `0x10` 进"编程会话"，再 `0x27` 用种子换密钥解锁。
少任何一道，`0x31/0x34/0x36/0x37` 都该被拒。

这一步第一次让"服务能不能用"取决于**之前发生过什么**，而且这个状态**会因为时间而消失**（S3）。

### 五个新东西与它们的分工

| 服务 | 名字 | 干什么 | 回什么 |
|---|---|---|---|
| `0x10 01/02/03` | DiagnosticSessionControl | 切默认 / 编程 / 扩展会话 | `50 xx 00 32 01 F4` |
| `0x27 01` | SecurityAccess（要种子） | 发一个一次性随机数 | `67 01 <4 字节 seed>` |
| `0x27 02` | SecurityAccess（交密钥） | 校验 tester 算出来的 key | `67 02` / `7F 27 35` |
| `0x3E 00` | TesterPresent | 我还在，别把会话收走 | `7E 00` |
| `0x3E 80` | TesterPresent（suppress） | 同上，但**别回包** | 不回 |

`0x50` 里那四个字节不是装饰：`P2 = 0x0032` 是 50ms（ECU 收到请求到开始回的最长时间），
`P2* = 0x01F4` 的单位是 10ms，也就是 **5000ms** —— 正好等于我们下面要讲的 S3。
诊断仪按这两个数决定"等多久算超时"，ECU 报小了就是自己在打自己的脸。

### 两道门，两个不同的码

```
默认会话        → 0x34/0x36/0x37/0x31 FF00  →  7F xx 7F   （会话不对：serviceNotSupportedInActiveSession）
编程会话但没解锁 → 同上                       →  7F xx 33   （会话对了、钥匙没插：securityAccessDenied）
编程会话 + 已解锁 → 同上                       →  正常干活
```

这两个码混起来，现场排查会彻底走偏：

- 看到 `0x7F`：客户端根本没 `0x10 02`，或者 `0x10` 被 S3 收走了；
- 看到 `0x33`：会话对了，但 `0x27` 没做、做错了、或者锁还没到期。

所以 `SessionGuard::denyFlash()` 只做这一件事，但把两个分支分开写死。

### 密钥：故意做得能手算

```
key = (seed + 0x12345678) ^ 0xA5A5A5A5        （32 位，溢出自然截断）
例：seed = 0x00000001
    0x00000001 + 0x12345678 = 0x12345679
    0x12345679 ^ 0xA5A5A5A5 = 0xB791F3DC
```

真实车厂的算法是保密的（常放在刷写包里，按 VIN/日期派生）。本项目只需要"能算、能算错、能锁"，
所以挑了两条运算：**加一个常数、再异或一个常数**。自测第一条就钉这个值：`key(0x00000001) = 0xB791F3DC`。

种子的三个规矩：

1. **每次要都不一样**（一次性），且**不为 0**——`0` 这个值专门表示"已解锁，你不用再交钥匙了"；
2. 没要种子就交密钥 → `0x24`（顺序错），不是 `0x35`；
3. 密钥长度不是 4 字节 → `0x13`（长度错）。

### 错密钥：0x35 → 0x35 → 0x36，然后锁 10 秒

| 第几次 | 回什么 | 意思 |
|---|---|---|
| 1 | `0x35` invalidKey | 还能再试 |
| 2 | `0x35` | 还能再试 |
| 3 | `0x36` exceededNumberOfAttempts | 锁 `delayMs`（本项目 10 秒） |
| 锁定期内任何 `0x27 01` | `0x37` requiredDelayNotExpired | 还剩多少毫秒写在 reason 里 |
| 锁到期后 `0x27 01` | `67 01` 新种子 | 计数清零，重新开始 |

"锁到期要清零计数"是最容易漏的一行：不清的话，锁一过就是"第 4 次错"，**立刻又锁上**，
现场看起来像"锁永远解不开"。这个坑自测里专门有一条。

### 换会话会把解锁清掉

`0x10` 不是"换个名字"，它把安全状态一起改了：**解锁只在当前会话里有效**。
所以顺序永远是"进编程会话 → 解锁 → 干活"，而不是"解锁一次，之后随便切"。

自测第 G 组就是这条：解锁 → 切扩展会话 → `unlocked=false`，且刷写依然被拒（刷写只认 `02`）。

### S3：5 秒没人理，门自己关上

- 任何一条请求都会重置 S3（不只是 `0x3E`）；
- `0x3E 80`（suppress）**也重置** —— 它本来就是为了保活才发的，不回包不等于没说话；
- 超时后：会话回默认、解锁清掉、错误计数清掉。**锁一起解开**是刻意的：否则"放着不管"成了绕过门禁的办法。

ECU 主循环每 `poll` 一拍（50ms）调一次 `tick(nowMs)`，超时打一行
`[会话] S3 超时（5000 ms 没动静）→ 回到默认会话，解锁一起清掉`。

### 为什么把 NRC 表抽成 `UdsNrc.h`

M15 的 `FlashTarget.h` 里本来有一份码常量，M16 的 `SessionGuard.h` 又要用同一批。
两个头一起被 `stub-ecu.cpp` 包含，编译器直接报：

```
error: redefinition of 'constexpr const uint8_t doip::kNrcIncorrectLength'
```

码表是**协议的一部分**，不是某个模块的私有常量 —— 所以它只有一个出处。这也是这一节唯一的结构性改动。

### 60 秒看懂门禁（`tools/m16_e2e.sh`）

```bash
bash tools/m16_e2e.sh 13475
```

三十七项，两条腿。第一条腿是主场景：

```
22 F1 90            → 62 F1 90 <VIN>     默认会话里老服务照常
34 …                → 7F 34 7F           刷写在默认会话里被拒（会话不对）
10 02               → 50 02 00 32 01 F4  进编程会话（带回 P2/P2*）
34 …                → 7F 34 33           会话对了但没解锁
31 01 FF00          → 7F 31 33           擦除也一样被挡
27 01               → 67 01 <seed>
27 02 <错 key>      → 7F 27 35           还能再试
27 02 <对 key>      → 67 02              解锁
31 01 FF00 → 71…, 34 → 74…, 36 01 → 76 01, 37 → 77 <CRC>
27 01（已解锁）      → 67 01 00 00 00 00
10 01 → 50 01, 34 → 7F 34 7F             换会话把解锁清掉
10 02 → 50 02, 34 → 7F 34 33             再进编程会话要重新解锁
3E 00               → 7E 00
（单开一条连接）3E 80 → 不回包
S3 干等 5.6 秒       → 34 → 7F 34 7F      门自己关上了
27 01 ×3 错 key      → 35 → 35 → 36       锁 10 秒

```

ECU 退场账：`会话：切换 4 次，种子 2 次，解锁成功 1 次 / 拒 4 次，锁定 1 次，S3 超时 1 次，保活 2 次`。

第二条腿是**回归腿**：不带 `--secure` 的老 ECU（M15 的 39 项跑的那个）行为必须一模一样 ——
`0x34` 直接放行，`0x10/0x27` 走"不支持"兜底（`7F 10 31`）。
门禁是新能力，不是把旧能力改红。

### M16 第一遍踩的四个坑

1. **两个头各写一份 NRC 表** → 编译期 `redefinition`。抽 `UdsNrc.h`，一个出处。
2. **测 S3 时"干等 5.6 秒"却不回心跳** → 网关 3 秒先断链，脚本在 `sendall` 上撞 `BrokenPipe`。
   测的是"网关的耐心"，不是 S3。修法：`idle()` 里继续读 socket 并回 `0x0008`。
3. **`0x3E 80` 塞在主流程里** → 网关是"一问一答"的中继，一条没有回响的请求会一直占着这条连接，
   下一条被忙拒（`0x8003 0x08`）。修法：单开一条连接验，并把这条写成边界。
4. **回归腿忘了先擦除** → `0x34` 回 `7F 34 22`，看着像"门禁没关"，其实是 M15 的前置条件没满足。

### 单元断言：748 → 809 项（新套件 `doip-session` 61 项）

| 组 | 覆盖 |
|---|---|
| 默认会话 | 0x27 → `0x7F`；`denyFlash` 也是 `0x7F` |
| 0x10 | `50 02 00 32 01 F4` 六字节；子功能 04 → `0x12` |
| 密钥公式 | `key(1) = 0xB791F3DC`；`key(0)` 与手算一致 |
| 种子 | 非 0、一次性（两次不同）、回包与内部记账一致 |
| 顺序/长度 | 没种子就交密钥 → `0x24`；3 字节密钥 → `0x13` |
| 解锁 | `67 02`；`flashAllowed()` 变 true；已解锁再要种子 → `67 01 00…` |
| 换会话 | 解锁清掉、刷写仍拒、计数 2 |
| 错密钥 | `35/35/36`、锁 10000ms、锁定期 `0x37`、到期能重新要种子且计数清零 |
| S3 | 4999 不动 / 5001 回落、解锁清掉、只报一次 |
| 0x3E | `7E 00`；`80` 空回包且重置计时；`01` → `0x12` |

`ctest -R doip-session` 不需要 `vcan0`，也不需要 `sleep` —— 因为时间是从参数传进去的。
"真的在总线上 5 秒后回落"只能靠 `m16_e2e.sh` 称。

## M17：0x11 ECUReset（硬复位 / 点火循环 / 软复位）

M16 把门装上了：进编程会话、解锁、刷完、校验通过。但刷完之后 ECU 还停在"编程会话"里，
新程序要**重启一次才生效** —— 这一步就是 `0x11`。

它和前面十六条服务的区别只有一句话：**它是唯一一条"答完就把整机状态改掉"的服务**。
顺着这条线，能看到三个以前没遇到的东西：

1. **应答和动作的先后顺序**（先回 `51 xx` 再复位，反了就永远收不到应答）；
2. **复位带走什么、留下什么**（会话、解锁、锁计数都带走；软复位留下镜像，硬复位连镜像一起带走）；
3. **什么时刻不许复位**（刷到一半按下去，等于把半截镜像当完整镜像用）。

### 三个子功能

| 子功能 | 名字 | 我们怎么处理 | 回什么 |
|---|---|---|---|
| `0x11 01` | hardReset | 断电重启：状态全清 **+ 镜像清掉** | `51 01` |
| `0x11 02` | keyOffOnReset | 等下一次点火循环（本实现立刻执行，日志里说清） | `51 02` |
| `0x11 03` | softReset | 软复位：状态全清，**镜像留着** | `51 03` |
| 其它 | — | 不认 | `7F 11 12` |
| 连子功能都没有 | — | 长度错 | `7F 11 13` |

### 关键：先回包，再动手

真实的实现里，`0x11 01` 一旦执行，ECU 的电就断了 —— 如果代码写成"先复位、后组应答"，
那条 `51 01` 永远发不出去，诊断仪只会看到超时，然后去怀疑网关、怀疑线束、怀疑人生。

所以这里把顺序做成**物理可见**的两步：

```cpp
// SessionGuard 只做"回包 + 把状态清零"，并把待执行动作挂起来
SessionReply handleEcuReset (sub, nowMs, flashInProgress);   // 返回 51 xx
std::uint8_t  takePendingReset ();                            // 非 0 = 真的要复位了

// stub-ecu 主循环：先 sendUds(...)，这一行跑完才允许取
const std::uint8_t kind = guard->takePendingReset ();
```

自测里专门有一条：`takePendingReset()` 取过一次再取必须是 `0` —— 同一个复位不会被执行两遍。

### 镜像的两套语义（这是本题的"手算"部分）

| 复位 | 会话/解锁/锁计数 | 镜像 | 擦除标记 |
|---|---|---|---|
| `03` 软复位 | 全清 | **保留**（同一份 CRC 还能校验通过） | 保留 |
| `01` 硬复位 | 全清 | **清掉**（RAM 掉电，M15 的边界在这里兑现） | 回到"未擦除" |
| `02` 点火循环 | 全清 | 清掉（等同断电） | 回到"未擦除" |

所以硬复位之后有两条路都会撞 `0x22`，但它们**不是同一件事**：

- `0x31 01 FF01` 校验 → `7F 31 22`：**没有镜像可校验**（不是校验不过，校验不过是正响应 `...01`）；
- `0x34` → `7F 34 22`：**没擦除**（得先重新 `0x31 FF00`）。

两条都写进脚本断言了。这也是为什么"0x22"这个码在刷写链路上出现了三次却意思各异：
没擦除、空镜像、刷写中途复位。

### 什么时候不许复位：0x34 之后、0x37 之前

镜像只收了一半的时候重启，等于把半截镜像当完整的用 —— 真机上这是**变砖**的经典路径。
所以 `0x11` 在这段窗口里回 `0x22`，而且**被拒之后下载不能坏**：脚本里紧接着 `0x37`，
CRC 照样对得上。这条比"回个 22"重要得多：拒绝必须是"什么都没动"，不是"拒了但已经乱了"。

### 默认会话里也允许复位

`0x27` 在默认会话里回 `0x7F`（不许做安全访问），但 `0x11` **允许**。
理由很实际：诊断仪把 ECU 弄乱了（错会话、错配置），最省事的复原手段就是"重启一下"。
如果重启本身也要先解锁，那这个复原手段就没了。

这条也在自测里正着钉住：新起的 `SessionGuard` 直接 `0x11 01` → `51 01`。

| 组 | 覆盖 |
|---|---|
| 子功能 | `51 01/02/03` 各两字节；`04` → `0x12`；被拒的不算一次复位 |
| 取用 | `takePendingReset()` 取到 01，再取是 00 |
| 默认会话 | 新起的 guard 直接 `0x11 01` → `51 01`，仍在默认会话 |
| 清状态 | 编程会话+解锁 → `0x11 03` → 默认会话、未解锁、`flashAllowed` 假、种子/计数清零 |
| 清锁 | 3 次错 → `0x36` 锁 10 秒 → `0x11 01` → 锁没了、计数 0、立刻能要种子 |
| 刷写中途 | `0x11 01`（busy）→ `0x22`，会话与解锁**都没动**、不留待执行 |
| 镜像 | 刷 8 字节 → `powerCycle()` → 镜像空、`erased` 假、`receipts` 仍是 1、再 `0x34` → `0x22` |
| S3 | 复位把活动时间重置到当下；复位不计 S3 超时；默认会话里 tick 不产生超时 |
| 记账 | 硬 2 / 点火循环 1 / 软 1 |

`ctest -R doip-reset` 同样不 sleep、不需要 vcan0。

### 这一遍的四个判断题（不是 bug，是"想清楚再写"）

1. **resetting 该不该知道 FlashTarget**：不该。`SessionGuard` 只接收一个 `flashInProgress` 布尔，
   镜像怎么清是调用方的事 —— 否则会话层就和刷写层粘在一起了。
2. **`0x11` 放哪个分支**：放 `sessionService`（会话层），不是 `flashService`。它不属于刷写，
   默认会话里也要能答。
3. **被拒的复位要不要清状态**：不清。拒绝的语义是"什么都没发生"，清一半就变成了"拒了但坏了"。
4. **`receipts` 要不要随复位清**：不清。它是终身账；"镜像 0 字节"才是现状。两个数混在一起，
   日志就会骗人。

## M18：刷写包完整性（SHA-256 + 76 字节清单 + 标签）

M15 的 `0x37` 已经带 CRC-32 了，看起来"完整性"这件事已经做完。但在安全意义上它没做完，
而且差的不是精度，是**方向**：

```
CRC 是线性的：CRC(a) ^ CRC(b) ^ CRC(c) = CRC(a^b^c)
```

意思是改掉镜像里的几个字节，再往别处补一个"补偿值"，总 CRC 照样对得上。
CRC 回答的是"传的过程有没有出错"（噪声、丢帧、位翻转），
不回答"这份镜像是不是原来那份"（有人故意换的）。

M18 加的是后者，而且分两层：**哈希管"内容"，标签管"这包是谁做的"**。

### 清单长什么样（76 字节，版本化，不猜）

| 偏移 | 内容 | 说明 |
|---|---|---|
| 0–3 | `DGIM` | magic，先确认"这是我们这套格式" |
| 4 | `0x01` | 版本 |
| 5 | `0x00` | flags（保留） |
| 6–9 | imageLen | u32 大端：镜像多少字节 |
| 10–41 | imageSha | SHA-256(镜像)，32 字节 |
| 42–43 | keyId | u16 大端：用哪把钥匙（`0x0001` / `0x0002`） |
| 44–75 | tag | SHA-256(前 44 字节 ‖ 钥匙)，32 字节 |

用 `0x31 01 FF02` 把清单送进来（routine 的 option record 就是这 76 字节）。
`FF00` 擦除、`FF01` 校验、`FF02` 验签 —— 三个例程共用一条服务，靠 routine id 分开。

### 为什么自己做 SHA-256，而不是"造个像哈希的东西"

哈希最怕的不是慢，是"差不多"。自己写的混淆跑得过自己的测试，跑不过标准向量。
所以先钉三条官方 known-answer：

```
sha256("")                      = e3b0c442…b7852b855
sha256("abc")                   = ba7816bf…f20015ad
sha256(448 位标准向量)           = 248d6a61…19db06c1       ← 跨 64 字节块边界
```

前两条只验"基本对"，第三条才验**补位与跨块**（最常写错的地方：`0x80` 之后补多少零、
长度字段写不写进计数）。再补一条工程判据：**逐字节 update、分三段 update、一次算完，
三者必须同一个摘要** —— 否则流式和一次性两条路会在某个长度上分叉。

### 标签是"MAC"，不是"签名"

这是本题最该记住的一句区分：

- **对称 MAC**（我们做的）：双方共用一把钥匙。它证明"这个包是知道钥匙的人做的"，
  但如果钥匙泄露（本项目钥匙就写在源码里），任何拿到源码的人都能做出一份合法包。
- **非对称签名**（真车厂做的）：私钥签、公钥验。拿到公钥只能验，做不出包。

所以 M18 的定位是"防顺手换包"，不是"防对手伪造"。要后者，下一步得引入非对称签名
（那是另一套东西：密钥生成、证书、吊销）。边界里写清楚了，不装作有。

### 校验顺序：先便宜后贵

```
长度 76 → magic/版本 → keyId → 标签（只看 44 字节）→ 镜像哈希（要看整包）
```

镜像可能有几兆，标签只有 44 字节。便宜的放前面，贵的放后面 —— 这不是性能优化的小技巧，
而是"单位时间里能拒掉多少坏包"的排序。

### 错的分两类：NRC 与状态 01

| 情况 | 回什么 | 为什么 |
|---|---|---|
| 清单 75 字节 | `7F 31 13` | 请求本身不合法（长度错） |
| magic 不是 DGIM | `7F 31 31` | 不是我们这个格式 |
| 版本 `0x02` | `7F 31 31` | 不认识的格式 |
| keyId `0x00FF` | `7F 31 31` | 没这把钥匙 |
| 标签不符 | `71 01 FF 02 01` | 请求合法，是包不对 |
| 长度/哈希不符 | `71 01 FF 02 01` | 同上 |
| 通过 | `71 01 FF 02 00` | |
| 没有镜像 | `7F 31 22` | 条件不满足（先 `0x34/0x36`） |

分界线是"**请求**有没有问题"：格式错是我的错（NRC）；格式对但内容对不上是你的包不对（状态 01）。
混成一个码，诊断仪就不知道"该改请求还是该换包"。

状态码只有一个字节，装不下"标签不符 / 长度不符 / 哈希不符"三种原因 —— 所以原因进日志：

```
验签：镜像哈希不符：ECU 里的 5C1A…，清单说 9D22…
验签：标签不符：这包不是知道钥匙的人做的（或者清单被改过）
验签：keyId 0x255 不认识（ECU 里没有这把钥匙）
```

### 单元断言：856 → 884 项（新套件 `doip-integrity` 28 项）

| 组 | 覆盖 |
|---|---|
| 标准向量 | 空串 / `abc` / 448 位向量三条官方值 |
| 分块等价 | 逐字节、分三段、一次算，三者同摘要；只差一个字符摘要必须不同 |
| 长度边界 | 0/1/54/55/56/63/64/65/128 字节分块与一次算全一致 |
| 清单结构 | 76 字节、magic、版本/flags、长度字段、keyId、标签公式 |
| 正例 | 一致 → `Ok` |
| 内容错 | 改镜像 1 bit → `HashMismatch`；改标签 → `BadTag`；只改长度不重盖 → `BadTag`；重盖后 → `LengthMismatch` |
| 结构错 | 75 字节 → `BadLength`；magic → `BadMagic`；版本 → `BadMagic`；keyId `0x00FF` → `UnknownKey` |
| 钥匙 | 同一镜像不同钥匙 → 清单不同、各自能过；用 1 号标签冒充 2 号 → 验不过 |
| 大镜像 | 1000 字节能过；改最后一个字节就不过 |

### 这一遍踩的坑（真的红了）

**断言"清单长度与镜像不符 → `LengthMismatch`"跑出来是 `BadTag`。**
一开始以为顺序写错了，其实是**设计在保护自己**：标签盖的是整个 44 字节头（含长度），
所以任何"没重算标签的改动"都会先撞标签，根本轮不到长度判定。
想验 `LengthMismatch` 必须模拟"签错了长度"的真实失误 —— 改完长度再用钥匙重盖一次标签。
这条已经写进自测，并且在代码注释里点明：**标签绑住整个头，所以未授权的改动第一步就死**。

### 这一遍的四个口径

1. **验签不进 `FlashTarget`**：它管镜像与刷写状态，不管"谁签的"。验签放 `FirmwareManifest.h`，
   两本账（通过/不过）留在 `stub-ecu` 里 —— 分层清楚了，FlashTarget 也不用认识钥匙表。
2. **NRC 与状态 01 的分界线是"请求有没有问题"**：格式错 NRC，内容错状态。
3. **一个字节装不下三种原因**：所以三种原因都进日志，脚本断言日志而不是只断言状态码。
4. **MAC ≠ 签名**：本项目防"顺手换包"，不防"有源码的对手" —— 这句话写在头文件、README、报告三处。

## M19：刷写前置条件检查（0x22 读身份 / 0x2E 写指纹 / 0x31 01 0203）

M16 的门回答的是"**你是谁、有没有钥匙**"。它不回答"**现在合不合适**"。
一台 11 伏的车、一个没切会话的 tester、一个正在下载中途的连接，都能拿到钥匙 —— 然后刷成砖。
M19 补的就是这一层：在 `0x34` 之前，先把"这台车现在能不能刷"判掉。

### 刷之前先回答三个问题

| 问题 | 手段 | 本项目的 DID |
| --- | --- | --- |
| 这台是不是我要刷的那台 | 读零件号 | `F187`（12 字节 ASCII） |
| 现在装的是什么版本 | 读软件版本 / 序列号 | `F188`（8 字节）、`F18C`（10 字节） |
| 电够不够 | 读电池电压 | `F1A5`（u16，**mV**，大端） |

再加上一个"这份程序是谁写进来的"：`F184` 刷写指纹（u32，4 字节）——**唯一可写的 DID**，
因为它只能在写完之后由 tester 填进去，天然属于"会改这台 ECU"的动作。

### 0x2E 的三道拦，三种不同的"不行"

`0x2E` 写 `F184` 要过三关，每一关给的是**不同的码**，因为它们该让诊断仪做不同的事：

| 拦在哪 | 回答 | 诊断仪该干什么 |
| --- | --- | --- |
| 默认会话 | `7F 2E 7F` | 先切编程会话（`0x10 02`） |
| 编程会话但没解锁 | `7F 2E 33` | 先插钥匙（`0x27`） |
| DID 是只读的（如 `F187`） | `7F 2E 31` | 换一个可写对象（找错了） |
| 数据长度不是 4 | `7F 2E 13` | 改请求长度（这才是数据错） |

写成 `6E F1 84`，并且 `0x22 F1 84` 读回来必须是刚写的那个值 ——
**跨请求保存，不是回显**。这一条自测和端到端各验一遍。

### 前置条件检查：`0x31 01 0203`

四条规则，逐条判，逐条进日志：

1. 电压 ≥ **11500 mV**（12V 系统，低于 11.5V 不刷；`≥` 不是 `>`，正好 11500 算过）；
2. 会话是 **0x02 编程会话**；
3. **已解锁**；
4. **不在下载中**（`0x34` 之后、`0x37` 之前这段）。

全过回 `71 01 02 03 00`，任何一条不过回 `71 01 02 03 01`。

**这里最容易讲错的一点**：不满足时回的是**正响应 + 状态 01**，不是 NRC。
请求本身完全合法（你就是在问"能不能刷"），答案是"不能" —— 这是一个合法的否定结论。
回 NRC 会让诊断仪以为服务用错了，去改请求；而它真正该做的是去充电或者去切会话。

日志里会把四条逐条打出来，哪条是 ✗ 一眼能看见：

```
前置条件：不满足 → 01（电压 11000 mV ≥ 11500 ✗；会话 0x02（编程） ✓；已解锁 ✓；不在下载中 ✓）
```

### 光"检查过"不够：`0x34` 自己也要看一眼电压

真实项目里刷写中途掉电是最常见的变砖原因。所以即使 tester 跳过了 `0203`，
`0x34` 在进门时也要自己判电压：不够就 `7F 34 22`（conditionsNotCorrect，**不是** `0x33`）。

到 M19 为止，`0x22` 这一个码已经背着**四种**完全不同的意思，这是这一步的核心教学点：

| 场景 | 码 | 意思 |
| --- | --- | --- |
| `0x34` 没先擦除（M15） | `7F 34 22` | 状态机顺序不对，先去 `FF00` |
| `0x31 FF01` 镜像为空（M15） | `7F 31 22` | 没有东西可校验 |
| `0x11` 刷写中途复位（M17） | `7F 11 22` | 现在不能动，会变砖 |
| `0x34` 电压不足（M19） | `7F 34 22` | 条件不满足，先去充电 |

同一个码、四种理由，所以**日志必须把理由写出来** —— 一个字节装不下这些区别，
这也是前面几步一直坚持"状态码只给结论，原因进日志"的延续。

### stub 的两个新参数

### 踩到的两个坑

1. **自测里把 `read()` 和 `hex()` 写在同一个表达式里**：`check(d.read(...) && ... "（" + hex(r) + "）")`
   求值顺序不确定，日志打出的是**上一次**的 `r`（A1 打印出空、A3 打印出 A1 的内容）。
   改成"先读进 `r`、再判、再拼日志"，一次就对了。日志错了比断言错了更麻烦 —— 断言至少会红。
2. **`answer()` 里给 `read()` 传了 `std::string()` 临时量**：`read` 收的是 `std::string&`，
   非 const 引用绑不上右值，gcc 直接报 `cannot bind non-const lvalue reference`。
   加一个局部 `readWhy` 就解决了 —— 这也是 `-Werror` 之外、编译器真正在替我们挡的一类错。

### 已知边界的补充

- 电压是 **stub 报出来的常量**，不是真的测出来的。真机上这一步要接 ADC，
  而且"电压够"只是一个瞬时判断 —— 刷写中途掉电要靠硬件欠压保护，软件挡不住。
- `F184` 的指纹写进去之后**没有回滚手段**：写错了只能再写一次。真实项目会用
  "只能写一次"的 OTP 或者带签名的记录，本项目不做。
- `0x2E` 只放开了 `F184` 一个 DID。真实 ECU 会有一整张可写表（日期、编程计数、
  匹配值），每一个都要单独定"要不要门禁"；本项目用一个 DID 把规矩立住就够了。

## M20：包与车对不对得上（`0x31 01 0204` + `0x34` 凭证）

M19 让 ECU **读得出**零件号和软件版本。读得出不等于用得上：
一台车可以老老实实报出自己的零件号，然后照样被刷进**另一台车**的程序。
M20 补的是"比对"这一层，并顺手把"检查结果"变成一张**只能用一次的凭证**。

### 一个版本号，两种比较方式

```
车上 SW-1.9.0，包里 SW-1.10.0
  按数值比：1.10.0 > 1.9.0   → 升级，放行 ✅
  按字符串比："1.10.0" < "1.9.0"（'1' < '9'）→ 降级，误拒 ❌
```

这不是理论问题：任何 `x.9.y` 升到 `x.10.y` 的版本都会踩。
所以版本必须 `parse` 成三段整数再比，自测里 A9/A10 两条就是这个对照 ——
一条验"数值上是升级"，一条同时验"字符串比较确实会说反"，免得有人改回去。

### 判定三种结论，不能混

| 情况 | 结论 | 为什么 |
| --- | --- | --- |
| 零件号不符 | 拒 | 刷错车，最严重的一类 |
| 目标版本 < 现在 | 拒（除非 `--allow-downgrade`） | 降级常常是"回退到能跑的老版本"，得有人签字 |
| 目标版本 = 现在 | **放行** | 现场最常见的"同版本重刷一遍"，是修复，不是事故 |
| 目标版本 > 现在 | 放行 | 正常升级 |

零件号优先于版本：先确认"是不是这台车"，再谈"刷哪个版本"。

### 记录格式：零件号定长，版本变长

```
0x31 01 0204 + <12 字节零件号 ASCII><1–16 字节版本 ASCII>
```

零件号 12 字节，长度抄自 `F187`；版本是**变长**的 —— `SW-1.10.0` 比 `SW-1.9.0` 多一个字节。
所以长度只判下界（≥ 13）和上界（≤ 28），不能写死 20：
写死就把两位数的段位判成"格式错"，而那正是最该放行的一次升级。

| 错在哪 | 回答 | 类别 |
| --- | --- | --- |
| 记录 11 字节（零件号都不全） | `7F 31 13` | 结构错 |
| 版本号不是三段数字（`SW-latest`） | `7F 31 31` | 结构错 |
| 零件号不符 / 降级 | `71 01 02 04 01` | 内容"对不上" |
| 通过 | `71 01 02 04 00` | 可以刷 |

结构错给 NRC（请求本身不合法），内容不符给正响应 01（请求合法、结论是否定）——
这个分工从 M18 的验签一路延续到这一步。

### 查询类例程不设门，动作类例程设门

`0203`（前置条件）和 `0204`（兼容性）都**不受门禁保护**：任何人都能来问。
理由很直白——"问"不会改变这台车，而且门禁本身也答不了"现在合不合适"：
没解锁的 tester 也会想知道"我要是解锁了，这包能不能刷"。

`0x2E`（写指纹）和 `0x34`（开始下载）就不是问问题了，它们改东西，所以都要过门。

### 凭证：检查通过 ≠ 有资格刷

`0204` 通过之后，ECU 里留下一张凭证（`policy::Gate`）。`0x34` 进门时**取走**它：

```cpp
if (ctx.requireCompat) {
    if (ctx.gate == nullptr || !ctx.gate->consumeOk()) {   // 取不到 → 22
        resp = {0x7F, 0x34, kNrcConditionsNotCorrect};
        why  = "0x34 被拒：没有有效的兼容性凭证（…）—— 先 0x31 01 0204";
        return true;
    }
}
```

三个细节都在这一步的判据里：

1. **一次一用**：`consumeOk()` 成功即作废。同一张凭证刷不了两次 ——
   否则诊断仪只要检查一次，之后的每一轮都能绕过比对。
2. **擦了就失效**：`0x31 FF00` 擦除之后 `clear()`。擦除就是"这一轮重来"，
   上一个包检查过的身份不能继续用。
3. **收尾也失效**：`0x37` 正常退出后 `clear()`；复位（`0x11` 真执行的那个）、
   换会话（`0x10`）、S3 超时也各 `clear()` 一次。**被拒的复位什么都不动**（M17 的规矩）。

于是"上周检查通过"不能用来刷今天的包 —— 这句就是凭证存在的原因。

### 两个新开关

```bash
# 要求凭证（默认关，老脚本 M15–M19 不跑 0204 也能刷）
./build/stub-ecu ... --flash --secure --require-compat

# 允许降级（默认拒）
./build/stub-ecu ... --flash --secure --require-compat --allow-downgrade
```

`--require-compat` **默认关**是这个里程碑最重要的工程决定：新能力默认关，
所有老脚本原样通过，M15–M19 的回归腿一条都不动。真机出厂应当默认打开。

### 两条腿的验收

```bash
bash tools/m20_e2e.sh 13483 13484
```

- **腿一（车 `SW-1.0.3`，不许降级）**：没检查就 `0x34` → `7F 34 22`；
  记录 11 字节 → `13`；`SW-latest` → `31`；零件号不符 → `01`；降级 `1.0.2` → `01`；
  同版本 → `00`；升级 `1.0.4` → `00` → `0x34` 放行 → 收块 → `0x37`；
  收尾后凭证作废（再 `0x34` → `22`）；重新检查 → 擦除作废 → `0x34` → `22`。
- **腿二（车 `SW-1.9.0`，`--allow-downgrade`）**：`1.10.0` 判**升级**放行（数值比较），
  `1.8.0` 降级放行且日志写明"allowDowngrade 已开"。

实测 **40 项**，`ci_local.sh` 第 24 步。

### 这一步的结构改动：参数打包成 `FlashContext`

`flashService` 原来的参数表已经长到 `(FlashTarget&, req, resp, why, batteryMv, minBatteryMv)`，
再加"要不要凭证、凭证在哪"就该换写法了：

```cpp
struct FlashContext {
    std::uint32_t batteryMv = 12400;
    std::uint32_t minBatteryMv = 11500;
    bool          requireCompat = false;
    policy::Gate *gate = nullptr;
};
```

判据是"这些参数是不是同一件事"——电压、门槛、要不要凭证、凭证在哪，
确实是同一件事：**这台车此刻允许刷写的条件**。参数超过三个时问一句这句话，比硬塞省事。

### 踩到的坑

1. **先把记录长度写死了 20**（零件号 12 + 版本 8），结果腿二的 `SW-1.10.0` 是 9 字节，
   直接撞 `0x13`，把最该放行的那次升级判成格式错。改成"零件号定长 + 版本变长（1–16）"。
   这个坑很典型：**定长的假设是从"现在的数据"里抄来的，不是从协议里来的**。
2. `m20_check.py` 里 `compat()` 一开始给版本 `ljust(8)`，对 9 字节的 `1.10.0` 是无效补齐 ——
   和上一条同源，都是"以为版本是 8 字节"。

### 单元断言：908 → 942 项（新套件 `doip-policy` 34 项）

```
A 版本：parse 形状、数值比较、字符串陷阱对照、超长数字                 13 项
B 比对：升级 / 同版本 / 降级 / 允许降级 / 零件号优先 / 版本格式错         9 项
C 凭证：未检查不给、失败不给、一次一用、clear 失效、计数                12 项
```

`ctest` 十七套件全绿，累计 **942 项**（908 + **34**）。

### 已知边界的补充

- 兼容性判据是"零件号相等 + 版本不降级"，**没有**按 VIN、按车型、按电池类型判；
  真实项目还要一张"这个零件号允许装哪些版本"的白名单。
- 目标版本是 tester 报上来的，不是从清单里读的：`0204` 与 `FF02` 两份数据之间
  **没有交叉校验**，理论上可以拿 A 包的清单配 B 包的版本号来骗过检查。
  真实现会把目标身份写进清单，让 `FF02` 一起验。**（M21 已补上：清单 v2 的身份就在标签下面。）**
- 凭证只活在 RAM：进程重启就没了（本来也该没了），但也没有"凭证过期时间"。
- `--allow-downgrade` 是整机开关，不是按包授权：开了之后任何降级都放行，日志会记下来。

## M21：把"这包是给谁做的"写进清单（`0x31 01 0205` + `FF02` 身份）

M20 留下一个洞：目标零件号和目标版本是 tester 在 `0x31 01 0204` 里**口述**的。
ECU 只能听，没法核对 —— 那么"这包是给这台车的"这句话，本质上还是**声明**，不是**证明**。

M21 要把它变成证明：身份写进清单，而且**落在标签覆盖的范围之内**。
改一个字符，标签就崩。

### 清单 v2：104 字节，身份在标签下面

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0..3 | 4 | `DGIM` magic |
| 4 | 1 | 版本 `0x02`（v1 是 `0x01`） |
| 5 | 1 | flags（保留 0） |
| 6..9 | 4 | 镜像长度 u32 大端 |
| 10..41 | 32 | SHA-256（镜像） |
| 42..43 | 2 | keyId u16 大端 |
| 44..55 | 12 | **目标零件号**（ASCII，右补空格） |
| 56..71 | 16 | **目标版本**（ASCII，右补空格） |
| 72..103 | 32 | tag = SHA-256（前 **72** 字节 ‖ 钥匙） |

前 44 字节和 v1 完全一致，身份插在中间，标签的覆盖长度从 44 变 72 —
这是"加字段"最省事、也最不容易出事的排法。

```
v1：tag = SHA-256(0..43 ‖ key)      76 字节，没有身份
v2：tag = SHA-256(0..71 ‖ key)     104 字节，身份在盖住的范围内
```

于是有两种篡改都躲不过：

- 改零件号 → 标签覆盖到它，重算不出原来的标签 → `BadTag`；
- 把 v1 的标签搬到 v2 上 → 覆盖长度不同，算的不是同一段，也对不上。

### 长度和版本必须成对

```
76  ⇄ 0x01
104 ⇄ 0x02
```

不配对（104 字节写着版本 `0x01`，或 76 字节写着 `0x02`）一律 `BadMagic` → NRC `0x31`。
这一条不是洁癖：两种长度的标签覆盖长度不同，**版本字节是"该按哪段算标签"的唯一线索**，
它和长度打架的时候就不知道该信谁了，只能拒绝。

v1 继续可用 —— 老包、老脚本一条都不动。代价是 `hasIdentity = false`，
它建立不了"已比对"的凭证。

### `checkEnvelope`：不看镜像的那一半

`verify()` 被拆成两段：

```cpp
checkEnvelope (manifest);   // 长度 / magic / 版本 / keyId / 标签 / 身份
verify (image, manifest);   // = checkEnvelope + 镜像长度 + 镜像哈希
```

为什么值得拆：**镜像还没传上来的时候也能验信封**。
预检的意义就是"在把 8 KB 镜像推上去之前，先知道这包是不是给我的"——
等镜像传完再告诉人家"这包不是给你的"，白折腾一轮。

### `0x31 01 0205`：预检，通过即发凭证

```
0x31 01 0205 + <整份清单，104 字节>
```

| 情况 | 回答 | 类别 |
| --- | --- | --- |
| 收到 v1（76 字节） | `7F 31 31` | 只收带身份的 v2 |
| 100 字节之类 | `7F 31 13` | 结构错 |
| 版本与长度不配对 / 标签不符 | `7F 31 31` | 结构错（包不是我们这个格式） |
| 信封对、身份不符 | `71 01 02 05 01` | 包不对（内容层面） |
| 全部通过 | `71 01 02 05 00` + 发凭证 | 可以刷 |

过的那条直接把 `policy::Gate` 置为通过，`0x34` 拿着 `--require-compat` 来 `consumeOk()`
取走 —— 一次一用，M20 的规矩一点没动。

**失败的预检会 `clear()` 凭证**，这一点是刻意的：
前一条包通过了、后一条包不通过，前一次的"通过"必须作废。
否则诊断仪可以先发一个对的包把凭证拿到手，再换一个错的包下载 —— 检查就白做了。

### `FF02` 的三态：包真 ≠ 给这台车

整包验签（`0x31 01 FF02`）现在多了一档：

| 状态 | 含义 |
| --- | --- |
| `00` | 包是真的，身份也对（或是 v1，没有身份可比） |
| `01` | 包不对：标签 / 长度 / 哈希对不上 |
| **`02`** | **包是真的，但不是给这台车的** |

`02` 是这一步新增的状态码，理由很实际：`01` 和 `02` 的处置完全不同 ——
`01` 是"这包坏了/被改过，去找供应商"；`02` 是"包是好的，你拿错车了"。
一个状态码糊住这两件事，现场就会去查错方向。

FF02 **不发凭证**：它是事后核对，不是门口放行。凭证只在门口（`0204` / `0205`）发。

### `0205` 与 `0204` 对"版本号写错"回答不同，是故意的

同样是包里版本写成 `SW-latest`：

- `0204` → `7F 31 31`：那是 tester 在**请求里**报的，请求本身不合法；
- `0205` → `71 01 02 05 01`：那是**签过名的包内容**，包是合法的请求，只是包有问题。

判断依据是"这个坏数据是谁给的"：请求里给的 → NRC；包里带的 → 正响应 + 状态。

### 两条腿的验收

```bash

```

- **腿一（车 `PART-ABC1234` / `SW-1.0.3`，不许降级）**：v1 → `31`；104 字节写版本 1 → `31`；
  100 字节 → `13`；2 号钥匙盖章 → `31`；零件号不符 → `01`（且 `0x34` 仍 `22`）；

## 已知边界（M0 – M21）

- ~~载荷类型 0x4001-0x4004 只认得名字、不解析~~ → M14 已实现（0x4002 只发 7 字节长式，收侧 3 / 7 字节都认）。
- 不做 TLS。~~不做 CAN FD~~ → M9 已支持（经典帧与 FD 帧可在同一张路由表里并存）。
- `parseMessage` 是单条解析；粘包靠调用方循环 `pos += consumed`（M0 的测试里验证过这个循环）。
- 发现层不做定时主动广播（真实实体会周期性喊"我在"）；`buildAnnouncement` 已就绪，接定时器是一行的事。
- 虚拟机的 NAT 环境下 `255.255.255.255` 广播不一定通，端到端一直用 loopback 单播验逻辑。
- TCP 服务器是**单线程 poll**。连接数上限默认 4；M4 做多客户端互斥时会重新审视这个模型
  （要么继续单线程排队，要么每连接一线程 + 互斥表）。
- `0x0001`/`0x0002`/`0x0003` 出现在 TCP 上会被当成"不处理"记日志 —— 发现报文只走 UDP。
- M3 的下游是**假 ECU**，答 3E 00 / 22 F1 86，其余 `7F xx 31`；真链路是 M4 的事。
- 一条 `0x8001` 在同一时刻只对应一条请求，没有并发排队（M4 多客户端时再谈互斥）。
- 未激活连接发 `0x8001`：回 `0x8003 0x02` 后断开，不是"回了码还能接着用"。
- 载荷不足 4 字节的 `0x8001`：回 `0x0000 0x04` 并断开（连 SA/TA 都读不出，流已不可信）。
- ~~M4 只桥**一个 ECU**（固定 7E0/7E8）~~ → M6 起改为**静态路由表**，`--route TA:TX:RX[:名]` 决定每条通道。
  表在启动时定型，**不支持运行期增删**（真实网关可以从诊断配置里改表，本项目不做）。
- 路由表只支持 **1 个 TA ↔ 1 对 ID**：一个 TA 不能挂多条并行通道，也不能多个 TA 共用一对 ID（`add()` 直接拒绝）。
- 不支持 CAN FD（FD 的 SF 能装 62 字节，逻辑不一样）；M7 只做 11 位 / 29 位**经典帧**，两种宽度都只走物理寻址。
- ~~不支持功能寻址（`7DF` 一发多收）~~ → M8 已支持物理 + 功能两种寻址；功能的语义边界见文末。
- 流控只按 BS 简单处理；STmin 用 `sleep` 实现，没有做高精度定时。
- ~~并发策略是"一把锁串行"，没有做优先级或超时抢占~~ → M10 已改成"每通道一条队列 + 一条线程"；
  但仍**没有优先级、没有抢占、没有公平性**（FIFO 到底）。
- M5 的"迟到帧"处理是**清仓 + 跳过**，够用但不是多 tester 隔离：真实网关会给每个 tester
  分配独立的 DoIP 逻辑地址并做通道映射（甚至独占总线），本项目是"共享总线 + 串行化"的简化模型。
- 路由激活请求接收侧 7/11 字节都认（互通性），但**没做 vm_specific 语义**（OEM 字段读到就丢）。
- 反向发现（实体主动周期性 0x0004 广播）仍未接定时器；`buildAnnouncement()` 已就绪。
- 路由表是**静态配置**：`--route` 只在启动时读，运行期改不了，也没有从 UDP 发现/诊断配置里拉表。
- 地址"不认识"只回 `0x8003 0x03`，**不给候选**（真实网关有时会回一段支持的地址列表，本项目不做）。
- 一个 TA 只有一条通道；**同一 ECU 挂两个 TA（比如网关后面还有一个子网关）不支持**。
- M6 的两台 ECU 都是我们自己写的：项目一 `uds-demo`（`7E0/7E8`）+ `stub-ecu`（`7A0/7A8`）。
  没有在真实多节点总线上验过总线负载、也没有验过两个 ECU 同时回多帧的碰撞场景
  （现在的做法是"一把锁串行 + 通道之间排队"，逻辑上不会撞，但没在 1 Mbps、高负载下称过时间）。

- M7 只覆盖 ISO-TP **物理寻址**的两对 ID（`7E0/7E8` 与 `18DA00F1/18DAF100`）；
  29 位下的功能寻址写法（`18DB33F1` 那类）没做，功能寻址整体留给 M8。
- `--route` 的 ID 仍按整数给（`18DA00F1`），`formatCanId` 只负责打印，不做入参解析。
- 一条路由仍只对应一对 ID，**同一个 TA 不能一半 11 位一半 29 位**（表结构没变，M7 只放开宽度上限）。
- 没有在真实 1 Mbps 总线上量过"标准帧与扩展帧交织时的总线负载/仲裁延迟"，vcan0 不模拟仲裁。
- M8 的端到端只跑 **11 位广播 `7DF`**；29 位广播 `0x18DB33F1` 能进功能表（有单测），但没在总线上跑过。
- 功能应答是**串行轮询每条通道**收的（每通道一个固定窗口 150ms），不是事件驱动；
  ECU 比窗口慢就按"没答"处理——真实网关会给每条通道独立的接收线程。
- 功能寻址下只接受**单帧响应**；收到首帧/连续帧会跳过并计 `funcMultiSkip`（协议上不该出现，但拦不住别人乱发）。
- 一个 `0x8001` 只对应**一次** CAN 广播，不做"一条 DoIP 请求分发到多张网卡/多路 CAN"。
- `0x8003` 的码用点：请求超过 7 字节 → `0x04`，广播出去无人应答 → `0x06`，功能地址不在表里 → `0x03`。
- 没做"功能请求的应答去重/顺序保证"：多条应答按通道顺序发出，不按到达时间。
  → M11 在**客户端侧**补上了按 SA 归档与去重；网关侧仍是"按通道顺序发"，没有到达序保证。

- M9 的 FD 只做**固定 64 字节**（`frameBytes=64`），不支持 8/12/16/20/24/32/48 那些短 FD 帧；
  真实 FD 网络常常按 DLC 变长，本项目为了"单帧边界讲清楚"把帧长钉死。
- FD 下也不发 `BRS`（只置了 flags，没有配波特率切换），所以数据段速率等于仲裁段速率；
  真实 FD 网关会按报文配 BRS 与数据段波特率，本项目不碰位定时。
- 一张路由表里 FD/经典混挂，但**同一条总线只有一个 `--iface`**；真实网关是"多路 CAN 各走各的"。
- 转义单帧的长度字节写死在 8..62 区间；对端如果发"转义单帧声称 >62"会被装配器拒（有单测），
  但**收侧不校验"FD 帧真实长度 ≤ 64"**（内核已经挡了一层）。
- FD 的 `0xF1A1`（103 字节）只进了 `stub-ecu`，端到端脚本没验这一档（104 字节级的两帧边界
  由 0xF1A2 / 0xF1A0 两端夹住了）。
- `candump -L` 的 FD 格式（`##` + 一位 flags）只在 Ubuntu 22.04 的 can-utils 上核过；
  别的版本 flags 位数不同时，`m9_e2e.sh` 里那条 `awk` 会数错——它是**取证脚本**，不参与通过/失败判定
  之外的第 2 步断言，改版时留意。

- M10 的队列容量是**写死的 8**（`JobQueue{8}`），没有按通道配、没有背压（满了就是 `0x8003 0x08`）。
- "每条通道一条线程"意味着**线程数 = 通道数**，没有线程池；80 条通道就是 80 条线程，
  这个规模在真网关（几路 CAN）够用，但不是"可扩展到几百条"的设计。
- 一条连接**同一时刻只许一条在途**：再发第二条当场 `0x8003 0x08`。没有流水线（DoIP 本身也没有请求/响应配对字段）。
- 作废的结果**不重试、不缓存、不进任何队列**，直接丢；`abandoned_` 只是计数，
  真实网关会把它记成诊断日志或回一条"请求已作废"给上层。
- 广播仍然**独占所有通道**（`lockAllBuses` 按 TA 升序），期间物理请求在各队列里排队；
  没有做"只锁目标通道"的细粒度广播。
- 排队时长用 `CAS` 记最大值（`maxQueueWaitMs`），只用于观感，**不参与任何超时判断**。
- vcan0 不模拟总线仲裁与负载，所以"排队 62ms""快通道 143ms"是**本地量**，
  不能当 1 Mbps 真总线的指标用。
- M10 只验了**三台 ECU / 最多 3 个并发 tester**；没有在"几十个 tester 同时打同一台 ECU"
  的规模上量过队列满 / 忙拒的比例。

- M11 的"收齐"是**客户端自己拍的静默窗口**，不是协议保证：DoIP 的 `0x8001` 没有批次结束字段。
  窗口给小了整批都可能收不到（第 5 步就是这么验的），给大了每条请求都要多等一窗。
  真实诊断仪用 UDS 的 `P2*`，本质相同但有时限来源。
- ~~网关仍然是攒批交回~~ → M12 起默认**流式交付**（收一条转一条）；`--no-stream` 可以退回 M11 的攒批行为做 A/B 对照。
- 功能寻址下 ECU 只能**单帧答**（M8 的边界），所以 VIN 这类长 DID 在广播上永远没有答案：
  M11 验的是 `22 F1 91`（6 字节）。要读 VIN 只能物理寻址，一条一条来。
- `duplicates` / `changes` 只计数，不保存"改口后的第二份正文"；要查"它到底改成什么"
  目前得自己加字段。
- 客户端不做"超时后重发"：窗口到点就收工，宁可少收也不重发（重发会把功能寻址变成
  "N 台 ECU 各答两遍"，需要另一套去重语义）。
- M12 的流式答案**按到达顺序**发，不做重排：慢的那台晚到，就真的排在后面（诊断仪侧靠 `SA` 归档，不靠顺序）。
- 流式发出去之后如果那条连接断了，这些答案**只记账（`流式时连接已断 M 条`）、不重发**：
  下一位 tester 拿不到别人的答案，符合 M10 的"宁可丢，不可错配"。
- 交卷差额依赖"收/发同序"这个前提：流式发的是 `replies` 的前 k 条，`deliver()` 就从第 k 条接着发。
  如果以后引入乱序/并发交卷，这本账要跟着改。
- 客户端仍然**不做超时重发**：`--trace` 只测量，不改变 M11 的收工语义（静默窗口到点就收工）。
- `--no-stream` 只是 A/B 对照开关，不保证在别的方面与 M11 逐字节一致（日志与账目都会不同）。
- 地址仲裁只做"查重 + 限流"，**不做地址分配**：ISO 13400 里 tester 的地址是 tester 自己选的（0x0E00–0x0FFF），
  实体发号是厂商扩展，本项目不做。
- 0x03 / 0x01 的判定是**实体级**的；同一 SA 在不同**接口**上激活（标准允许，见 6.2 的多接口场景）本项目只有一条 TCP，
  所以没有"按接口分别判"的逻辑。
- 名额满时**不排队**：拿 0x01 的 tester 只能自己重试，网关不会替它占位、也不会通知它"有空位了"。
- 释放只在 `dropConn` 一处发生；异常退出（进程被杀）不会有"残留地址"，因为没有持久化。
- 连接上限 8 / 激活上限 4 都是**写死的默认值**，只有 `TcpServerConfig` 能改；命令行没暴露 `--max-testers`。
- 仲裁只看 SA，不看"这台 tester 是不是真的那台"：没有证书、没有绑定 IP/MAC，地址仍是自报的。

- 0x4002 我们只**发 7 字节长式**（带 max data size）；3 字节短式只认不收 —— 收侧两种都解，
  发侧固定长式，因为"少发 4 字节"在一个无版本协商的字段上只会让对面猜。
- `cur open sockets` 数的是"accept 之后仍然开着的 TCP_DATA socket"，**不含正在三次握手的那条**；
  它由 UDP 线程读原子量得到，快照可能正好差一条（那一刻有人连上/断开），这是刻意的取舍：
  宁可差一条，不要跨线程遍历别人的容器。
- 0x4001 / 0x4003 只走 UDP：TCP 上收到**只记账、不回答、不断开**；带载荷的请求在 UDP 上**沉默**
  （UDP 上不造 NACK）。只做发现、没接 `entityStatus` 回调的实体沉默也是合规的（这是可选特性）。
- `max data size` 我们填 4096，等于 `parseMessage` 里真正卡的那个 `maxPayload`（**不含 8 字节头**）。
  ISO 的文字是"能处理的最大报文大小"，各实现对"含不含头"理解不一致，互通时以实测为准：
  超过就会被 NACK 0x02，那个数才是真的。
- 电源模式是**启动时的静态配置**（`--power-mode 0|1|2`），不随 CAN 侧实际状态变。
  真实实体是去问子网上的 ECU 能不能诊断，再合成一个结论；本项目没有那条"探测"链路。
- `node type` 写死 `0x00`（网关）。没有多接口场景（一边 TCP、一边子网关），所以也没有
  "按接口分别报"这回事。
- 不做 2019 版新增的 0x4005 / 0x4006（实体状态扩展），也不做周期性主动广播 0x4002。
- 没有 TLS 下的实体状态差异（secure DoIP 另有一套要求），TLS 整体不做。
- `doip-serve` 只开 TCP，所以它收到 0x4001/0x4003 只会记账、不可能回答；要真答得用 `doip-gateway`。

- M15 的"擦除"是**把内存镜像清零**，不是真的操作 Flash：没有扇区、没有擦除时间、没有坏块，
  也没有"擦一半掉电"这种半擦状态。真 ECU 的擦除动辄几十毫秒到几秒，`0x31` 的 `P2*` 要跟着改。
- 镜像只在 ECU 的内存里，**掉电即失**，也没有"读回来比对"的例程（真实的 `0x31 FF01` 常常是
  ECU 自己算 CRC，而不是 tester 送上来）。
- BSC 按"从 0x01 起、`0xFF`→`0x00` 回绕"实现。有的 OEM 是 `0xFF`→`0x01`（`0x00` 非法），
  互通时要确认对上，本项目的自测里只钉了我们这一种。
- 只看 BSC 判"重发/跳号"，**不做内容哈希**：同一个 BSC 换了数据重发，我们也当幂等收下
  （真实现会拒或记异常）。要防这件事，得在 `0x37` 的 CRC 上兜底（内容变了 CRC 就对不上）。
- 没有 `0x36` 的"块级暂停/恢复"（`0x71` 只作为"超总长"的拒绝码出现），也没有 `maxNumberOfBlockLength`
  的**动态重协商**（真实刷写会在第一块后按实测吞吐调块长）。
- `0x34` 的 `alfid` 高/低半字节只支持 1–4 字节（`0x44` 是四字节地址 + 四字节长度）；
  8 字节地址（64 位）与 1 字节长度这类组合没做。
- `0x34` 只保留**最后一次**声明的长度与地址：中途再发 `0x34` 会把镜像清掉重来，
  不支持"一条会话里刷多段"。
- 刷写只走**物理寻址**：广播（`7DF`）上的 `0x31/0x34/0x36/0x37` 一律不处理（`flashService` 只被物理路径调用），
  真实产线也是一台一台刷。
- ~~没有前置的 `0x10` 会话切换与 `0x27` 安全访问~~ → M16 已补（`--secure` 打开门禁）。但默认**是关的**：
  不带 `--secure` 的 ECU 仍是"谁都能刷"，这是为了守住 M15 的 39 项回归；真机行为应当默认开门禁，
  本项目把开关留给脚本，好让两条腿都跑。
- `flash-selftest` 不验时间：没有 `P2` 超时、没有擦除耗时、没有块间最小间隔（STmin 由 ISO-TP 层管）。
- 刷写链路的端到端只在 vcan0 上跑过，**没有在真实 1 Mbps 总线上量过 100 块的耗时**
  （块变多、帧变多，瓶颈会从"判据"挪到"总线"）。

- M16 的"种子"是**确定性混淆**（`0x9E3779B9 ^ (++counter * 0x85EBCA6B)` 再两轮 xor-shift），
  不是密码学随机：目的是"每次不同、非零、脚本可复现"。真实现用硬件 RNG，且种子要能被 ECU 自己反推校验。
- 密钥公式 `(seed + 0x12345678) ^ 0xA5A5A5A5` 是**教学用的明文算法**，写在代码里、能手算。
  真实 OEM 的算法在刷写包里、按 VIN/日期派生，双方都不公开；本项目一公开就失去"防刷"意义 ——
  它防的是"手滑"，不是"有意"。
- 解锁状态只挂在**会话**上：`0x10` 一切换就清；S3 一超时也清。没有"按安全等级分档"
  （真实的 `0x27` 有多个 level，`27 01/02` 只是第一档，`27 03/04` 是另一档，本项目只做一档）。
- 锁定期是**固定 10000ms**（真实实现常随失败次数递增，第二次锁更久），也不落盘：
  进程重启就归零。
- `0x3E 80`（suppress）**只做"不回包 + 重置 S3"**，没有做"N 条请求合并一条应答"的抑制策略；
  而且因为网关是"一问一答"中继，一条没有回响的请求会让这条连接"看起来还在忙"，
  所以在 `m16_e2e.sh` 里它被单独放在一条连接上验（见下一条）。
- **网关一问一答**这条约束在 M16 被第一次踩到：`0x3E 80` 不回包，网关就认为"还有一条在途"，
  下一条请求当场 `0x8003 0x08`。真实网关靠 P2 计时器超时释放，本项目没有那条计时器。
- 会话层状态是**每台 ECU 自己一份**（`stub-ecu` 进程内的 `SessionGuard`），网关完全不知道谁解锁了谁 ——
  这是分层的正确结果，但也意味着"网关侧没法做统一的刷写权限审批"。
- S3 的 5000ms 写在 `SessionGuard` 里，`0x10` 应答里的 `P2*` 也是 5000ms，两处手抄；
  改一处忘了另一处，诊断仪就会"按 ECU 自己说的时限超时"。真实实现从同一常量派生。
- M17 的 `02`（keyOffOnReset）在本实现里**立刻执行**，没有"等下一次点火"的挂起态：
  真机要等 KL15 动作，本项目没有点火信号可等。
- 复位是**软件模拟**：没有真正的进程重启、没有冷启动自检、没有启动耗时；`receipts`（收块终身账）
  不随复位清，"镜像 0 字节"才是现状，两个数在退场账里并排印出来就是为了不让人混。
- 硬复位会让真机的连接断开（ECU 掉电）；本项目里"重启"的是 ECU 的状态机，网关连接照旧 ——
  所以脚本能在同一条连接上继续验"复位后 0x34 又回 0x22"。
- 锁计数全在 RAM，三种复位都清。真机常把锁计数存 NVM，`03` 软复位不该清锁 ——
  我们的"断电清锁"只在 `01/02` 上是对的。
- 没有 `0x11` 的 `powerDownTime` 附加参数（ISO 里硬复位允许带，本项目不收）。
- 复位没有"复位后主动通知"（真 ECU 会重建连接、重发路由激活），这一步没有对应链路。
- M18 的标签是**对称 MAC**（钥匙写在源码里），只能防"顺手换包"，不防"拿到源码的对手"：
  真要防伪造得用非对称签名（私钥签、公钥验），本项目不做 —— 那一套要密钥生成、证书、吊销。
- 清单固定 76 字节、版本 `0x01`；没有"多段镜像各带一份清单"，也没有清单的清单（多级哈希树）。
- 钥匙只有 `0x0001` / `0x0002` 两把演示钥匙，`key = SHA-256("doip-gw demo key <id>")`；
  真项目里钥匙在刷写包与 ECU 的 NVM 里，不在源码里。
- 验签只验"包与镜像是一对"和"包是知道钥匙的人做的"：**不验"这个包该不该刷"**
  （版本降级、零件号不匹配、VIN 不符这些策略判断都没做）。
- 状态码只有 `00/01` 一个字节，装不下"标签/长度/哈希"三种原因，原因只进日志；
  所以脚本断言的是日志文本，不是靠状态码区分。
- SHA-256 是软件实现：没有看门狗、没有耗时上限；真实现常带硬件加速，验签耗时会计入 `P2*`。
- 没有签名方案可选、没有公钥证书链、没有"验不过就自动回滚"的机制。

- M19 的电压是 **stub 报出来的常量**，不是真的测出来的：真机要接 ADC，而且"电压够"只是一个瞬时判断 ——
  刷写中途掉电得靠硬件欠压保护，软件这一层挡不住。
- `F184` 写进去之后**没有回滚手段**，写错只能再写一次；真项目会用只能写一次的 OTP 或带签名的记录。
- `0x2E` 只放开了 `F184` 一个 DID。真 ECU 有一整张可写表（日期、编程计数、匹配值），
  每一个都要单独定"要不要门禁"；这一步只用一个 DID 把规矩立住。
- 前置条件检查是**一次性的快照**：`0203` 回 `00` 之后电压掉了，`0x34` 仍会自己再判一次，
  但 `0x36` 期间不会再判 —— "条件在变，判据只在门口"是这一层的固有边界。

- M20 的兼容性判据只有"零件号相等 + 版本不降级"，**没有**按 VIN / 车型 / 电池类型判；
  真实项目还要一张"这个零件号允许装哪些版本"的白名单。
- 目标版本是 tester 报上来的（`0204` 的记录），**不是**从清单里读的：`0204` 与 `FF02`
  两份数据之间没有交叉校验，理论上可以拿 A 包的清单配 B 包的版本号骗过检查。
  真实现会把目标身份写进清单，让 `FF02` 一起验。**（M21 已补上：清单 v2 的身份就在标签下面。）**
- 凭证只活在 RAM（进程重启就没了，本来也该没了），但**没有过期时间**，
  也没有"按包授权"：`--allow-downgrade` 是整机开关，开了之后任何降级都放行（日志会记）。
- `0204` 的记录是"零件号定长 12 + 版本变长 1–16"，版本上限 16 字节是拍的，没有按 OEM 规范核过。
- 身份 DID 全是**常量字符串**（`--part-no` / `--sw-version` / `--serial` 传进来），没有"从 Flash 里读出来"
  这一层。（"零件号不符就拒刷"已在 M20 补上，见下面 M20 的边界。）
- M21 的清单身份是"零件号 + 版本"两段定长 ASCII，**没有** VIN / 车型 / 电池类型；
  要按 VIN 判，就得把 VIN 也放进清单（字段还能加，代价是再来一版 v3，标签覆盖长度又变一次）。
- 标签仍是**对称 MAC**：它证明"这包是知道钥匙的人做的"，**不能**证明"是厂商做的"；
  要防厂商内部伪造，得换非对称签名（私钥签、公钥验），那是另一套钥匙管理。
- v1 包永远没有身份：`FF02` 对它只能回答"包真"，"给谁"还得靠 `0204` / `0205` 口述。
  兼容老包换来的就是这个缺口 —— 想彻底关掉，得让 `--require-compat` 默认开、并拒收 v1。
- `0205` 的预检结论**不保鲜**：信封验过就不再验，镜像推上去的过程中清单内容可能已经变了。
  所以 `FF02` 必须跑 —— 它验的是"镜像和清单还是不是一对"。
- 清单只有 1 / 2 两档版本，`flags` 字节留着但**没有定义任何语义**（现在写死 0，非 0 直接 `BadMagic`）。
