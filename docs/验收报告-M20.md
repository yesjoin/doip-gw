# M20 验收报告 —— 包与车对不对得上（0x31 01 0204 + 0x34 凭证）

## 1. 目标

M19 让 ECU 读得出零件号和软件版本。读得出不等于用得上：
一台车可以老老实实报出自己的零件号，然后照样被刷进另一台车的程序。

M20 补比对这一层，并顺手把"检查结果"变成一张只能用一次的凭证：

- **比**（`0x31 01 0204`）：tester 报"目标零件号 + 目标版本"，ECU 拿自己的 `F187` / `F188` 比；
- **凭证**（`policy::Gate`）：通过之后留一张凭证，`0x34` 取走即作废；
- **一次一用**：擦除 / 复位 / 换会话 / S3 超时 / 收尾，五个点各自作废。

## 2. 复现

```bash
cd ~/doip-gw
cmake --build build -j4
./build/policy-selftest                 # 34 项，纯内存，不需要 vcan0
bash tools/m20_e2e.sh 13483 13484       # 四十项，约 40 秒（两条腿）
bash tools/ci_local.sh gcc              # 24 步 37 项
```

依赖：`vcan0`、`build/stub-ecu`、`python3`。

## 3. 版本必须按数值比

```
车上 SW-1.9.0，包里 SW-1.10.0
  数值：1.10.0 > 1.9.0        → 升级，放行
  字符串："1.10.0" < "1.9.0"  → 降级，误拒
```

自测里 A9 / A10 两条就是这个对照：一条验"数值上是升级"，一条同时验
"字符串比较确实会说反"，免得以后有人把实现改回字符串比较。

`parse` 只认"三段十进制、允许非数字前缀"，`SW-1.0`（两段）、`SW-1.0.3.4`（四段）、
`SW-a.b.c`（字母）一律 invalid → 归到结构错（NRC 0x31）。

## 4. 三种结论

| 情况 | 结论 | 理由 |
|---|---|---|
| 零件号不符 | 拒 | 刷错车，最严重 |
| 目标版本 < 现在 | 拒（除非 `--allow-downgrade`） | 降级要有人签字 |
| 目标版本 = 现在 | **放行** | "同版本重刷一遍"是修复，现场最常见 |
| 目标版本 > 现在 | 放行 | 正常升级 |

零件号先判、版本后判：先确认"是不是这台车"，再谈"刷哪个版本"。

## 5. 记录格式：零件号定长，版本变长

```
0x31 01 0204 + <12 字节零件号><1–16 字节版本>
```

零件号 12 字节抄自 `F187`；版本**变长**（`SW-1.10.0` 比 `SW-1.9.0` 多一字节），
所以长度只判 13–28，不能写死 20。

| 错在哪 | 回答 | 类别 |
|---|---|---|
| 记录 11 字节 | `7F 31 13` | 结构错 |
| 版本号不是三段数字 | `7F 31 31` | 结构错 |
| 零件号不符 / 降级 | `71 01 02 04 01` | 内容对不上 |
| 通过 | `71 01 02 04 00` | 可以刷 |

## 6. 查询不设门，动作设门

`0203`（前置条件）和 `0204`（兼容性）都**不受门禁保护**：任何人都能问。
问不会改变这台车；而且没解锁的 tester 也想知道"我要是解锁了，这包能不能刷"。

`0x2E`（写指纹）和 `0x34`（开始下载）改东西，所以都要过门。

## 7. 凭证：检查通过 ≠ 有资格刷

`0x34` 进门时取凭证：

```cpp
if (ctx.requireCompat) {
    if (ctx.gate == nullptr || !ctx.gate->consumeOk()) {
        resp = {0x7F, 0x34, kNrcConditionsNotCorrect};
        why  = "0x34 被拒：没有有效的兼容性凭证（…）—— 先 0x31 01 0204";
        return true;
    }
}
```

五个作废点：`consumeOk()`（一次一用）、`FF00` 擦除、`0x37` 收尾、
真执行的 `0x11` 复位、`0x10` 换会话 / S3 超时。
**被拒的复位什么都不动**（M17 定的规矩）。

## 9. 结构改动：参数打包成 `FlashContext`

参数表长到 `(FlashTarget&, req, resp, why, batteryMv, minBatteryMv)` 之后再加两项就该换写法：

```cpp
struct FlashContext {
    std::uint32_t batteryMv = 12400;
    std::uint32_t minBatteryMv = 11500;
    bool          requireCompat = false;
    policy::Gate *gate = nullptr;
};
```

判据是"这些参数是不是同一件事"：它们确实是同一件事 —— 这台车此刻允许刷写的条件。

## 10. 踩到的坑

1. **记录长度写死 20**（零件号 12 + 版本 8）：腿二的 `SW-1.10.0` 是 9 字节，直接撞 `0x13`，
   把最该放行的那次升级判成格式错。改成"零件号定长 + 版本变长 1–16"。
   这个坑的教训是：**定长的假设来自"现在的数据"，不是来自协议**。
2. `m20_check.py` 里 `compat()` 一开始给版本 `ljust(8)` —— 与上一条同源，都是以为版本 8 字节。

## 11. 单元断言：908 → 942 项（新套件 `doip-policy` 34 项）

```
A 版本：parse 形状、数值比较、字符串陷阱对照、超长数字            13 项
B 比对：升级/同版本/降级/允许降级/零件号优先/版本格式错            9 项
C 凭证：未检查不给、失败不给、一次一用、clear 失效、计数           12 项
```

`ctest` 十七套件全绿，累计 **942 项**（94/57/72/73/96/100/29/45/27/43/58/54/61/47/28/24/**34**）。

## 12. 边界

- 判据只有"零件号相等 + 版本不降级"，没有按 VIN / 车型 / 电池类型的白名单。
- 目标版本由 tester 在 `0204` 里报，不是从清单读；`0204` 与 `FF02` **无交叉校验**，
  理论上可以用 A 包的清单配 B 包的版本号骗过检查。真实现把身份写进清单、由 `FF02` 一起验。
- 凭证只在 RAM，没有过期时间；`--allow-downgrade` 是整机开关，不是按包授权。
- `0204` 版本上限 16 字节是拍的，没有按 OEM 规范核过。
- `--require-compat` 默认关：老脚本（M15–M19）不跑 0204 也能刷，这是为了守住既有回归腿。
