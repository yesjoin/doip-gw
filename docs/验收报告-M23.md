# M23 验收报告 —— 让钥匙表活过一次重启（KeyRingStore + --key-store）

## 1. 目标

M22 的钥匙表在 RAM 里：进程重启就回到"1、2 号都启用"。对真车这是**事故级**的 ——
现场刚把泄露的 1 号钥匙吊销，断电重启后它又活了。**吊销记录不能丢，"吊销"才成立。**

M23 只干一件事：把 `keys::KeyRing` 存到盘上、从盘上读回来。难点不在写，在**读坏了怎么办**：

| 载入结论 | 什么时候 | 处理 |
|---|---|---|
| `Ok` | 读懂了 | 就按文件来 |
| `Missing` | 文件不存在 | 第一次上电：铺默认两把并写盘 |
| `Corrupt` | 文件在、读不懂 | **空表**（谁都验不过），绝不套默认两把 |

`Missing` 与 `Corrupt` 分开，是因为"把读坏了当成没有文件"等于**把吊销的钥匙复活**。
宁可谁都不认，也不猜；恢复只能靠人明确 `--reset-key-store`。

## 3. 文件格式

```
DOIPKEYRING 1
K 0001 00 <64 hex>
K 0002 02 <64 hex>
SUM 3f7c1a0e5b2d9c48
```

| 设计 | 理由 |
|---|---|
| 文本而不是二进制 | 现场 `cat` 一眼能看；省下的字节在这个场景没有收益 |
| 每把一行、状态一个字节 | 与 `0x22 F1B0` 报出去的 `00/01/02` 完全同一套编码 |
| 末尾一行校验和 | 对 `SUM` 之前全部内容取 SHA-256 前 16 hex；只为抓"半截 / 被手改" |
| 先验校验和，再验内容 | 校验和只证明字节没变，证明不了"id 非 0 / 状态 ≤ 2 / 不重复 / ≤ 8 把" |

## 4. 写入：临时文件 → rename → 读回来

```cpp
写 path.tmp → rename(tmp, path) → load(path) 与 encode(ring) 比一遍
```

- **rename 原子**：同一文件系统内，要么看到旧文件、要么看到新文件，看不到半截；直接覆盖写没有这个保证。
- **读回核对**：写成功不等于写对了（磁盘满、路径被换、编码截断都可能）。
- **rename 失败时旧文件保持原样**：这种时候宁可留旧表，不毁新表。

## 5. 写不进盘就不算改成功

```cpp
const keys::KeyRing before = ring;
ring.install (id, key);                                   // 或 setState
if (!persistRing (ring, storePath, pwhy)) ring = before;  // 回滚，回 01
```

对吊销尤其重要：吊销没落盘，重启就复活，等于没吊。

## 6. 半截的表上不再写

启动判 `Corrupt` 后，`0206` / `0207` 一律 `7F 31 22`，直到 `--reset-key-store`。
理由：半截说明"上一笔没落干净"，允许补一笔等于用新表**悄悄盖掉**旧表里可能还活着的吊销记录。

## 7. 三十项验收（四个阶段，四个进程）

| 阶段 | 起什么 | 验什么 | 实测 |
|---|---|---|---|
| 一 | 空目录 | 首启建表 | `0001=00,0002=00`；盘上 `K 0001 00` |
| 一 | 同上 | 装 3 / 吊销 1 / 装 4 | `7101020600` / `7101020700` / `7101020600`；盘上 `K 0001 02` |
| 二 | 同一文件重启 | 吊销还在 | `0001=02,0002=00,0003=00,0004=00` |
| 二 | 同上 | 1 号被拒、4 号通过 | `7F3131` / `7101020500`；同 id 再装 `01` |
| 三 | 文件砍掉尾巴 | 判 Corrupt | 表 `(空)`；预检任何钥匙 `7F31 31`；装/改 `7F3122`；退账"坏文件 1 次" |
| 四 | `--reset-key-store` | 重建回默认 | `0001=00,0002=00`；1 号包 `7101020500`；装 3 号 `00` |

阶段二那条 `0001=02` 就是这一步的全部意义。

## 8. 单元断言：991 → 1033 项（新套件 `doip-keyringstore` 42 项）

```
A 编码            7 项   版本行 / 空表两行 / K 行形状 / 状态 02 / 校验和 16 hex / 内容变则和变
B 往返            7 项   id / 状态 / 材料 / dump / 空表合法
C 坏文件         13 项   半截 / 手改状态 / 改校验和 / 版本不对 / 重复 id / 状态 03 /
                         keyId 0 / 9 把 / 空文件 / 缺 SUM 行 / SUM 行后又加一行
D 文件层         15 项   写盘读回 / 覆盖写 / rename 替换 / Missing 与 Corrupt 分开 /
                         目录不存在 → 失败带理由 / 不留 .tmp / 盘上半截文件
```

C 组占一半是有意的：这一层出事的方式几乎全在"读坏了怎么办"。

## 9. 踩到的坑

1. **`0205` / `FF02` 都在刷写流程里**：第一版 e2e 没先 `0x10 02` + 解锁就去问，拿到 `7F 31 7F`。
   "问"也要在对的会话里 —— 这和 M22"读表不过门"不冲突，读表才是真不需要会话的。
2. **`FF02` 需要镜像**（`7F 31 22`），而这里只想验"钥匙认不认"，所以换 `0205`（只验信封、不看镜像）。
   选服务按"我要证明什么"，不按"哪个名字更熟"。
3. **检查脚本自己也会错**：`verify_pkg` 与 `precheck` 混用导致三处断言全红，读了两遍才发现是脚本错。
4. 头文件里行长度手写成 `4+4+1+2+1+64 = 76`，而实际是 `2+4+1+2+1+64 = 74` —— 一跑就判坏，改回 74。

## 10. 边界

- **没有 fsync**：只 `fflush` + `close`，掉电时 rename 之后的目录项未必落盘。真机要 `fsync(file)` + `fsync(dir)`。
- **钥匙材料明文在盘上**：真机要加密 NVM 或 HSM；这里只演示"状态机怎么落盘"。
- **没有版本迁移**：文件头写死 `1`；将来加字段要设计"读旧写新"，现在只会判 Corrupt。
- **单机语义**：每台 ECU 一张表，没有"钥匙清单广播"；多 ECU 要逐台下发。
- **没有擦写寿命管理**：每改一次整份重写，真 NVM 要考虑寿命。
