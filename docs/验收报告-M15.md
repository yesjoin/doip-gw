# M15 验收报告 —— UDS 刷写链路（0x31 / 0x34 / 0x36 / 0x37）

## 1. 目标

到 M14 为止，这条链路上的每条诊断都是**一问一答**：问 VIN、问快照、问实体状态，
ECU 不需要记住上一个请求。刷写不是。

这一步第一次引入**有状态的会话**：

- `0x31 01 FF00`：擦除（把镜像清零，状态回到"可下载"）
- `0x34`：`RequestDownload` —— 声明地址与长度，协商"一块最大多少字节"
- `0x36`：`TransferData` —— 一块一块传，每块带 BSC（块序号）
- `0x37`：`RequestTransferExit` —— 收尾，回报整条镜像的 CRC-32
- `0x31 01 FF01`：完整性校验（tester 送 CRC，ECU 比对，正响应带状态字节 `00` / `01`）

要把 M9 的 CAN FD、M10 的每通道队列、M12 的流式交付一起串起来：一百块数据要在
"单帧 7 字节 / FD 单帧 62 字节"两种信封下都跑得动，还不能把别的通道堵死。

## 2. 复现

```bash
cd ~/doip-gw
cmake --build build -j4
./build/flash-selftest                  # 54 项，纯内存，不需要 vcan0
bash tools/m15_e2e.sh 13474             # 三十九项，约 45 秒
bash tools/ci_local.sh gcc              # 19 步 32 项
```

依赖：`vcan0`、`build/stub-ecu`、`python3`（场景脚本是裸 socket，不需要 `doipclient`）。

## 3. 拓扑

- 网关：`--iface vcan0 --port 13474`，路由 `0003:7A0:7A8`
- 一台经典 ECU：`stub-ecu --rx 7A0 --tx 7A8 --flash --flash-block 34 --flash-max 65536`
  - TA `0x0003`，VIN `LSVZZ0000B7654321`，`--seconds 20`（等它自然退场，退场账才算得出来）
- 第二条腿：同一台 ECU 换成 `--flash-block 10`（证明通告的块长真的在卡客户端）
- 传输：TCP 13474 → 网关 → `7A0/7A8` → ISO-TP（经典帧 8 字节）

## 5. 三个关键口径（都是"错一个字节，现场就查不出来"）

1. **`0x76` 回的是收到的那块 BSC**（echo），不是"下一块"。写成下一块，客户端会在回绕处错位。
2. **`maxNumberOfBlockLength` 含 `0x36` + BSC 两个字节**。通告 34 = 数据最多 32；
   当数据上限用，每块多带 2 字节，边界那块必报 0x13。
3. **BSC 从 `0x01` 起，`0xFF` → `0x00` 回绕**。100 字节测不到，所以自测专门跑 260 块。

## 6. 为什么重发必须幂等

`transferData()` 的第一条判断不是"序号对不对"，而是"这是不是刚收过的那块"：

```cpp
if (lastBsc_ != 0 && bsc == lastBsc_)   // 重发：不写、只重回 76 <bsc>
```

否则链路丢一次应答，客户端重发，ECU 回 `0x73`，客户端再重发 —— **永久卡死**。
场景里第 16/17 项连发两次 `36 01`，两次都 `76 01`，最后的 CRC 证明镜像没有写两遍
（写两遍就是 132 字节，`0x77` 的 CRC 立刻不一样）。

## 7. 为什么 0x37 要带 CRC

`0x37` 的判据 `image_.size() == expectedSize_` 只证明**字节数够了**，不证明内容对。
所以正响应带 4 字节 CRC-32（poly `0xEDB88320`，init/xor `0xFFFFFFFF`，与 zlib 一致）。
自测第一条先钉尺子：`crc32("123456789") = 0xCBF43926`。

校验例程的语义也要分清：**校验失败不是否定响应**，是正响应 `71 01 FF 01 01`。
否则日志里"刷写失败"永远分不清是链路问题还是镜像问题。

## 8. 这一遍踩的三个坑

1. **VIN 的 DID 写成 `F186`**：`22 F1 86` 落到"未知 DID"，回了 `62 F1 86 02`（4 字节），
   脚本断言 20 字节 —— 第一步就红。正确是 `F190`。教训同 M14：**先确认"我发的这条本来就该成功"**。
2. **把 `0x8003` 当成诊断响应**：DoIP 里 `0x8001` 是诊断报文本身（请求与响应同类型），
   `0x8003` 是"诊断报文否定应答"。按 `0x8003` 取响应永远取不到：每个请求白等 3 秒，
   还顺带触发网关的心跳检查（`0x0007`/`0x0008`，不回就被断链）。
3. **退场账按"整场"算**：账是跟着**最后一次 `0x34`** 算的（`0x34` 会清镜像），
   最后重刷 8 字节 → 1 块。断言前先想清楚"这个数从哪一刻起算"。

## 9. 单元断言：694 → 748 项（新套件 `doip-flash` 54 项）

| 组 | 覆盖 |
|---|---|
| CRC | `"123456789"` = `0xCBF43926`；空数据 = 0 |
| 未擦除 | `0x34` → `0x22`；`0x31 FF01` 空镜像 → `0x22` |
| 擦除 | `71 01 FF 00` |
| `0x34` 参数 | `dfi≠0` / `alfid=0` / 缺字节 / 长度 0 / 超上限 |
| `0x34` 成功 | `74 20 00 22`、`payloadPerBlock=32`、进入下载态 |
| 顺序 | 没 `0x34` 就 `0x36` / `0x37` → `0x24` |
| BSC | 01→02；重发幂等；跳 05 → `0x73`；被拒后下一块仍能接 |
| 块长/总长 | 11 > 10 → `0x13`；超声明总长 → `0x71`；最后短包补齐 |
| `0x37` | 8/20 → `0x24`；传够 → `0x77` + CRC；收尾后 `0x36` → `0x24` |
| 回绕 | 260 块，第 256 块是 `0x00`，全部接受 |
| 校验 | 对/错 CRC 的状态字节；2 字节 CRC → `0x13` |
| 重置 | 下载中途再擦除 → 允许，状态与镜像全清 |

## 10. M15 之后仍然没有的

- "擦除"是内存镜像清零，不是真 Flash：没有扇区、擦除耗时、坏块、半擦状态。
- 镜像掉电即失；没有"ECU 自己算 CRC"的校验变体（我们是 tester 送 CRC）。
- BSC 只钉了 `0xFF → 0x00` 一种回绕；OEM 的 `0xFF → 0x01` 变体没做。
- 只看 BSC 判重发，不做内容哈希（同 BSC 换数据重发会被当幂等收下，靠 `0x37` 的 CRC 兜底）。
- 没有块级暂停/恢复，没有 `maxNumberOfBlockLength` 动态重协商。
- `0x34` 的 `alfid` 只支持 1–4 字节；只保留最后一次声明的地址与长度（不支持一条会话刷多段）。
- 刷写只走物理寻址（广播上的 `0x31/0x34/0x36/0x37` 不处理）。
- 没有 `0x10` 会话切换与 `0x27` 安全访问：`--flash` 等于"谁都能刷"，M16 才补。
- 不验时间（无 `P2` 超时、无擦除耗时）；没有在真实 1 Mbps 总线上量过 100 块的耗时。
