# M21 验收报告 —— 把"这包是给谁做的"写进清单（0x31 01 0205 + FF02 身份）

## 1. 目标

M20 的目标身份是 tester 在 `0x31 01 0204` 里**口述**的，ECU 只能听、没法验。
那么"这包是给这台车的"这句话，本质上还是**声明**。

M21 把它变成**证明**：

- **身份进清单**（v2，104 字节）：`targetPart`（12 字节）+ `targetSw`（16 字节）；
- **身份落在标签覆盖范围内**：标签盖前 **72** 字节，改一个字符标签就崩；
- **预检**（`0x31 01 0205`）：只收 v2，`checkEnvelope` 不看镜像，通过即发凭证；
- **`FF02` 三态**：`00` 包真且身份对 / `01` 包不对 / **`02` 包真但不是给这台车的**。

## 2. 复现

```bash
cd ~/doip-gw
cmake --build build -j4
./build/integrity-selftest           # 46 项（原 28 + D 组 18），纯内存

```

依赖：`vcan0`、`build/stub-ecu`、`python3`。

## 3. 清单 v2 的排布

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0..3 | 4 | `DGIM` |
| 4 | 1 | 版本 `0x02` |
| 5 | 1 | flags（保留 0） |
| 6..9 | 4 | 镜像长度 u32 大端 |
| 10..41 | 32 | SHA-256（镜像） |
| 42..43 | 2 | keyId |
| 44..55 | 12 | **targetPart**（右补空格） |
| 56..71 | 16 | **targetSw**（右补空格） |
| 72..103 | 32 | tag = SHA-256(0..71 ‖ key) |

前 44 字节与 v1 一致 —— 加字段时"新增的放后面、覆盖长度跟着延长"是最省事的排法。

```
v1：76 字节，tag 盖 0..43，无身份
v2：104 字节，tag 盖 0..71，身份在盖住的范围内
```

两种篡改都躲不过：改零件号 → 标签重算不出原值；v1 的标签搬进 v2 → 覆盖长度不同，算的不是同一段。

## 4. 长度与版本必须成对

```
76 ⇄ 0x01      104 ⇄ 0x02
```

不配对 → `BadMagic` → NRC `0x31`。理由：标签的覆盖长度由版本字节指示，
版本和长度打架时"该按哪一段算"没有答案，只能拒。

v1 继续可用，代价是 `hasIdentity = false`，建立不了"已比对"的凭证。

## 5. `checkEnvelope`：不看镜像的那一半

```cpp
checkEnvelope (manifest);   // 长度 / magic / 版本 / keyId / 标签 / 身份
verify (image, manifest);   // checkEnvelope + 镜像长度 + 镜像哈希
```

拆开的唯一目的：**镜像还没传上来时也能验信封**。预检的意义就是"推 8 KB 之前先知道这包是不是给我的"。

## 6. 服务行为与状态码

`0x31 01 0205 + <整份 104 字节清单>`：

| 情况 | 回答 | 类别 |
|---|---|---|
| 收到 v1（76 字节） | `7F 31 31` | 只收带身份的 v2 |
| 100 字节之类的长度 | `7F 31 13` | 结构错 |
| 版本/长度不配对、标签不符、keyId 不认识 | `7F 31 31` | 结构错 |
| 信封对、身份不符（零件号 / 降级 / 版本号乱写） | `71 01 02 05 01` | 包不对 |
| 全部通过 | `71 01 02 05 00` + 发凭证 | 可以刷 |

`0x31 01 FF02 + <清单>`（整包验签）：

| 情况 | 回答 |
|---|---|
| v2，镜像与身份都对 | `71 01 FF 02 00` |
| v2，标签/长度/哈希不对 | `71 01 FF 02 01` |
| **v2，包真但身份不符** | **`71 01 FF 02 02`** |
| v1，镜像对 | `71 01 FF 02 00`（日志补一句"v1 没有身份字段"） |

为什么 `01` 与 `02` 要分开：`01` 是"包坏了，找供应商"；`02` 是"包是好的，你拿错车了"。
一个码糊住两件事，现场就会查错方向。

FF02 **不发凭证**（它是事后核对），凭证只在 `0204` / `0205` 发。

## 7. 为什么 `0205` 的坏版本号回 `01`，`0204` 回 `31`

同样把版本写成 `SW-latest`：

- `0204` 的坏数据在**请求里** —— 请求不合法 → NRC `0x31`；
- `0205` 的坏数据在**签过名的包内容里** —— 请求合法、包有问题 → 正响应 `01`。

判据是"这个坏数据是谁给的"，不是"坏在哪一段字节"。

## 9. 结构改动：`FlashContext` 再扩两个字段

```cpp
struct FlashContext {
    std::uint32_t batteryMv = 12400;
    std::uint32_t minBatteryMv = 11500;
    bool          requireCompat = false;
    bool          allowDowngrade = false;   // FF02 用同一套比对规则
    const DidTable *dids = nullptr;          // 要比对，就得知道"车自己是谁"
    policy::Gate *gate = nullptr;
};
```

`FF02` 没有 `dids` 就输出不了 `02` —— 这是"能不能报身份不符"的前提。

## 10. 踩到的坑

1. **预检之后才擦除 → `0x34` 回 `22`**：e2e 第一次跑出 `DOWNLOAD=7F3422`。
   原因是擦除本身是凭证作废点（M20 定的五条之一），顺序必须是"擦除 → 预检 → 下载"。
   这不是 bug，是我忘了自己写的规矩。
2. **`v1_as_v2` 写了两遍**：复制粘贴残留，后一段覆盖前一段。跑不出错但读着出戏，删掉重跑才信。
3. **include guard 写坏**：重写 `FirmwareManifest.h` 时 `#ifndef` 与 `#define` 名字不一致，编译直接拒；
   另有两次把 ASCII 双引号嵌进中文字符串（本项目老毛病），编译前统一换成 `「」`。

## 12. 边界

- 身份只有"零件号 + 版本"两段，**没有** VIN / 车型 / 电池类型；按 VIN 判就要再来一版 v3（标签覆盖长度又变）。
- 标签是对称 MAC：证明"知道钥匙的人做的包"，不能证明"厂商做的"；防内部伪造要非对称签名。
- v1 包永远没有身份：`FF02` 只能回答"包真"，"给谁"仍靠 `0204` / `0205` 口述 —— 兼容老包的代价。
- `0205` 的预检结论不保鲜（只验信封），所以 `FF02` 必须跑：它验"镜像与清单还是不是一对"。
- `flags` 字节保留但无语义（非 0 即 `BadMagic`）；清单只有 1 / 2 两档。
