# M7 验收报告：11 位 / 29 位扩展帧并存

验收目标不是"以太网侧读到了正确的值"，而是**证明这两种宽度的帧真的都发到了总线上**。
所以本报告的证据重心在 `candump`：只有总线上同时出现 8 位的 `18DAF100` 和 3 位的 `7E8`，
才能排除"网关自己编了个 VIN 回来"这种可能。

- 复现：`bash tools/m7_e2e.sh 13462`（自起两台 ECU + 网关 + 总线录制，约 40 秒）
- 结果：**通过 9 项，失败 0 项**；单元断言 421 条（6 套件，`doip-route` 由 32 → **57**）；
  `ci_local.sh` **11 步 24 项**全绿

## 拓扑（同一条 vcan0 上）

| 角色 | 逻辑地址 | CAN 收发 | 宽度 | VIN / 其他 |
|---|---|---|---|---|
| 网关实体 | `0x0001` | — | — | UDP 发现声明 VIN `LSVAA0000A1234567` |
| ECU_A（项目一 `uds-demo`） | `TA=0x0002` | `7E0` / `7E8` | **11 位** | VIN `LSVAA0000A1234567` |
| ECU_EXT（`stub-ecu`） | `TA=0x0006` | `18DA00F1` / `18DAF100` | **29 位** | VIN `LSVZZ0000B7654321`，HW `HW02` |

## 六步九项

| # | 要证明的事 | 实测 |
|---|---|---|
| 1 | 路由表打印的宽度能一眼分清 | `TA=0x0002 → 0x7E0 / 0x7E8`（3 位）、`TA=0x0006 → 0x18DA00F1 / 0x18DAF100`（8 位） |
| 2 | 11 位通道没被 29 位逻辑影响 | `22 F1 90` → `LSVAA0000A1234567` |
| 3 | 29 位通道真到了另一台 ECU | 同一 DID → `LSVZZ0000B7654321`（与 A 不同） |
| 4 | 29 位通道上服务也在跑 | `22 F1 91` → `62 F1 91 48 57 30 32` |
| 5 | **总线侧取证** | `candump` 里 `18DA00F1#...` 与 `7E8#...` 同时出现，8 位即扩展帧 |
| 6 | 两条通道分开记账 | `TA=0x0002`：转发 1 / 发帧 2 / 收帧 3；`TA=0x0006`：转发 2 / 发帧 3 / 收帧 4 |

## 总线样本（`candump -L` 原始行，节选）

```
(1795516048.625188) vcan0 7E0#0322F19000000000
(1795516048.625275) vcan0 7E8#101462F1904C5356
(1795516048.625310) vcan0 7E0#3000000000000000
(1795516048.625316) vcan0 7E8#2141413030303041
(1795516048.656924) vcan0 7E8#2231323334353637
(1795516048.703356) vcan0 18DA00F1#0322F19000000000
```

前 5 行是 11 位那条通道（`7E0` 发请求、流控，`7E8` 回 FF + 2 个 CF），第 6 行是 29 位那条通道的首帧。
**同一条总线上两种宽度交织，互不影响**——这正是 M7 要的结论。

## 网关记账（同一次跑）

```
转发 3 条，失败 0 条（其中目标地址不认识 0 条），最长排队 0 ms
  TA=0x0002（0x7E0/0x7E8）：转发 1 条，失败 0 条，发帧 2，收帧 3，超时 0，序号错 0，迟到帧丢弃 0
  TA=0x0006（0x18DA00F1/0x18DAF100）：转发 2 条，失败 0 条，发帧 3，收帧 4，超时 0，序号错 0，迟到帧丢弃 0
```

手算可对：读 VIN 是多帧 —— 1 FF + 2 CF = 3 发，ECU 回 1 FF + 2 CF = 3 收，再加 1 个流控帧 → **3 发 4 收**；
读 HW 是单帧 → 1 发 1 收。所以 29 位通道 3 发 4 收，11 位通道（只读了 VIN）2 发 3 收。

## 单元断言新增 25 项（`tests/route_selftest.cpp` C 段）

| 组 | 覆盖 |
|---|---|
| 宽度判定 | `0x7FF` / `0x800` 边界两侧 |
| 合法性 | `0` 非法、`0x1FFFFFFF` 合法、`0x20000000` 拒绝 |
| 置位 / 剥位 | `idForSend` → `idFromRecv` 往返一致；11 位原样不动 |
| 格式化 | 3 位 / 8 位且都带 `0x` |
| 入表 | 超 29 位被 `add()` 拒，错误信息含"29" |
| 混表 | 11 位 + 29 位同表并存 |

## 本轮修掉的问题

1. `src/IsoTpClient.cpp` 漏 `#include "CanId.h"` → 六个 `was not declared`（头文件分开的必然代价）。
2. `tools/m7_e2e.sh` 第一版有死代码（`m7_vin_a.log` 从未生成、`echo` 跨行引号错位），整份重写。
3. **连带影响**：`m6_e2e.sh` 断言写成老格式 `TA=0x0002 → 7E0 / 7E8`，日志统一带 `0x` 前缀后两项变红 →
   断言同步为 `0x7E0 / 0x7E8`。属"格式统一后必须同改"，不是新 bug。

## 已知边界

- 只做**经典帧**（无 CAN FD）；只做**物理寻址**，29 位下的 `18DB33F1` 那类功能寻址留给 M8。
- `--route` 的 ID 仍按整数给，`formatCanId` 只负责打印，不做入参解析。
- 一条路由仍只对应一对 ID，同一 TA 不能一半 11 位一半 29 位（表结构没变）。
- 未在真实 1 Mbps 总线上量过两种宽度交织时的总线负载 / 仲裁延迟（vcan0 不模拟仲裁）。
