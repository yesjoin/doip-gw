# M12 验收报告：流式交付（收一条转一条，且一条都不发两遍）

M11 解决的是"客户端收得齐"，M12 解决的是"**第一条答案多久到**"。

M11 之后网关还是攒批：一轮广播 → 按 TA 升序逐通道收 → 全部收齐才一次性交回。
功能寻址问的本意是"这一类 ECU 谁在"，结果 3 条答案的到达时刻被**最慢的那台**决定（ECU_C 每条答前睡 120ms）。
M12 要证明两件事，缺一不可：

1. **强的**：谁答完谁先到——首条 ≈0ms，而不是 ≈120~213ms；
2. **不能退化的**：改成逐条发之后，**同一条答案不许被发两遍**（流式发过的，交卷时不许再补）。

第 2 条比第 1 条更容易做错：`JobResult` 里仍然带着全部 replies（失败语义、统计、日志都要用），
交卷时若不动脑子再循环一遍，客户端立刻看到重复。

- 复现：`bash tools/m12_e2e.sh 13469 13470`（自起三台 ECU + 两个网关 + 总线录制，约 27 秒）
- 结果：**通过 25 项，失败 0 项**；单元断言 **593 条**（9 套件，新增 `doip-stream` **27 项**）；
  `ctest` 9 套件全绿；`ci_local.sh` **16 步 29 项**全绿（含 `-O2 + -Werror`）

## 拓扑（同一条 vcan0）

| 进程 | 地址 | CAN ID | 信封 | 特点 | 答案 |
|---|---|---|---|---|---|
| 网关一（流式） | `0x0001` | — | — | 功能表 `0xE400 → 0x7DF`，**接了 ReplySink** | 收一条转一条 |
| 网关二（对照） | `0x0002` | — | — | 功能表 `0xE400 → 0x7DF`，**`--no-stream`** | 退回 M11 的攒批 |
| ECU_A | `TA=0x0003` | `7A0`/`7A8` | 经典 8 | 快 | `22 F1 91` → `62 F1 91 48 57 30 32`（`HW02`） |
| ECU_B | `TA=0x0006` | `18DA00F1`/`18DAF100` | FD 64 | 快 | `HW03` |
| ECU_C | `TA=0x0007` | `7B0`/`7B8` | 经典 8 | **每条应答前睡 120ms** | `HW04` |

两个网关打的是**同一条总线、同一批 ECU**，唯一的差别是交付方式——这样"流式 vs 攒批"的对比才干净。

## 八步二十五项

| # | 要证明的事 | 实测 |
|---|---|---|
| 1 | 流式网关打的是流式 | `交付方式：流式` |
| 1 | 对照网关真退回了攒批 | `交付方式：攒批`（`--no-stream` 生效） |
| 1 | 三条物理通道都开了 | `TA=0x0007 → 0x7B0` |
| 2 | 三条答案一条不少 | `RESPONSE_COUNT=3` |
| 2 | 首条不等慢的那台 | `FIRST_AT=0ms`（≤50） |
| 2 | 末条确实是慢的那台 | `LAST_AT=135ms`（≥100） |
| 2 | 答案是陆续到的，不是一整批 | `SPAN_AT=135ms`（≥90） |
| 3 | 对照也是三条 | `RESPONSE_COUNT=3` |
| 3 | 对照是"一口气到齐" | `SPAN_AT=0ms`（≤20） |
| 3 | 对照的首条被最慢那台拖住 | `FIRST_AT=213ms`（≥100） |
| 3 | 同一场景下的收益 | 流式首条比攒批早 **213ms**（≥80 即通过） |
| 4 | 没有多发 | `RESPONSE_COUNT=3`、`RESPONSE_ARRIVALS=3` |
| 4 | 归档里没有重复 | `COLLECTOR_DUPLICATES=0` |
| 4 | 三台 SA 各一条，没谁被补成两条 | `RESPONSE_SAS=0x0003,0x0006,0x0007` |
| 4 | 账把重复发挡住了 | `回来 3 条（流式已发 3 条）→ 补齐 0 条` |
| 5 | 窗口 40ms：快的先到 | `RESPONSE_COUNT=2`（M12 前这里是整批 0 条） |
| 6 | 提前断线：迟到的那条只记账 | `流式时连接已断 2 条`（≥1） |
| 6 | 下一位 tester 只拿自己的 | `RESPONSE_COUNT=3`（前一位的残留没混进来） |
| 7 | 流式网关广播 6 次 | `广播 6 次`（热身 1 + 第 2/4/5/6 步 5 次） |
| 7 | 收回应答 18 条（含客户端提前走的） | `收回应答 18 条` |
| 7 | 真正流式送达 16 条 | `流式交付 16 条`（≥12） |
| 7 | 断线丢弃 2 条 | `流式时连接已断 2 条`（≥1） |
| 7 | 对照网关只广播 1 次 | `广播 1 次` |
| 7 | 对照网关没有流式账 | 日志里没有 `流式交付` |
| 7 | 总线上一次广播就一帧 | `7DF#` 7 条 = 6 + 1（两台网关广播次数之和） |

时间断言不写绝对值：stub 自己有几十毫秒抖动，所以用**同一次会话里的两端对比**（`nFirst - sFirst ≥ 80ms`）
和 **SPAN 的形状**（流式 ≥90、攒批 ≤20）。写死"首条必须 0ms"会在慢机器上随机红。

## 时序对照（同一批 ECU，只换交付方式）

```
流式（默认）
t=0     客户端发 0x8001（TA=0xE400）
        ← 0x8002 ACK（立刻）
t≈0     ECU_A 答 → 网关立刻 0x8001 转给客户端      ← FIRST_AT=0ms
t≈1     ECU_B 答 → 立刻转                          ← 第 2 条
t≈120   ECU_C 才答 → 立刻转                        ← LAST_AT=135ms（SPAN=135ms）

攒批（--no-stream）
t=0     客户端发 0x8001（TA=0xE400）
        ← 0x8002 ACK（立刻）
t≈120   ECU_C 才答
t≈130   网关把 3 条一起交回                        ← FIRST_AT=213ms、SPAN=0ms
```

攒批这一列是 M11 的原样行为：快的两台 1ms 内就答了，但那 3 条答案在网关里排队等慢的那台。
**M12 没有让 CAN 侧变快（ECU_C 还是 120ms），只是不再让别人陪它等。**

## 五个坑（按发现顺序，全部已修并被验收覆盖）

1. **`drainStale()` 一直是个空操作。** 原写法 `while (recvFrame(d, dlc, 0, e))` 里，`recvFrame` 第一步是
   `if (now >= deadline) return "接收超时"`——`timeout=0` 时 deadline 就是"现在"，一条都读不到。
   于是"别人家/上一轮"的应答帧躺在 socket 缓冲区里，被下一次 `recvFunctional` 当成本次答案：
   **上一轮慢 120ms 的那台，这一轮 0ms 就"答"了，它真正的答案留给下一轮，一轮轮传下去。**
   M11 攒批时被整批延迟掩盖，M12 立刻显形。改成真正的非阻塞清仓（`poll(0)` 说没数据就停，非本 rxId 的帧丢掉不计数）。
2. **测试桩自己的睡意混进了测量。** `stub-ecu` 主循环 `poll(&p,1,50)` → 改 10ms，
   否则"应答几毫秒"会被量成"应答 50ms"。
3. **`-O2` 下 `(void)::write(...)` 照样报 `warn_unused_result`。** 改成 `const ssize_t wr = ::write(...); (void) wr;`。
   ci_local 用 `-O2 + -Werror` 就是为了抓这种只在优化后才露头的警告。
4. **`routing_selftest` 收包没缓冲。** 开了 `TCP_NODELAY` 之后两条 21 字节应答常同段到达，
   旧 `recvMessage` 把两条都塞进 `whole` 就返回——看着像"服务器吞了粘包第二条"，实际是测试桩吞的。
   改成按 fd 记余字节、一条条交出去。
5. **窗口 40ms 的断言连红两次**：不是阈值问题，是坑 1 的"慢的也秒回"。
   **验收脚本自己也要被验收**：先证明现象，再调数字。

## 账目与总线样本

网关一（流式）退场账：

```
功能寻址：广播 6 次，收回应答 18 条，无人应答 0 次
流式交付 16 条（收到就转，不等一轮收齐；同一 job 交卷时只补差额）
流式时连接已断 2 条（丢弃不转交）
```

手算校验：第 6 步那位提前挂断的 tester 发了 1 条广播 → 3 台都答了（`收回应答` 计入），
但客户端在 20ms 就断了，快的 2 条到的时候人还在（送达）、慢的第 3 条到的时候人已走（丢弃 1 条）；
另一位提前走的是第 5 步（窗口 40ms，慢的那条同样丢弃）。所以 `断线丢弃 = 2`、`流式交付 = 18 - 2 = 16`。

总线（`candump -L`）：一次广播只有一帧请求，与交付方式无关：

```
(…) vcan0 7DF#0322F19100000000
(…) vcan0 7A8#0762F19148573032
(…) vcan0 18DAF100#0762F19148573033
(…) vcan0 7B8#0762F19148573034        ← 慢 120ms 的这一条，晚到但不再拖住前两条
```

`7DF#` 共 7 条 = 流式 6 次 + 对照 1 次：**流式改变的是"什么时候把答案交回"，不是"发几次广播"**。

## 单元断言：566 → 593 项（新套件 `doip-stream` 27 项）

`StreamLedger` 只做整数加减，自测覆盖的全是"同一批答案被两条路径各处理一次"的情形：

| 组 | 覆盖 |
|---|---|
| 全流式 | 3 条都流式过 → `remainder(3) = 0`（这就是不重复发的全部保证） |
| 部分流式 | 流式 2 条 → 补 1 条 |
| 一条没流式 | 补发全部 |
| 不下溢 | 账比结果多（流式 5 条、结果 3 条）→ 补 0 |
| 不串味 | 两个 job 各自的账互不影响 |
| 销账 | `forget` 后 `streamed()=0`、`jobs()` 减一；`totalStreamed` 是观测量不回退 |
| 复位 | `clear()` 全部归零 |
| 规模 | 64 位 jobId、100 个 job 也能归档 |

`ctest -R doip-stream` 一秒内跑完，不需要 `vcan0`；它证明的是"账不会算错"，
"答案真的提前到了"只能靠 `m12_e2e.sh` 在真总线上称。

## 边界（写清楚，不糊过去）

- **共享总线上的另一家广播**：网关无法区分"这一帧是回应我这次广播"还是"回应别人的广播"（ISO-TP 没有请求/响应配对字段）。
  `drainStale` 能清掉历史残留，但清不掉"同时发生的另一家广播"——此时仍可能误认，属于共享介质的固有边界。
- **交卷差额依赖"收/发同序"**：流式发的是 `replies` 的前 k 条，`deliver()` 从第 k 条接着发。
  以后若引入乱序或并发交卷，这本账要跟着改。
- **迟到流式只记账不重发**：断线后到达的答案计入 `流式时连接已断 M 条` 并丢弃，不缓存、不转交给下一位 tester。
- **客户端不做超时重发**：`--trace` 只测量，不改变 M11 的静默窗口收工语义。
- **`--no-stream` 仅供对照**：它保证"退回攒批"，但不保证日志与账目和 M11 逐字一致。
- 时延数字是 vcan0 上的本地量；真实 1 Mbps 总线上 ECU 的应答时间不同，但"首条不再由最慢那台决定"这条性质不变。
