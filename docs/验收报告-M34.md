## 1. 这一步要解决的问题

M33 的越权账只代表**一次运行**：秒是进程单调秒，重启归零，两份账的时间不可比。
所以 M33 明确不做合并，只让外部按运行轮转存多份。

问题是工具只读一份。而真正要回答的问题是跨文件的：

- 某台诊断仪**是不是每周都在撞**？
- 钥匙表被试探的次数**在涨还是在落**？
- 上周挡了 300 次、这周挡 5 次 —— 是换了人，还是同一个人收了手？

M34 就是把这多份账读进来的那道桥：`doip-deny --merge a.txt b.txt c.txt`。

## 3. 机制

### 3.1 只并计数，不并秒

合并结果的一个条目是 `MergedEntry`：

```cpp
sa, sid, did, need, have, why
count            // 各份之和
perRun[]         // 每份账里这条各几次；没有就是 0
```

**`MergedEntry` 里没有时间字段。** 不是忘了，是刻意不放：

不同进程的"第 300 秒"不是同一时刻。硬取 `min(firstSec)` / `max(lastSec)` 会造出
"第一次在第 300 秒、最后一次在第 12 秒"的账 —— 一个自相矛盾的数字比没有数字更糟。

替代物是 `perRun`。它回答的是"分布"而不是"时刻"：

```text
×8  （每份：5/3/0）
```

`5/3/0` 说明前两次运行一直在撞、这次停了。这个信息用"8"是读不出来的。

### 3.2 不套 32 组上限

单账 `kMaxEntries=32` 是"一次运行记不下就丢最旧"的现场取舍。

合并账是**事后阅读**：少一组就等于把一条审计线索扔掉。所以合并结果保留全部组，
只在输出里说明一句"合并账不套单账 32 组上限"。

### 3.3 一份坏就整次不给

`loadAll` 逐份读，任一份失败就返回 `false` + 坏在第几份：

```text
越权账合并失败：第 2 份（/tmp/bad.txt）：SUM 不符
  2 份里有 1 份读不出来；坏账不参与合并，整份结果也不给
```

**不给"能读的那几份先汇总"** —— 半份总账比没有账更危险，它会让人以为"就这些"。

### 3.4 按人/按物换成"出现于几分"

单份账报"撞了几次"；合并账多一列"**出现于 2/3 份**"。

同一个 SA 可能有多组试探分散在不同份里（第 1、2 份撞 DID，第 3 份扫服务号）。
所以 `runsOfSa` 求**并集**，不是取最大 —— 取最大会把 3/3 算成 1/3。

## 4. 口径

| 问题 | 单份（M33） | 合并（M34） |
|---|---|---|
| 时间 | 本次运行第 N–M 秒 | **不给**（跨运行不可比） |
| 总量 | 一条记录的 ×N | 各份之和 ×N |
| 分布 | 无 | **每份：5/3/0** |
| 出现跨度 | 无 | **出现于 2/3 份** |
| 上限 | 32 组，丢最旧 | 不设上限 |
| 坏账 | 退出 1 | 退出 1 且**一条都不给** |

## 5. 命令行与输出

```bash
./build/doip-deny --merge /tmp/d1.txt /tmp/d2.txt /tmp/d3.txt [--top 5]
```

```text
越权账合并：3 份
合计：10 次挡回，2 组记录（合并账不套单账 32 组上限）
  时间：只并计数、不并秒 —— 各份的秒是各自进程的单调秒，跨运行不是同一时刻
按 SA（谁在撞墙）：
  0x0E00：8 次（出现于 2/3 份）
  0x0E01：2 次（出现于 1/3 份）
按对象（被试探的是谁）：
  DID 0xF1B0（钥匙表）：10 次（出现于 3/3 份）
明细（按次数从多到少；括号里是每份各几次）：
  0x0E00 想 0x22  DID 0xF1B0（钥匙表）  DID 级别不够 ×8  （每份：5/3/0）
  0x0E01 想 0x22  DID 0xF1B0（钥匙表）  DID 级别不够 ×2  （每份：0/0/2）
```

退出码：`0` 读通（含全空账）、`1` 任一份坏、`2` 用法错（含 `--ledger` 与 `--merge` 同给）。

`--merge` 与 `--ledger` 互斥是有意的：一份和多份的口径不同（有没有时间窗），
混着看会让人以为时间列存在。

## 9. 踩到的坑

### 9.1 `runsOfSa` 第一版写成取最大

同一个 SA 可能有多组试探分散在不同份账里：

- A 组（撞 `F1B0`）出现在第 1、2 份
- B 组（扫服务号）出现在第 3 份

取最大得到 2（组 A 的 runs=2），并集才是 3。

这不是数学细节 —— 报"2/3 份"会让人以为这人漏了一周没来，实际每周都在。
E 组把三种情形都钉住（同一 SA 分散、同一 DID 分散、只在第一份）。

### 9.2 单测里两处期望值自己敲错

- B6 取了 `entries[1]`，但插入顺序是 `0x0E00 0x2E` 在前 → 应该是 `entries[0]`
- C3 把"40 组进账、32 留 8 丢"的合计写成 `32 + 1`，实际是 `40 + 1`

和 M33 是同一个毛病：**红的是断言，不是代码**。每次都要先问"这个期望值是从哪来的"，
而不是直接改代码去迎合它。

## 10. 与 M33 的关系

M33 造出单份账，M34 把多份读进来。两个工具同一个入口（`doip-deny`），
`--ledger` 与 `--merge` 互斥 —— 因为一口径有秒、一口径没秒，混着看会误导。

```
doip-gateway --deny-ledger run1.txt   →  run1.txt（一次运行）
doip-gateway --deny-ledger run2.txt   →  run2.txt
doip-deny --merge run1.txt run2.txt   →  跨运行看分布
```

---

## 11. 边界

- **合并结果不落盘**：只打印；要留总账就重定向成文本（没有 `DOIPMERGE` 格式、没有校验和）。
- **不按时间排序**：`--merge` 的顺序就是文件给顺序；跨运行的秒不可比，排了也是假的。
- **不做趋势图/阈值告警**：只回答"多少次、几份里出现"，不回答"该不该报警"。
- **只覆盖网关这一跳**：能直接接 CAN 的人绕过。

---

## 12. 结论

M34 把"一次运行的账"接成"多份账的分布"：

- 隔离验证：33 项只碰纯逻辑（跨份累加、perRun、不套上限、并集、纯函数）。
- 端到端验证：38 项真跑三次网关、落三份真文件，`5/3/0` 从落盘一路走到输出。
- 回归：28 套件 1438 项全绿，`ci_local.sh` 38 步 51 项全绿，GitHub Actions 双绿。

这一步没有新 bug 要修，但把 M33 留下的一个坑（并集 vs 取最大）在写代码时就钉住了 ——
`runsOfSa` 第一版就是错的，是 E 组把它拦下来的。
