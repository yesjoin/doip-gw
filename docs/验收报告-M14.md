# M14 验收报告 —— 实体状态与电源模式（0x4001 / 0x4002 / 0x4003 / 0x4004）

## 1. 目标

M13 建了一张**实体级**的账（谁激活了、还剩几个名额），但它只活在网关自己的退场日志里。
诊断仪想知道"你还接得下几台、能收多大的包"，只能靠撞：撞出 0x01 才知道名额满了。

这一步就是把这张账按标准公布出去：

- `0x4001`（UDP）→ `0x4002`：节点类型 + 最大 socket 数 + **当前开着的 socket 数** + 最大可处理载荷
- `0x4003`（UDP）→ `0x4004`：诊断电源模式（`0x00` 未就绪 / `0x01` 就绪 / `0x02` 给不出）

顺带解决一个跨线程问题：`cur open sockets` 是活的，而回答它的是 UDP 线程、管理连接的是
I/O 线程 —— 直接遍历 `conns_` 就是数据竞争。

## 2. 复现

```bash
cd ~/doip-gw
cmake --build build -j4
./build/entity-selftest                 # 58 项，纯内存，不需要 vcan0
bash tools/m14_e2e.sh 13472             # 二十项，约 25 秒
bash tools/ci_local.sh gcc              # 18 步 31 项
```

依赖：`vcan0`、`build/stub-ecu`、`python3`（场景脚本是裸 socket，不需要 `doipclient`）。

## 3. 拓扑

- 网关：`--iface vcan0 --port 13472`，`maxConnections=8`、`maxActivated=4`、`maxPayload=4096`
- 一台经典 ECU：`stub-ecu --rx 7A0 --tx 7A8`，TA `0x0003`，VIN `LSVZZ0000B7654321`
- UDP 13472 上同时住两套业务：发现（`0x0001` → `0x0004`）与实体状态（`0x4001/0x4003`）

## 5. 为什么 `cur open sockets` 不是"激活了几台"

M13 刚把两个数拆开：`maxConnections = 8`（挂得住几条 socket）/ `maxActivated = 4`（同时给几台激活）。
0x4002 里这个字段数的是**前者**：一个连上来但没激活的连接，仍然占着一个 socket。
所以场景里 3 条连接只激活 1 条，`cur` 必须是 3。混起来的话，诊断仪会看到一个"永远比实际忙"的实体。

## 6. 公告必须等于实现

`max data size` 填 4096，正好是 `parseMessage` 里真正的 `maxPayload`（不含 8 字节头）。
报 32KB 却在内部分 4KB 拒收，诊断仪会按公告发大包，然后每次都吃 `0x0000 0x02` ——
这不是"标准有问题"，是公告和实现不一致。

## 7. 跨线程：为什么加了一个原子量

- `conns_` 只有 I/O 线程动（accept / drop / 遍历）；
- 回答 `0x4001` 的是 UDP 线程。

让 UDP 线程遍历 `conns_` 是数据竞争，而且"跑十遍崩一次"。所以服务器维护
`std::atomic<std::size_t> openSockets_`（accept +1、close -1），UDP 线程只读它。
快照可能差一条（那一刻正好有人连上），但**不可能是坏内存**。

## 8. 这一遍踩的两个坑

1. **0x0006 的码取错了位**：`payload[2]` 是实体地址的高字节 `0x00`，看着像"未知源地址被拒"，
   成功码 `0x10` 在 `payload[4]`。教训同样是"验收脚本自己也要被验收"。
2. **账目条数算少了**：以为 6 条，实际 7 条（带载荷的两条也算实体查询）。断言前先数清楚。

## 9. 单元断言：636 → 694 项（新套件 `doip-entity` 58 项）

| 组 | 覆盖 |
|---|---|
| 编码布局 | 7 字节、字段顺序、4 字节大端（4096 = `00 00 10 00`） |
| 往返 | 四字段编了再解一个不差 |
| 短式 | 3 字节老式也认，`maxDataSize=0`（未告知，不猜 4096） |
| 长度 | 2 / 5 / 8 字节都解不开且带原因 |
| 电源模式 | 0x00/0x01/0x02 三值 + 保留值 0x03 拒绝 |
| 0x4001 | 回 0x4002、整条 15 字节、长度字段=7；带载荷沉默且不发字节 |
| 0x4003 | 三种答案原样带出去；带载荷沉默 |
| 越界 | 其它类型一条都不答 |
| 折快照 | 300 → 255（不回绕成 44）；0 个连接报 0 |
| 极值 | `0xFFFFFFFF` 往返不变 |

## 10. M14 之后仍然没有的

- 只发 7 字节长式 0x4002；3 字节短式只认不发。
- `cur` 不含正在三次握手的那条；跨线程读的是原子快照，可能差一条。
- 0x4001/0x4003 只走 UDP；TCP 上收到只记账、不回答、不断开。
- 电源模式是启动时的静态配置，不随 CAN 侧实际状态变化（没有"去问子网 ECU 能不能诊断"的探测链路）。
- 不做 2019 版新增的 0x4005 / 0x4006，不做周期性主动广播 0x4002。
- 没有 TLS 下的实体状态差异（TLS 整体不做）。
- `doip-serve` 只开 TCP，所以它收到这两条只会记账、不可能回答。
