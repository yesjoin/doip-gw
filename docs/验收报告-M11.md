# M11 验收报告：诊断仪侧多响应配对（一条广播，三台 ECU 各答一句）

验收目标不是"服务端能发几条"——M8 已经验过了。M11 要证明的是**客户端侧终于收得齐**：

1. 一条广播出去的答案条数**由"谁在听"决定**，不是固定 1 条；
2. 每条答案归谁**只能按 SA 认**，按"第几条"猜一定会错位；
3. "收齐了吗"协议层没有答案——只能靠**静默窗口**，窗口给小了整批都可能收不到；
4. 没有答案的两种情形要分得清：`0x06`（没人听）与 `0x03`（地址不认识）。

只验"能收到一条"等于没验：M8 之前 `doip-client` 就是收一条就退出，脚本能过，
真去做功能寻址扫描时却只能看到第一台车。

- 复现：`bash tools/m11_e2e.sh 13467 13468`（自起三台 ECU + 两个网关 + 总线录制，约 27 秒）
- 结果：**通过 20 项，失败 0 项**；单元断言 **566 条**（8 套件，新增 `doip-collector` **45 项**）；
  `ci_local.sh` **15 步 28 项**全绿

## 拓扑（同一条 vcan0）

| 角色 | 逻辑地址 | CAN 收发 | 信封 | 性格 | 应答内容 |
|---|---|---|---|---|---|
| 网关一 | `0x0001` | — | — | 功能表 `0xE400 → 0x7DF` | — |
| 网关二 | `0x0002` | `7C0/7C8` | 经典 | 功能表 `0xE400 → 0x5DF`（**没人听**） | — |
| ECU_A | `TA=0x0003` | `7A0`/`7A8` | 经典 8 | 快 | `22 F1 91` → `62 F1 91 48 57 30 32`（`HW02`） |
| ECU_B | `TA=0x0006` | `18DA00F1`/`18DAF100` | FD 64 | 快 | `HW03` |
| ECU_C | `TA=0x0007` | `7B0`/`7B8` | 经典 8 | **每条应答前睡 120ms** | `HW04` |

为什么读 `22 F1 91`（硬件号，6 字节）而不是 VIN：功能寻址下的请求是单帧，ECU 也只能**单帧答**，
VIN 那条 20 字节的响应在广播上按协议根本不答（M8 的边界）。这一点在本步第一次跑时就踩到了，
详见"踩到的坑"。

## 时序：为什么"窗口太短"是整批 0 条，不是少收一条

网关这一轮广播的动作是：发一帧 `7DF` → 按 TA 升序，每条通道固定 150ms 收 →
**攒齐所有答案后一次性交回**。中间有一台慢 120ms 的 ECU：

```
t=0     客户端发 0x8001（TA=0xE400）
        ← 0x8002 ACK（立刻，I/O 线程不等 CAN）
t≈120   ECU_C 才答（每条前面睡 120ms）
t≈130   网关把 3 条答案一次交回（deliver 里一条循环全发）
```

于是窗口 80ms 的客户端在 `t=80` 就收工了，一条都拿不到；而网关账上那 3 条是真收到了。
第 9 步的 `广播 5 次，收回应答 15 条` 就是这句的账单：**客户端 0 条 ≠ 没人答**。

这也是"客户端怎么知道收齐了"这个问题的正面回答：DoIP 没有批次结束字段，
网关又是攒批交回，所以客户端唯一能用的信号就是"多久没新东西了"。
真实诊断仪用 UDS 的 `P2*` 计时，本质相同，但它有时限来源（OEM 规范），我们只能自己定。

## 归档规则：为什么按 SA 而不是按顺序

| 输入 | 归档结果 | 为什么 |
|---|---|---|
| `0x0006` 先答 | 第 1 条 | 顺序是"谁先答"，不是 SA 大小 |
| `0x0003` 后答 | 第 2 条 | 同上 |
| `0x0007` 再答一遍 | `duplicates=1`，台数不变 | 一台不能被算成两台 |
| `0x0007` 第三次答得不一样 | `changes=1`，**正文保留第一次** | 覆盖就把"它改了口"这个证据抹掉了 |
| `0x7F 22 31` | 一条合法答案，`negative()` 为真 | "不支持这个 DID"也是答案，不能当没答 |

按顺序归类的写法在这里一定错：只要有一台答慢了，后面全部错位一格，
而错位的表现是"VIN 报给了另一台车"——这正是 M5/M10 一直在防的那类事故。

## 单元断言：521 → 566（新套件 `doip-collector` 45 项）

`include/DiagResponseCollector.h` 是纯逻辑（假时钟、无 socket），45 项一秒跑完：

| 组 | 覆盖 |
|---|---|
| 空 | 0 台 / 0 条 / `quietMs=-1` / 永远不收工 |
| 顺序 | 先到的排第 1（`0x0006` 在前不是因为它大） |
| 重复 | 同 SA → `Duplicate`，台数不涨、`duplicates++`、正文不覆盖 |
| 改口 | 正文变了 → `changes++`，仍不覆盖 |
| 窗口 | 静默 99ms 不收工、**100ms 收工**（边界含等号）、新响应把收工时间往后推 |
| 负响应 | `0x7F` 也算答案 |
| 长报文 | 200 字节逐字节相同 |
| 规模 | 20 台一起答，顺序与查表都对 |
| 复位 | `reset()` 回到"从来没响过" |

## 这一步踩到的坑

1. **功能寻址只收单帧**：第一版拓扑用 `22 F1 90`（VIN 20 字节），两台经典 ECU 当场拒绝回答
   （`stub-ecu` 日志："响应 20 字节塞不进单帧（上限 7），按协议不答"），只有 FD 那台答了 →
   `RESPONSE_COUNT=1`。换成 `22 F1 91`（6 字节）才对。这不是 bug，是 M8 的边界在教训我。
2. **`0x8003` 会晚到**：`--all` 的循环第一版只认 `0x8001`，NACK 被当"不是响应，跳过"，
   第 7 步永远等不到码。ACK 先回、NACK 后回，是"先受理再判断"的直接后果。
3. **`nameOf(DiagNack)` 返回 `const char*`**，写成 `.c_str()` 直接编译报错。
4. **`const find()` 不能在 `add()` 里用来改**：`-Werror` 下报 `invalid conversion from const*`，
   加了个私有 `findMutable()`——语义上也该分开：查询只读，归档要改。

## 边界（这一步明确没做的）

- "收齐"靠客户端拍的静默窗口，不是协议保证；给小了整批都可能收不到，给大了每条都多等。
- 网关仍是**攒批交回**，客户端看不到"一条条到达"的过程；流式交付留给下一步。
- 功能寻址下长 DID（如 VIN）永远没有答案，只能物理寻址一条一条读。
- `duplicates` / `changes` 只计数，不保存"改口后的第二份正文"。
- 客户端不做超时重发：宁可少收，也不把功能寻址变成"N 台各答两遍"。
