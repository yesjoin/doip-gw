# M10 验收报告：多 tester 独立通道（一条通道一条队列 + 一条线程）

验收目标不是"同时连上两个客户端"——那件事 M5 就验过了，M4 起就是"一把锁串行"，
两条连接也能连、能答，只是**排队**。M10 要证明的是相反的三件事：

1. **两条不同通道真的并行**：一台 ECU 慢，另一条通道不许陪它等；
2. **同一条通道必须串行**：两个 tester 抢同一台 ECU，总线上的帧不许交叉；
3. **断线的那条请求不许转交**：结果回来找不到人就得落地无声，下一位 tester 只能拿到自己的答案。

只验"两条都答上了"等于没验：一把锁串行也能两条都答上。所以第 3 步必须**在慢请求还睡着的时候**
去打快通道，第 4 步必须**不看网关日志、看总线**。

- 复现：`bash tools/m10_e2e.sh 13466`（自起三台 ECU + 网关 + 总线录制，约 27 秒）
- 结果：**通过 20 项，失败 0 项**；单元断言 **521 条**（7 套件，新增 `doip-pool` **29 项**）；
  `ci_local.sh` **14 步 27 项**全绿

## 拓扑（同一条 vcan0，三台 ECU）

| 角色 | 逻辑地址 | CAN 收发 | 信封 | 性格 | VIN / HW |
|---|---|---|---|---|---|
| ECU_C（`stub-ecu`） | `TA=0x0003` | `7A0`/`7A8` | 经典 8 字节 | 快 | `LSVZZ0000B7654321` / `HW02` |
| ECU_FD（`stub-ecu --fd`） | `TA=0x0006` | `18DA00F1`/`18DAF100` | FD 64 字节 | 快 | `LSVCC0000C7654321` / `HW03` |
| ECU_SLOW（`stub-ecu --delay-ms 700`） | `TA=0x0007` | `7B0`/`7B8` | 经典 8 字节 | **每条应答前睡 700ms** | `LSVSS0000S7654321` / `HW04` |

`--delay-ms` 是这一步特意给 `stub-ecu` 加的：真实的慢 ECU（做刷写、做自检）就是这样，
不是网络慢，是**它自己**慢。

## 八步二十项

| # | 要证明的事 | 实测 |
|---|---|---|
| 1 | 三条通道都开起来了 | 网关打印 `TA=0x0003 → 0x7A0 / 0x7A8`、`TA=0x0006 → …（FD，帧长 64）`、`TA=0x0007 → 0x7B0 / 0x7B8` |
| 1 | 慢的那台自己声明 | `每条应答前先睡 700 ms（模拟慢 ECU）` |
| 2 | 两条不同通道同时问 | FD 拿到 `LSVCC…`、经典拿到 `LSVZZ…`，**两条答案没串** |
| 3 | 慢的还在飞时，快的照常答 | 快通道 **141ms** 拿到 VIN（判据 < 300ms） |
| 3 | 慢的是真的慢 | 慢通道总耗时 **782ms**（≥ 700ms） |
| 4 | 同通道两个 tester 都成功 | T1、T2 都拿到 `LSVZZ…`（是排队，不是丢弃） |
| 4 | 同通道帧序不交叉 | `SEQ=1014 215A 2237 1014 215A 2237` |
| 5 | 同一连接发第一条 | `0x8002` ACK |
| 5 | 同一连接发第二条 | 当场 `0x8003`，码 `0x08` |
| 6 | 发完慢请求立刻断连 | 后一位 tester 读到的是**自己的** `LSVZZ…` |
| 7 | 3 tester × 5 条交替两个通道 | **15 条全对**，同一 tester 的序列 `ZZ CC ZZ CC ZZ` |
| 8 | 转发条数对得上 | `转发 24 条，失败 0 条`（2+2+2+1+2+15） |
| 8 | 忙拒记了 | `忙拒 1 条` |
| 8 | 断线作废记了 | `作废 1 条（…结果不转交给下一台诊断仪）` |
| 8 | 同通道真的排过队 | `排队峰值 3，最长排队 62 ms` |

第 3 步的时序是这一步唯一的"并行证据"，摆出来看：

```
t=0      tester A 发慢请求（TA=0x0007，700ms 后才回）
t=200ms  tester B 打 TA=0x0003      → 141ms 后拿到 VIN   （快通道完成，慢的还在睡）
t=782ms  慢通道才拿到 VIN            （慢的确实慢，但没有拖住任何人）
```

如果还是 M9 的"一把锁串行"，B 的 141ms 会变成 **941ms**（排在 A 后面）——这个数字就是判据。

## 总线样本（`candump -L` 原始行，第 4 步那一段）

```
(1795521126.500837) vcan0 7A8#101462F1904C5356   ← 第 1 条的首帧：10 14 = 首帧，长度 0x14（20 字节）
(1795521126.515662) vcan0 7A8#215A5A3030303042   ← 连续帧 1（PCI 21）
(1795521126.531xxx) vcan0 7A8#2237363534333231   ← 连续帧 2（PCI 22）
(1795521126.547xxx) vcan0 7A8#101462F1904C5356   ← 第 2 条的首帧：**从 FF 重新开始**
```

`SEQ=1014 215A 2237 1014 215A 2237` 这一串就是"两条答完再开始下一条"的指纹：
两组 `FF + CF1 + CF2` 背靠背，中间没有一个别人的首帧插进来。
真要交叉了，长成这样：`1014 1014 215A …`——第二个 tester 的首帧把第一个的连续帧挤走，
装配器会因为"SN 不连续"报错，或者干脆把两份答案拼成一份垃圾。

慢通道的同一时刻（注意时间戳差 700ms 以上）：

```
(1795521127.343380) vcan0 7B8#101462F1904C5356
(1795521127.358757) vcan0 7B8#2153533030303053
(1795521127.374827) vcan0 7B8#2237363534333231
```

## 网关的账（退场时打印，逐字抄）

```
  0x8001 ← 0x0E21，3 字节 UDS → 回 0x8002 ACK
  0x8001 已投递（job=21，TA=0x0006），I/O 先回 ACK 不等结果
  job=21 回来 1 条 → 逐条用 0x8001 送回

--- 以太网侧 ---
发现：收到 0 条 UDP，回了 0 条
接入 25，激活 24，诊断请求 25（ACK 25 / NACK 1）
在途丢弃 0 条（结果回来时连接已断），忙拒 1 条（上一条请求还没回）
作废 1 条（连接断开时还在途，结果不转交给下一台诊断仪）
--- CAN 侧 ---
转发 24 条，失败 0 条（其中目标地址不认识 0 条），最长排队 0 ms
  TA=0x0003（0x7A0/0x7A8）：转发 15 条，失败 0 条，发帧 30，收帧 45，超时 0，序号错 0，迟到帧丢弃 0，广播应答 0，排队峰值 3，最长排队 62 ms
  TA=0x0006（0x18DA00F1/0x18DAF100，FD）：转发 7 条，失败 0 条，发帧 7，收帧 7，超时 0，序号错 0，迟到帧丢弃 0，广播应答 0，排队峰值 2，最长排队 0 ms
  TA=0x0007（0x7B0/0x7B8）：转发 2 条，失败 0 条，发帧 4，收帧 6，超时 0，序号错 0，迟到帧丢弃 0，广播应答 0，排队峰值 1，最长排队 0 ms
```

三行账里有三个细节值得看：

- `诊断请求 25` = `转发 24` + `忙拒 1`。忙拒那条**根本没进网关**，所以转发数里没有它——
  如果这两个数加起来不等于诊断请求数，就说明有请求凭空消失了。
- `在途丢弃 0` 与 `作废 1` 是两个不同的东西：作废是"断线时我主动删槽"，
  在途丢弃是"结果回来发现槽没了"。这次删槽在前、结果在后，所以作废了、没丢弃。
  两者同时为 0 才说明断线语义压根没测到。
- `TA=0x0003` 的 `发帧 30` = 15 条 × 2 帧（请求 1 帧，流控 1 帧）。

## 单元断言：492 → 521（新套件 `doip-pool` 29 项）

`include/JobQueue.h` 里全是纯逻辑（没有 socket、没有 CAN），所以这 29 项在内存里一秒跑完：

| 组 | 覆盖 |
|---|---|
| 顺序 | 三条进、三条按 FIFO 出；`depth` 涨落、`peak` 取最大 |
| 满载 | 容量 3 塞第 4 条 → `push` 返回 false，`rejected` 加一 |
| 停机 | `stop()` 后不再收新活，**但已入队的照跑完**；`stop()` 能唤醒阻塞在 `pop` 的线程 |
| 交卷台 | `complete` → `takeAny` 拿回同一个 `id` 和原请求；`pending` 计数对 |
| 超时 | `wait` 超时返回 false，槽被清（不留脏数据） |
| 作废 | `abandon` 之后迟到结果无人接，`pending` 归零 |
| 跨线程 | 一个线程 `pop` 阻塞着，另一个线程 40ms 后 `push`，被唤醒耗时实测 **46ms** |

最后一项是这一步唯一"碰时间"的断言，阈值给得宽（40ms 唤醒、允许 ±10ms），
因为它验的是"能不能醒"，不是"醒得多快"。

## 这一步最容易糊弄过去的地方

- **只看总耗时看不出并行**：三条通道串行跑，总耗时也是三条之和；
  必须像第 3 步那样"在慢的还睡着的时候插一条快的"，且把两条耗时分别打出来。
- **只看网关日志看不出串行**：日志是"谁进了、谁回来了"，交叉发生在总线上。
  第 4 步坚持用 `candump` 取证，就是为了不让自己糊弄自己。
- **断言本身也会错**：`candump -L` 的 data 是十六进制**字符串**，`1014` 的前两个字符 `10` 就是首帧 PCI，
  `14` 是长度。我第一版按"第三、四个字符才是 PCI"写断言，帧序完全正确却报"交叉"——
  断言写错和代码写错长得一模一样，所以脚本先把 `SEQ=` 打出来，人才有可能一眼看出是谁错了。

## 踩到的坑（都留在仓库里了）

1. `-Werror` 抓到死函数：`src/DoIpGateway.cpp` 匿名命名空间里留着 M8 的 `nackFor()`，重写后没人调用。
2. 自测断言写早了：`stop()` 的语义是"不再收新活"，不是"清空"，第一版直接断言 `pop` 立刻返回 false。
3. M9 的日志断言被异步路径打红：`下游答了` 变成 `job=N 回来 N 条`，判据改成 `回来 .* 条|下游答了`。
4. `pendingTarget` 漏赋值：`deliver()` 失败要回 `0x8003`，SA 必须是"请求里的 TA"，初版只存了 tester SA。

## 边界（这一步明确没做的）

- 队列容量写死 8，**没有背压**：满了就 `0x8003 0x08`，tester 自己重试。
- 一条连接同一时刻只许一条在途，**没有流水线**（DoIP 本身也没有请求/响应配对字段）。
- 作废的结果不重试、不缓存，直接落地无声。
- 线程数 = 通道数，没有线程池；几十条通道没问题，几百条不是这个设计的目标。
- 广播仍独占所有通道（按 TA 升序拿锁），没有做"只锁目标通道"的细粒度广播。
- "排队 62ms""快通道 141ms"都是 **vcan0 上的本地量**，vcan 不模拟仲裁与总线负载。
