# M24 验收报告 —— 车队钥匙清单（广播只能投票，搬数据要逐台）

## 1. 目标

M23 的边界里自己写着：**每台 ECU 一张表，没有"钥匙清单广播"，多 ECU 要逐台下发。**

M24 本来要做的是"一条广播几台一起装"。真写下去，被协议改了口径：

| 想广播的事 | 报文长度 | 结果 |
|---|---|---|
| 装一把钥匙 `31 01 02 06 <id><材料>` | 38 | `0x8003` + `0x04 MessageTooLarge`，ECU 零应答 |
| 改钥匙状态 `31 01 02 07 <id><state>` | 8 | 同样发不出去（SF 的 PCI 占 1 字节，7+1=8） |
| 读全表 `22 F1B0` 的响应 | 3 + 3N | 请求能发，响应 9 字节起，回不来 |

原因不是实现偷懒：**功能寻址是"喊一嗓子"，喊完没有任何一个对象可以收流控帧**。多帧传输要 FC 指向唯一接收方，广播场景里那个人不存在。所以功能寻址请求只能 SF（≤7 字节），响应也只能 SF。

于是 M24 的结论定为：

> **广播只能投票，不能搬数据；搬数据要逐台；核对靠摘要。**

## 3. 报文设计

### 3.1 摘要 `0x22 F1B1`（7 字节，可广播）

```text
22 F1 B1  →  62 F1 B1 <总> <启用> <退役> <吊销>
```

四个 u8 计数，正好 7 字节 —— 刚好塞进一个经典单帧。**这不是凑巧，是先确定信封长度再决定接口**。

比读全表（`3+3N`）便宜一个数量级，而且足够回答车队最关心的问题："三台一不一样"。

### 3.2 容量表决 `0x31 01 02 0A`（5 字节，可广播）

```text
31 01 02 0A  →  71 01 02 0A 00   // 能装
                 71 01 02 0A 01   // 表满了
                 71 01 02 0A 02   // 表是坏的（Corrupt），别下发
```

**问句不过门**：谁都能问"你装得下吗"。和 M22 "读表不过门"同一条理由 —— 只读的问题不该要凭证。

### 3.3 车队的顺序

```text
① 广播问一圈   31 01 02 0A   （5 字节，能广播）
② 逐台搬数据   31 01 02 06 … （38 字节，只能物理寻址）
③ 广播对账     22 F1 B1      （7 字节，能广播）
```

## 4. 表决通过 ≠ 装成功

`020A` 只看容量，`0206` 才过门（`0x10 02` + `0x27` 解锁）。所以表决全 00 之后，逐台装仍可能有一台回 `7F 31 7F`。

同一步里放开 `keyService` / `flashGateDenied` 走功能寻址（去掉调用点的 `!onFunc`），**每台用自己那份会话状态过门** —— 广播不会"因为其中一台解锁了就替所有 ECU 放行"。这是广播最容易写错的地方：把"一条请求"误当成"一个上下文"。

## 5. 二十四项验收（两条腿）

| 腿 | 起什么 | 验什么 | 实测 |
|---|---|---|---|
| 一 | 三台健康 ECU，各自一张盘上的表 | 摘要三台一致 | `0003/0006/0007 = 62 F1 B1 02 02 00 00` |
| 一 | 同上 | 广播装钥匙被拒 | `0x8003` NACK `0x04`；`BC_INSTALL_REPLIES=0` |
| 一 | 同上 | 020A 三台都能装 | `7101020A00` ×3 |
| 一 | 同上 | 逐台读全表 | 三台都 `0001=00,0002=00` |
| 一 | 同上 | 逐台装 3 号 | 三台 `7101020600` |
| 一 | 同上 | 摘要跟着变 | `3/3/0/0` ×3 |
| 一 | 同上 | 只退役 `0x0003` 一台 | `0003:3/2/1/0`，另两台仍 `3/3/0/0` |
| 一 | 同上 | 补齐两台 | 三台回到 `3/2/1/0` |
| 一 | 同上 | 三台一起吊销 1 号 | `3/1/1/1` ×3 |
| 二 | 同上，但 `0x0006` 的表文件砍掉 10 字节 | 启动判 Corrupt | 表空；`0206` 回 `7F 31 22` |
| 二 | 同上 | 表决 2 对 1 错 | `00` / `02` / `00` |
| 二 | 同上 | 逐台装 4 号 | `00` / `7F 31 22` / `00` |
| 二 | 同上 | 汇总如实 | `成 2 / 拒 1` |
| 二 | 同上 | 摘要分叉 | `4/2/1/1` vs `0/0/0/0` |
| 二 | 同上 | 一致性点名 | `不一致，0006 的摘要与 0x0003 不同` |

腿一"只退役一台、摘要立刻分叉"，就是广播对账的意义：三台 `3/2/1/0 / 3/3/0/0 / 3/3/0/0` 摆在一起，车队出问题第一眼能看见。

腿二"成 2 / 拒 1"必须如实报：**车队操作没有事务**。没有"全成或全败"，只有"各自报各自的"，只能收齐再算，算完还要点名。

## 6. 踩到的坑：验收脚本自己撒了谎

首跑：`BC_DIGEST_COUNT=1`、`BC_CAP` 少一台、`BC_CAP_PARTIAL` 只剩一台，**每次缺的还不一样** → 通过 6 项、失败 16 项。

排查顺序与结论：

1. 先怀疑网关的 `broadcastLocked` —— 没找到问题；
2. `candump` 看总线：**三台每次都答了**，`7A8 / 18DAF100 / 7B8` 一帧不少；
3. 网关日志：`job=1 流式送达 1 条` ×3、`回来 3 条` —— 网关也发了三条；
4. 问题在脚本：`parse(self.s.recv(8192))` **一次 `recv` 只解析第一条 DoIP 消息**。三条应答几乎同时到，被内核塞进同一个 TCP 段，剩下两条被静默丢掉。

修法：给 `Tester` 加报文缓冲区，按 `len` 字段切分（`next_msg`），不够就再读一段。

教训不是"记得写缓冲区"，而是：**DoIP 是面向流的，一条 `recv` 不等于一条消息**。M11/M12 只收两三台、应答隔得开，侥幸没撞上；三台一起答就撞上了。**验收脚本撒谎的方向是"产品坏了"，最容易被误信。**

## 7. 结构改动

- `tools/stub_ecu.cpp`：`keyService` 头加 `0x22 F1B1` 摘要与 `0x31 01 02 0A` 表决；调用点去掉 `!onFunc`（钥匙服务与门禁允许功能寻址）；banner 增一行。
- `tools/m24_check.py`：新增（`Tester` 带报文缓冲 + `broadcast()` 返回 `(replies, nack)` + 摘要/表决/逐台/一致性核对）。
- `tools/m24_e2e.sh`：新增（两条腿、五个进程、24 项）。
- `tools/ci_local.sh`：27 → 28 步（40 → 41 项）。
- 产品代码**零改动**：M8/M12 的广播与流式交付原样可用，改的只是"什么东西适合广播"。

## 8. 边界

- **没有车队级事务**：中途一台失败就是"成 N 拒 1"，回滚要靠上层再来一轮。
- **摘要只有计数**：能说"不一致"，不能说"哪一把不一致"；定位还得逐台读全表。
- **没有版本号**：两次广播之间被改过，计数可能又对上了；要真清单版本（类似 `FF02` 的清单 id）。
- **功能寻址仍限经典单帧**：给 `--func` 加 `:fd`（广播走 62 字节单帧）可行，但要同改 `FunctionalRoute`、`parseFunctional`、`broadcastLocked`、`sendFunctional` 四处，本步没做。
