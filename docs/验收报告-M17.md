# M17 验收报告 —— 0x11 ECUReset（硬复位 / 点火循环 / 软复位）

## 1. 目标

到 M16 为止，门禁、刷写、校验都跑通了，但刷完的 ECU 还停在编程会话里：
新程序要重启一次才生效。`0x11` 就是这个"重启"。

它是全项目第一条**答完之后立刻改变整机状态**的服务，所以它验收的不是码，是三件事：

1. 应答与动作的先后（先 `51 xx`，后复位）；
2. 复位带走什么、留下什么；
3. 什么时刻不许复位。

## 2. 复现

```bash
cd ~/doip-gw
cmake --build build -j4
./build/reset-selftest                # 47 项，纯内存，不需要 vcan0
bash tools/m17_e2e.sh 13477           # 三十三项，约 40 秒
bash tools/ci_local.sh gcc            # 21 步 34 项
```

依赖：`vcan0`、`build/stub-ecu`、`python3`（场景脚本裸 socket）。

## 3. 拓扑

- 网关：`--iface vcan0 --port 13477`，路由 `0003:7A0:7A8`
- 一台 ECU：`stub-ecu --rx 7A0 --tx 7A8 --flash --secure --seconds 24`
- 第二条腿（端口 13478）：同一台 ECU 去掉 `--secure`，验老路径

## 4. 三个子功能

| 子功能 | 名字 | 状态 | 镜像 | 正响应 |
|---|---|---|---|---|
| `01` | hardReset | 会话/解锁/锁计数全清 | **清掉** | `51 01` |
| `02` | keyOffOnReset | 同上（本实现立刻执行） | 清掉 | `51 02` |
| `03` | softReset | 同上 | **保留** | `51 03` |
| `04` | — | 不认 | — | `7F 11 12` |
| （无子功能） | — | 长度错 | — | `7F 11 13` |

## 6. 为什么"先回包、再复位"必须写在代码顺序上

`0x11 01` 真正执行以后 ECU 就没电了。如果代码写成"先复位、后组应答"，
那条 `51 01` 永远发不出去，诊断仪只能看到超时 —— 然后去怀疑网关、线束、对端。

所以 `SessionGuard` 只做两件事：回包、把状态清零，并把"待执行复位"挂起来；
`stub-ecu` 把应答 `sendUds()` 发出去之后，才调 `takePendingReset()` 执行真正的动作。
顺序在代码里是**物理可见**的，不靠注释保证。

自测里钉了一条：`takePendingReset()` 取到 `01` 之后再取必须是 `00` —— 同一个复位不会执行两遍。

## 7. 三个 `0x22`，三种意思

| 请求 | 回 | 意思 |
|---|---|---|
| `0x34` 在没擦除时 | `7F 34 22` | 条件不满足：先 `0x31 FF00` |
| `0x31 01 FF01` 在空镜像时 | `7F 31 22` | 没有镜像可校验（**不是**校验失败） |
| `0x11` 在下载中途 | `7F 11 22` | 半截镜像不许当完整镜像用（变砖路径） |

第三个最值得记：刷写中途复位是真实产线上"变砖"的经典原因。而且脚本不只验"回了 22"，
还紧接着 `0x37` 验 CRC —— **拒绝必须是"什么都没动"**，不是"拒了但已经乱了"。

## 8. 硬复位 vs 软复位：镜像的两套语义

| 复位 | 会话 | 解锁 | 锁计数 | 镜像 | 擦除标记 |
|---|---|---|---|---|---|
| `03` 软复位 | 默认 | 清 | 清 | **保留** | 保留 |
| `01` 硬复位 | 默认 | 清 | 清 | **清** | 回到未擦除 |
| `02` 点火循环 | 默认 | 清 | 清 | 清 | 回到未擦除 |

"硬复位清镜像"不是随口说的：M15 的边界里写了"镜像是 RAM 里的，掉电即失"。
M17 把这个边界**变成一个可断言的行为** —— 硬复位后同一份 CRC 校验会撞 `0x22`（无镜像），
而软复位后同一份 CRC 照样通过。两条都在脚本里。

## 9. 单元断言：809 → 856 项（新套件 `doip-reset` 47 项）

| 组 | 覆盖 |
|---|---|
| 子功能 | `51 01/02/03` 各两字节；`04` → `0x12`；被拒的不记账 |
| 取用 | `takePendingReset()` 一次生效、二次为 0 |
| 默认会话 | 新 guard 直接 `0x11 01` → `51 01` |
| 清状态 | 编程会话+解锁 → `0x11 03` → 默认、未解锁、刷写关门、种子/计数清零；复位后交密钥 → `7F 27 7F` |
| 清锁 | 3 次错 → `0x36` + 锁 10 秒 → `0x11 01` → 锁没了、计数 0、立刻可要种子 |
| 刷写中途 | `0x11 01`（busy）→ `0x22`，会话与解锁都不动、不留待执行 |
| 镜像 | 刷 8 字节 → `powerCycle()` → 空镜像、未擦除、`receipts` 仍 1、再 `0x34` → `0x22` |
| S3 | 复位重置活动时间；复位不计 S3 超时；默认会话 tick 不产生超时 |
| 记账 | 硬 2 / 点火循环 1 / 软 1 |

## 10. 这一遍的四个判断题

1. **`SessionGuard` 该不该知道 `FlashTarget`**：不该。只传一个 `flashInProgress` 布尔，
   镜像怎么清是调用方的事 —— 否则会话层和刷写层粘在一起。
2. **`0x11` 放 `sessionService` 还是 `flashService`**：会话层。它不属于刷写，默认会话里也要能答。
3. **被拒的复位要不要清状态**：不清。"拒绝"的语义是"什么都没发生"。
4. **`receipts` 要不要随复位清**：不清。它是终身账；"镜像 0 字节"才是现状。
   两个数混在一起，日志就会骗人（这次的退场账正好把两者并排印出来）。

## 11. M17 之后仍然没有的

- `02` 点火循环在本实现里立刻执行，没有"等下一次点火"的挂起状态（真机要等 KL15 动作）。
- 复位是软件模拟：没有真正的进程重启、没有冷启动自检、没有启动时间。
- `0x11 01` 在真机上会让连接断开；本项目是网关中继，ECU "重启"后连接照旧（边界写在 README）。
- 锁计数仍在 RAM：真机常存 NVM，`03` 软复位不该清锁，我们是三种都清（简化）。
- 没有 `0x11` 的 `powerDownTime` 附加参数（ISO 里硬复位可带）。
- 没有"复位后 ECU 主动回一条 0x0005/路由激活"之类的重连流程。
