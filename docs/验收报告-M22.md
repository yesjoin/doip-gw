# M22 验收报告 —— 把写死的钥匙变成一张活的表（0x22 F1B0 / 0x31 01 02 06 / 0x31 01 02 07）

## 1. 目标

从 M18 到 M21，钥匙是**写死在源码里**的：`demoKey(0x0001)`、`demoKey(0x0002)`，`lookupKey()`
一个 `switch` 查完。演示够用，现场不够用，因为有三件事一件也做不了：

| 现场要什么 | 写死钥匙的现状 |
|---|---|
| 按期轮换：新包用新钥匙签，老包还在路上 | 换钥匙 = 改源码 + 发固件 |
| 泄露后立刻拒收 | 没有"拒收"这个动作，只能等固件 |
| 审计"这台车现在认哪几把钥匙" | 只有看代码 / 看文档 |

M22 把钥匙做成一张**能在总线上读写**的表：

- 新头文件 `include/KeyRing.h`：定长 **8** 把，每把 `<id u16, key SHA-256, state>`；
- 三个状态：`00 启用 / 01 退役 / 02 吊销`；
- 新服务 `0x22 F1B0`（读表）、`0x31 01 02 06`（装钥匙）、`0x31 01 02 07`（改状态）；
- `fw::checkEnvelope` / `fw::verify` 多一个"带表"的重载，验签认**这台车自己的表**。

## 3. 状态机：为什么是三态而不是两态

```
Unknown ──install──► Active ──retire──► Retiring ──revoke──► Revoked
                       ▲                   │                  │
                       └──── revive ───────┘            终态，出不去
```

| 状态 | 能干什么 | 为什么需要这一档 |
|---|---|---|
| `00` 启用 | 验、签都行 | 正常状态 |
| `01` 退役 | **只验不签** | 直接删会让"已签好还没刷"的在途包突然验不过；退役让它继续能验，日志记一笔"退役钥匙" |
| `02` 吊销 | 拒收 | 钥匙不可信的前提，必须**终态**：复活等于把泄露的钥匙重新启用，要恢复只能装**新 keyId** |

`Active ⇄ Retiring` 双向放行（现场回滚很常见）；`Revoked` 出不去（`Transition::Immutable`）。

## 4. 三条安装规矩

1. **只在空槽成功**：同 id 第二次装，不看材料，一律 `Install::Exists` → `01`。
   理由：允许覆盖等于"知道旧钥匙的人可以把自己的材料顶进 Active 槽"，钥匙管理就变成谁先来谁说了算。
2. **keyId 0 不许装**：`Install::BadId` → `01`。0 是"没有 id"的意思，真装进去以后日志里分不出"0 号钥匙"和"没钥匙"。
3. **表满只报错、不扩容**：8 把定长 → `Install::Full` → `7F 31 22`。车控里装钥匙不该触发动态分配；
   "满了"是明确状态，比 OOM 好排查。

## 5. 三个服务，两种性质

| 请求 | 干什么 | 过门吗 |
|---|---|---|
| `22 F1 B0` | 读表：`62 F1 B0` + 每把 3 字节 `<id u16><状态>`，按 id 升序 | **不过**（它只是问） |
| `31 01 02 06` + `<id u16><32 字节材料>` | 装一把新钥匙 | 过（编程会话 + 0x27 解锁） |
| `31 01 02 07` + `<id u16><目标状态>` | 改状态 | 过（同上） |

**装钥匙为什么要过门**：装进去的钥匙能签出"验得过"的包，等价于**发证书**。
谁能装钥匙，谁就能给这台车签任何包。

**读表为什么不过门**：它不改任何东西；而且默认会话里的诊断仪本来就该能问
"我要解锁了，这车认不认我这个包"。

| 情况 | 回答 |
|---|---|
| `0206` 材料不是 34 字节 | `7F 31 13` |
| `0206` 装上 | `71 01 02 06 00` |
| `0206` 同 id / keyId 0 | `71 01 02 06 01` |
| `0206` 表满 | `7F 31 22` |
| `0207` 状态字节 > 02 | `7F 31 31`（请求里写了非法值 → NRC） |
| `0207` 改成功 | `71 01 02 07 00` |
| `0207` 表里没有 / 已是吊销 | `71 01 02 07 01` |

## 6. 和清单的关系：同一份包，钥匙状态不同，结论不同

`checkEnvelope` 查表三分：

| 表里的情况 | 结论 | FF02 / 0205 的回答 |
|---|---|---|
| 没有这个 keyId | `UnknownKey` | `7F 31 31` |
| 状态 `02` 吊销 | `RevokedKey` | `7F 31 31` |
| 状态 `01` 退役 | 照验，`Check.keyState = Retiring` | `71 01 FF 02 00`，日志注明"退役钥匙" |

`RevokedKey` 与 `BadTag` 分开，理由是现场处置完全不同：
`BadTag` = 包被改过，找供应商；`RevokedKey` = 包可能是泄露的密钥签的，**别刷，先查钥匙**。

带表的两个入口：

```cpp
fw::checkEnvelope (manifest, keyRing);      // 信封 + 身份 + 这台车的表
fw::verify        (image, manifest, keyRing);
```

不传表的老重载保留（内部走 `demoRing()`，1/2 号都启用），所以 M18–M21 的单元断言**一条没动**。

## 7. 顺手补的一个洞：`0205` 纳入门禁

M21 里 `0205`（预检）没过门，理由是"它只是问"。但它会**发凭证** —— 它其实是"做"。
M22 把 `0205` 和 `0206` / `0207` 一起挂到 `flashGateDenied`。

真正拦住危害的是 `0x34` 自己的解锁要求（没解锁也下载不了），所以 M21 没出事故；
但"发凭证算动作"这件事必须在门口说清，不能靠下游兜底。

同一次改动修掉一个越界隐患：门禁判定原本先读 `req[3]` 再判长度，`31 01` 这种短请求会读越界，
改成 `req.size() >= 4 && req[1] == 0x01` 之后才读。

## 9. 单元断言：960 → 991 项（新套件 `doip-keyring` 31 项）

```
A 安装            5 项   空表 / 装一把 / 同 id 被拒且不改原材料 / keyId 0 / 表满
B 状态机          6 项   启用→退役→启用→吊销→终态 / 不存在
C 查表与计数      5 项   找得到 / 找不到 / 三态各一把 / dump 形状 / 状态码 00-01-02
D 钥匙 × 清单    15 项   启用通过 / 退役照验且 keyState 带回 / 吊销 RevokedKey /
                         不认识 UnknownKey / 补装后同一份包立刻能过 /
                         传表与不传表两条路 / 演示表说验得过而这台车的表说吊销 /
                         老路径的 v1、v2 全都还在
```

关键一条是 **D10**：同一份清单，`demoRing()` 说"验得过"，而手搭的"1 号已吊销"表说 `RevokedKey` ——
同一个函数、同一份数据，结论只取决于**谁的表**。

`ctest` 十八套件全绿：`94/57/72/73/96/100/29/45/27/43/58/54/61/47/46/24/34/**31**` = **991 项**。

## 10. 踩到的坑

1. **`find` 只有一个 `const` 重载**：`setState` 里拿到 `const Entry*` 赋给 `Entry*`，编译直接拒。
   补一个非 const 重载 —— 写两遍循环比 `const_cast` 直白。
2. **e2e 的取值函数把值切断了**：`grab()` 用 `cut -d= -f2`，而读表的值本身是 `0001=00,0002=00` ——
   第一个 `=` 就把后半截切没了，六条断言全红。改成 `cut -d= -f2-`。
   **"测试脚本自己出错"看起来和被测代码出错一模一样**，这一步又验证了一次。
3. **门禁里差点越界**：见 §7 末尾。
4. **M22 改了日志措辞，把 M18 的 e2e 弄红了**：旧断言 `grep "验签：keyId 0x255 不认识"`，
   而新日志是 `keyId 0x00FF 不在钥匙表里`（多了表的内容，格式也从十进制变成 `%04X`）。
   断言跟着改；**这不是新代码的 bug，是"文案也是接口"的代价**。
   之后单独重跑 m18 全红（26 项取值为空），根因是上一次被 kill 的 CI 留下的
   `doip-gateway` / `stub-ecu` 还占着 vcan0 与端口，`pkill -x` 清干净后 27 项全绿。

## 11. 结构改动：`FlashContext` 加一项

```cpp
const keys::KeyRing *ring = nullptr;   // 验签要用这台车**自己的**钥匙表
```

M21 那句"结论取决于谁的表"到这里才真正落地 —— 之前只是清单里带着身份，
现在连"用哪把钥匙验"都是从表里查的。

## 12. 边界

- 钥匙材料明文放 RAM；真机要放 NVM + 加密，或者直接进 HSM。
- 没有时间维度：没有有效期、没有"用几次自动退役"。
- 仍是对称 MAC：换钥匙换的是**共享密钥**，不解决"防内部伪造"（那要非对称签名）。
- 表不持久化：进程重启回到默认两把。真机重启不能把吊销记录丢了。
- 吊销只在本地生效：多 ECU 场景下每台车要各自下发，没有"钥匙清单广播"这种机制。
