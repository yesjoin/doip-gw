# M9 验收报告：CAN FD（同一套 ISO-TP，换个 64 字节的信封）

验收目标不是"能发一条 64 字节的帧"，而是**证明分片规则跟着信封一起变了、而且两条通道的结果能对上**：
同一个 200 字节的响应，FD 要 4 帧、经典要 29 帧，拆完再装回去必须**逐字节相同**。
只验"收得到"，等于没验——按 8 字节硬编码也能收得到，只是帧数是错的。

- 复现：`bash tools/m9_e2e.sh 13465`（自起两台 ECU + 网关 + 总线录制，约 45 秒）
- 结果：**通过 20 项，失败 0 项**；单元断言 492 条（6 套件，`doip-isotp` 由 70 → **96**）；
  `ci_local.sh` **13 步 26 项**全绿

## 拓扑（同一条 vcan0，一张路由表两种信封）

| 角色 | 逻辑地址 | CAN 收发 | 帧长 | VIN / HW |
|---|---|---|---|---|
| 网关实体 | `0x0001` | — | — | UDP 发现声明 VIN `LSVAA0000A1234567` |
| ECU_C（`stub-ecu`） | `TA=0x0003` | `7A0`/`7A8`（11 位） | 经典 8 字节 | VIN `LSVZZ0000B7654321`，HW `HW02` |
| ECU_FD（`stub-ecu --fd`） | `TA=0x0006` | `18DA00F1`/`18DAF100`（29 位） | FD 64 字节 | VIN `LSVCC0000C7654321`，HW `HW03` |

环境前提：`vcan0` 的 MTU 必须 ≥ 72（FD 帧结构体就是 72 字节）。

## 七步二十项

| # | 要证明的事 | 实测 |
|---|---|---|
| 0 | vcan 装得下 FD 帧 | MTU = 72 |
| 1 | 一张表里两种信封各自标对 | `TA=0x0006 → 0x18DA00F1 / 0x18DAF100（FD，帧长 64）`、`TA=0x0003 → 0x7A0 / 0x7A8` |
| 1 | ECU 侧的自我声明也要对上 | FD 那台打印 `CAN FD（帧长 64，单帧最多 62 字节）`，经典那台打印 `帧长 8，单帧 7 字节` |
| 2 | FD 读 `0xF1A2`（200 字节） | 内容逐字节正确；总线恰好 **4 帧**；每帧 64 字节 |
| 3 | 经典读同一个 DID | 内容与 FD **逐字节相同**；总线 **29 帧** |
| 4 | 边界 `0xF1A0`（62 字节 = FD 单帧上限） | FD **1 帧**（转义单帧 `00 3E …`）；经典 **9 帧** |
| 5 | VIN（20 字节，落进 8..62 空档） | FD **1 帧**（`00 14 …`）；经典 **3 帧**（FF 装 6，余 14 分两张 CF） |
| 6 | 网关的账 | 每条请求都记了应答条数，零失败 |

手算对照（这一步是给人核的，脚本只是复读）：

| DID | 响应总长 | FD 帧数 | 经典帧数 |
|---|---|---|---|
| `0xF1A0` | 62 = 3 + 59 | 1（`00 3E` + 62） | 9（FF 6 + 8×7 = 62） |
| `0xF1A1` | 103 = 3 + 100 | 2（FF 62 + CF 41） | 15（FF 6 + 14×7 = 104，末帧补 1 字节空） |
| `0xF1A2` | 200 = 3 + 197 | 4（FF 62 + 3×63 = 251 装载，实际 200） | 29（FF 6 + 28×7 = 202） |

## 总线样本（`candump -L` 原始行）

FD 帧是**双井号**，`##` 后第一位是 FD flags，之后才是数据；经典帧是单井号。

```
(1795518964.245064) vcan0 18DAF100##410C862F1A2000102030405...   ← FD 首帧：10 C8 62 F1 A2 00 …（0xC8=200）
(1795518964.258806) vcan0 18DAF100##4213B3C3D3E3F4041...        ← FD 连续帧 1：21 3B 3C 3D …（63 字节）
(1795518964.273852) vcan0 18DAF100##4227A7B7C7D7E7F8081...      ← FD 连续帧 2：22 7B 7C …
(1795518964.289525) vcan0 18DAF100##423B9BABBBCBDBEBFC0...      ← FD 连续帧 3：23 9B 9C …（末帧补零）
```

经典通道同一个 DID 的开头两帧（同一时刻的另一条通道）：

```
(1795518965.337122) vcan0 7A8#10C862F1A2000102     ← 首帧只带 6 字节
(1795518965.352015) vcan0 7A8#2103040506070809     ← 连续帧带 7 字节
```

注意首帧两个通道的**长度字节完全一样**（`10 C8`），差别只在后面能塞多少——
这也说明长度字段、SN、流控都没变，变的只是信封。

## 网关的账（三个 DID × 两条通道）

```
TA=0x0003（0x7A0/0x7A8）：转发 3 条，失败 0 条，发帧 6，收帧 41，超时 0，序号错 0，迟到帧丢弃 0
TA=0x0006（0x18DA00F1/0x18DAF100，FD）：转发 3 条，失败 0 条，发帧 4，收帧 6，超时 0，序号错 0，迟到帧丢弃 0
```

这两行的对比就是 M9 的全部结论：

- 经典通道：发 6 帧（3 条请求 + 3 张流控），**收 41 帧**（29 + 9 + 3）
- FD 通道：发 4 帧（3 条请求 + 1 张流控，只有 200 字节那条需要），**收 6 帧**（4 + 1 + 1）

同样是三次读 DID，通信量差了 6.8 倍。这不是性能数字，是**信封大小直接决定的东西**。

## 单元断言 26 项（`doip-isotp` 70 → 96）

| 组 | 覆盖 |
|---|---|
| 单帧边界 | 7 字节仍是 `0x07`；8 字节变 `00 08`；62 字节 `00 3E`（上限）；63 字节溢出 → 首帧 `10 3F`；首帧写满 64 字节 |
| 分片 | 200 字节 = 4 帧；首帧带 62（`frameBytes-2`）；CF 带 63（`frameBytes-1`）；`consecutiveFrameCount(200,64)=3`、`(200,8)=28` |
| 往返 | 62 / 63 / 200 / 1000 字节在 FD 下拆了再装，字节全等 |
| 严格校验 | 转义单帧声明 ≤7 → 报错（该用 `0x0N`）；经典信封里"转义单帧声称 20 字节" → 报错（超上限 6）；首帧声称总长 ≤7 → 报错 |
| 流控 | FD 流控头部 `0x30`，尾部补齐到第 64 字节 |

## 踩到的坑

**① `#if defined (CAN_RAW_FD_FRAMES)` 永远为假 —— 这是本里程碑的真 bug。**

`CAN_RAW_FD_FRAMES` 在 `linux/can/raw.h` 里是 enum 成员，不是 `#define`，`defined()` 只认宏。
于是 `setsockopt` 那 6 行被静默编译掉了：编译不报、单测不报（单测不碰 socket），
现场表现是 `write` 回 `EINVAL` → 网关记 `0x8003 0x08` → 诊断仪超时。

```
strace 证据：write(3, "...", 72) = -1 EINVAL；日志里压根没有 setsockopt(...CAN_RAW_FD_FRAMES...)
```

**② 这类错误纯逻辑测不到。** 只有 `strace`/抓包能抓住——所以每个里程碑都必须有一条真总线上的脚本，
这不是"额外装饰"，是唯一的兜底。

**③ `vcan0` 的 MTU 要 ≥ 72。** 不满足时 FD 帧直接被丢，现象还是"全超时"；`m9_e2e.sh` 第 0 步先查，
不够就 `[SKIP]`（环境问题不算代码红）。

**④ 脚本里 `stub-ecu` 的日志被全缓冲吃掉了。** 重定向到文件时 stdout 变全缓冲，启动行迟迟不落盘，
前两项断言读到空文件。加 `stdbuf -oL` 就对了——这是"日志即证据"的脚本通病。

## 已知边界

- 只做**固定 64 字节** FD 帧，不支持 8/12/16/20/24/32/48 这些短 FD 帧（真实网络按 DLC 变长）。
- 不发 `BRS`，数据段速率 = 仲裁段速率；位定时不在本项目范围内。
- 一条 `--iface`，FD/经典混挂在**同一条总线**上；真实网关是多路 CAN 各走各的。
- `0xF1A1`（103 字节）只在 `stub-ecu` 里备着，端到端没验这一档（两帧边界由 62/200 两头夹住）。
- `candump -L` 的 FD flags 位数依赖 can-utils 版本，取证用的 `awk` 换版本可能要调。
