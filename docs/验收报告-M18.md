# M18 验收报告 —— 刷写包完整性（SHA-256 + 76 字节清单 + 标签）

## 1. 目标

M15 的 `0x37` 已经带 CRC-32，看起来"完整性"做完了。但 CRC 是线性的：
改几个字节再补一个补偿值，CRC 照样对上。它回答"传的过程有没有出错"，不回答"这是不是原来那份包"。

M18 补的是后者，分两层：

- **哈希**（SHA-256）管"内容"：镜像改一个比特，摘要整条变；
- **标签**（对称 MAC）管"这包是谁做的"：证明"知道钥匙"，但不证明"是厂商"（那要非对称签名）。

## 2. 复现

```bash
cd ~/doip-gw
cmake --build build -j4
./build/integrity-selftest            # 28 项，纯内存，不需要 vcan0
bash tools/m18_e2e.sh 13479           # 二十七项，约 30 秒
bash tools/ci_local.sh gcc            # 22 步 35 项
```

依赖：`vcan0`、`build/stub-ecu`、`python3`（清单由 python 的 hashlib 拼，ECU 用 C++ 的 Sha256 算）。

## 3. 清单格式（76 字节，版本化）

| 偏移 | 内容 | 说明 |
|---|---|---|
| 0–3 | `DGIM` | magic |
| 4 | `0x01` | 版本 |
| 5 | `0x00` | flags（保留） |
| 6–9 | imageLen | u32 大端 |
| 10–41 | imageSha | SHA-256(镜像) |
| 42–43 | keyId | u16 大端（`0x0001`/`0x0002`） |
| 44–75 | tag | SHA-256(前 44 字节 ‖ 钥匙) |

服务入口：`0x31 01 FF02` + 76 字节作为 routine option record。
`FF00` 擦除、`FF01` 校验、`FF02` 验签，一条 `0x31` 三种例程。

## 4. 二十七项（摘要）

| # | 验什么 | 实测 |
|---|---|---|
| 1 | 启动行声明格式与钥匙 | `验签：0x31 01 FF02 收 76 字节清单…认识的钥匙是 0x0001/0x0002` |
| 2 | 场景脚本自洽 | `FAIL=0` |
| 3 | 没解锁时 FF02 被门挡 | `NRC_FF02_DEFAULT=7F` |
| 4–8 | 解锁/擦除/`0x34`/`0x36`/`0x37` | `OK`、`7101FF00`、`74200022`、`7601`、CRC `DBBD6AF1` |
| 9 | CRC 仍对（M15 那层没被改） | `CRC_MATCH=1` |
| 10 | 正确清单 | `VERIFY_OK=7101FF0200` |
| 11 | 标签用错钥匙 | `BAD_TAG=…01` |
| 12 | 长度写错但重盖标签 | `LEN_MISMATCH=…01` |
| 13 | 哈希写错但重盖标签 | `SHA_MISMATCH=…01` |
| 14 | 清单 75 字节 | `NRC_LEN=13` |
| 15–17 | magic / 版本 / keyId 不认识 | `31 / 31 / 31` |
| 18–20 | 换一份镜像再刷 | `74200022`、`7601`、CRC `B2DE2642` |
| 21 | **原清单验换过的镜像** | `PACKAGE_SWAP=…01` |
| 22–23 | 硬复位清镜像 → 验签 | `5101`、`NRC_EMPTY=22` |

## 5. 为什么自己做 SHA-256

哈希最怕"差不多"。自己写的混淆能过自己的测试，过不了标准向量。所以先钉三条：

```
sha256("")             = e3b0c442…b7852b855
sha256("abc")          = ba7816bf…f20015ad
sha256(448 位标准向量)  = 248d6a61…19db06c1      ← 跨 64 字节块，补位最容易错的地方
```

再补一条工程判据：逐字节 / 分三段 / 一次算，三条路径必须同一个摘要（否则流式与一次性会在某长度分叉）；
长度扫 0/1/54/55/56/63/64/65/128 全部一致。最后一条：只差一个字符，"package-A" 与 "package-B" 摘要必须不同。

## 6. 校验顺序：先便宜后贵

```
长度 76 → magic/版本 → keyId → 标签（44 字节）→ 镜像哈希（整包）
```

镜像可能几兆，标签只有 44 字节。便宜的先拒，贵的后算。

## 7. NRC 与状态 01 的分界

| 情况 | 回 | 分界 |
|---|---|---|
| 75 字节 / magic / 版本 / keyId | `7F 31 13` / `7F 31 31` | **请求本身不合法** |
| 标签 / 长度 / 哈希 | `71 01 FF 02 01` | 请求合法，**包不对** |
| 通过 | `71 01 FF 02 00` | |
| 空镜像 | `7F 31 22` | 条件不满足（先 `0x34/0x36`） |

状态字节只有一个，装不下三种原因 —— 三种原因进日志，脚本断言日志文本。

## 8. MAC ≠ 签名

- 本项目：双方共用钥匙（写在源码里）。能证明"知道钥匙的人做的"，不能证明"厂商做的"。
- 真车厂：私钥签、公钥验。拿到公钥只能验，做不出包。

所以这个层的定位是"防顺手换包"，不是"防对手伪造"。要后者得引入非对称签名（密钥、证书、吊销），
本里程碑不做。

## 9. 单元断言：856 → 884 项（新套件 `doip-integrity` 28 项）

覆盖三条标准向量、分块等价、长度边界扫描、清单六字段、正例、三类内容错、四类结构错、
钥匙互换（同一镜像不同钥匙清单不同、冒充标签验不过）、1000 字节镜像改末字节也验不过。

## 10. 这一遍踩的坑

**断言"长度不符 → `LengthMismatch`"跑出来是 `BadTag`。**
不是顺序写错，是设计在保护自己：标签盖的是整个 44 字节头（含长度），
任何"没重算标签的改动"第一步就撞标签，轮不到长度判定。
要验 `LengthMismatch` 必须模拟真实失误：改完长度再用钥匙重盖标签。
这条已写进自测，并在断言文案里点明"标签绑住整个头"。

## 11. M18 之后仍然没有的

- 对称 MAC，不是非对称签名：钥匙在源码里。
- 只有一把钥匙两个 ID，没有轮换、吊销、证书链。
- 不验"这个包该不该刷"（降级、零件号、VIN 策略都没有）。
- 没有多段镜像的清单树，没有"验不过自动回滚"。
- SHA-256 是软件实现：没有耗时预算，验签时间可能超过 `P2*`。
