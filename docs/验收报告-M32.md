# 验收报告 · M32：响应方向也按 DID 过滤

> 项目三 `doip-gw`（DoIP 诊断网关）· 第 33 个里程碑
> 一句话：**M30/M31 挡"想读什么"，M32 挡"数据往哪流"——出口再查一道。**

---

## 1. 这一步要解决的问题

M30 按服务号分三档、M31 按 DID 抬档，但两者都拦在**请求侧**：诊断仪发出 `0x22` 的那一刻。

可数据的真实流向是：

```
诊断仪 --22 F1B0--> 网关 --(放行)--> ECU --62 F1B0 <钥匙表数据>--> 网关 --> 诊断仪
```

请求侧被绕过时（哪怕配置漏写一条 DID，或者某台 ECU 自己没按档位答），
`0x62` 照样带着数据从网关流出去。纵深防御的第一条就是：**别指望前面那层一定没破。**

M32 在**出口**上再查一次：ECU 答回来的 `62 <DID>` 同样按 DID 级别要档，不够档就这条 `0x62` 不发出去。

## 3. 机制：同一张表，查出口

```cpp
bool classifyResponse(uds, len, DidInfo&)   // 只认 0x62 且长度 ≥3
Tier needForResponse(table, uds, len, out)  // 62 <DID> → tierOf(该 DID 的级别)
                                            // 非 DID 响应 → 返回 Read 且 out.isRead=false
bool responseDenied(sa, uds, why)           // 出口处调一次；不够档就 return true
```

`needForResponse` 与请求侧的 `needFor` 用**同一张 `didTable`**、**同一个 `tierOf` 映射**、
**同一张 `PermissionTable::decide`**。没有另造阶梯 —— 响应方向只是换了个调用时机：

- 请求侧：`classify` 之后、转发之前；
- 响应侧：`deliver()` 每条 reply 发送前、`drainStream()` 数据出网卡前一刻。

两个方向可以独立开关：`--did-guard`（请求侧）与 `--did-guard-resp`（响应侧）默认都关，可分别对照验证。

## 4. 四个口径

1. **只碰 `0x62`**：`7F` 负响应、`50` 会话控制、`71` 普通正响应都不是数据外流，`needForResponse` 返回 `Read` 且 `isRead=false`，调用方先看 `isRead` 再决定拦不拦。
2. **拦截 = 这条 `0x62` 不发**：诊断仪那侧等到超时，而不是收到 `7F`。`7F` 是"这事不做"，此时数据已经在网关里了；不说清这一点，会把"出口拦截"误读成"请求被拒"。
3. **独立开关，默认都关**：响应过滤是纵深防御的下一层，不是替代请求侧。两层都开时请求侧先挡（根本到不了出口）。
4. **退账两行分开报**：请求侧挡 0 条、响应侧挡 N 条 = 有路在漏请求，看退账就能发现，而不是靠猜。

## 5. 命令行与日志

```bash
# 故意**不开** --did-guard：只靠响应侧这道闸，验它能不能独立兜住
./build/doip-gateway --iface vcan0 --port 13508 --seconds 20 \
    --route 0x0006:18DA00F1:18DAF100:网关ECU --power-mode 1 \
    --enforce-ops --grant 0E00:read --grant 0E01:write --grant 0E02:flash --default-grant read \
    --did-guard-resp --did-default guarded \
    --did F190:open --did F184:guarded --did F1B0:secret
```

```text
DID 白名单：关（0x22 读什么都按「读」档；加 --did-guard 才分 DID）
DID 白名单（响应）：开（62 <DID> 同样按级别检查；不够档的响应不发给诊断仪 —— 数据不出去）
```

```text
响应挡回：要给 SA 0x0E00 的「读响应 DID 0xF1B0（钥匙表，锁死级）」(刷写档)，但它只有「读」→ 这条 0x62 不发给诊断仪（数据不出去）
DID 白名单（响应）：因 DID 级别不够而挡回 2 条
```

## 6. 25 项端到端

| 段 | 起什么 | 验什么 | 项 |
|---|---|---|---|
| 一 | 只开 `--did-guard-resp`，**不开** `--did-guard` | 读档：`62 F190` 放行（公开）、`62 F184` 超时（要写档）、`62 F1B0` 超时（要刷写档）。写档：`62 F184` 放行。刷写档：`62 F1B0` 放行。日志点名两类被挡的 DID，退账挡回 2 条 | 16 |
| 二 | 只开防火墙，响应侧关 | 读档读 `F1B0` → `62 F1B0` 原样出来（没有这道闸，锁死数据真的流了出去） | 5 |
| 三 | `--did-guard` + `--did-guard-resp` 都开 | 读档读 `F1B0` → `7F 22 33`（请求侧先挡，不是超时） | 4 |

段一是这套设计的关键：请求侧白名单**故意关着**，`0x22 F1B0` 只算"读"，读档就放行到了 ECU；
挡发生在 `62 F1B0` 回来的那一刻。这证明响应侧是独立的一层，不是请求侧的马甲。

## 9. 踩到的坑

1. **响应日志的 SA 带 `0x` 前缀**：`hex4` 输出 `0x0E00`，断言里写成 `SA 0E00` 全红。对日志字符串下断言前，先 `grep` 一眼真实输出再写。
2. **两行退账尾都带"因 DID 级别不够而挡回 N 条"**：请求侧是「DID 白名单：因…」，响应侧是「DID 白名单（响应）：因…」，用行尾 `$` 分不开；改用「白名单：因」这个请求侧专属前缀。

## 10. 与 M31 的关系

```
M31：请求侧    0x22 进去之前，按 DID 抬档 → 不够档替 ECU 回 7F 22 33
M32：响应侧    0x62 出来之前，按 DID 要档 → 不够档这条 62 不发（诊断仪超时）
```

两层是**同一张 `didTable`、同一个 `tierOf`、同一张 `decide`**，只有调用时机不同。所以
M31 的级别表（公开/受限/锁死）在 M32 原样生效，不用重新配。

## 11. 边界

- 只挡网关这一跳能看到的 `0x62`；能直接接 CAN 总线的人绕过。
- 拦截表现为"诊断仪超时"，不是显式的负响应 —— 现场排查要会看"没有 62 回来"这条线索。
- 表仍是命令行配置，能改配置就能提权（与 M30/M31 同一信任模型）。
- 只按 DID 分档，不管响应多长、多频繁：没有配额与速率。

## 12. 结论

M32 把 M31 的 DID 白名单从请求侧延伸到响应侧，复用同一张表与判定，在数据出网关的前一刻再查一次。请求侧与响应侧独立开关、独立退账，可分别对照验证。66 项单元（+18）+ 25 项端到端 + 36 步本地 CI 全绿。
